# Этап 02: Проверенный комплект и подготовка

- **Статус:** см. [план](../../plan.md).
- **Утверждённое ТЗ:** [spec.md](../../spec.md), приложение A.
- **План:** [plan.md](../../plan.md).
- **Зависимости:** 01 — identity, журнал и владение.
- **Покрытие:** REQ-02, 06–07, 11, 14–15, 19, 30–31; AT-02, AT-03, AT-10, часть AT-11.

## Цель этапа

Воспроизводимо выбрать и проверить кандидатный релиз и подготовить исполнимый план в отдельном staging.

## Контекст

`services/installation_manager/application/{base,install,update}.py`, `infrastructure/{docker_cli,dvt_lib}.py`, `docker-compose.yaml`, `scripts/offline/`. Зафиксируй переиспользуемый JSON-контракт комплекта и тестовые подписанные fixtures для Distributor и CI.

## Объём работ

1. Определи версию формата и тестовый контракт манифеста по §4, включая платформенные digest всех образов и Compose, bootstrap, профиль, переходы и совместимость мастера. Проверяй подпись, закреплённую цепочку доверия, хеши и разрешённый переход; поддержи срок действия/ротацию по задокументированной политике доверия. Только тестовые закрытые ключи в тестовой изоляции.
2. Собери явно сформированное окружение Compose, совместимое с сохранёнными секретами и профилями; смоделируй конфигурацию Compose и наблюдаемый проект, тома и привязки перед изменениями. Запрещай неподдерживаемые инфраструктурные переходы. Отдельно храни подготовленный, применённый и наблюдаемый релизы.
3. Для подготовки реализуй наблюдаемые проверки среды и реальные пути загрузки, bounded retry только для временных ошибок, общий deadline всего процесса Compose (включая молчание и потомков), оценку места и inode на фактических ФС. Учитывай containerd, распаковку, параллелизм, кэш, копии и прошлые образы. Диагностика должна называть конкретную причину и безопасное действие.

## Не входит в этап

Публичный Distributor, интерфейс работы с каталогом, window обслуживания и настоящее переключение работающей установки.

## Контракты и инварианты

Ни один staging-артефакт не меняет рабочий указатель. Пакет считается пригодным только после проверки по закреплённому digest; валидный входящий процесс не может пустым env перекрыть сохранённый секрет.

## Критерии приёмки

- [ ] `SAC-01`: Неверная подпись, digest, версия/платформа, конфигурация и рискованная смена инфраструктуры останавливают подготовку до изменений.
- [ ] `SAC-02`: Экземпляр с работающим DVT доступен при отказе TLS, Registry, места или inode. Повтор временного отказа работает на том же ID и манифесте.
- [ ] `SAC-03`: Эффективная конфигурация AI MCP сохраняет согласованные значения; секреты не отображаются; удержание молчащего Compose и его дочерних процессов ограничено.

## Проверки

`python -m pytest tests/unit/services/installation_manager` из venv; Compose config и контролируемые сбои TLS/MTU/Registry/диска на локальном изолированном Linux. Прогоны AT-02/03 на целевых ВМ повторяются в этапе 10. Python запускать через venv соответствующего репозитория с абсолютным корнем в `PYTHONPATH` там, где это требует AGENTS.md.

## Ожидаемые артефакты

- `report.md` по шаблону `$feature-coder`: изменения, наблюдаемые результаты, `PASS` / `FAIL` / `NOT_RUN`, команды и соответствие критериям.
- `artifacts/` при необходимости: только очищенные доказательства без секретов и больших пакетов.
- Для изменений DVT, требующих changelog, использовать `dvt-project-ops` и его helper; записать краткую запись по-русски.
