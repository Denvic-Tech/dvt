# Этап 04: Окно обслуживания и согласованная копия

- **Статус:** см. [план](../../plan.md).
- **Утверждённое ТЗ:** [spec.md](../../spec.md), приложение A.
- **План:** [plan.md](../../plan.md).
- **Зависимости:** 01–03 — журнал, staging, исполнитель.
- **Покрытие:** REQ-16–17, 19, 28, 30; AT-07, предпосылка AT-09.

## Цель этапа

Остановить новые корневые задачи, дать текущим цепочкам завершиться и снять проверяемую точку восстановления без старых писателей.

## Контекст

`src/modules/task_execution`, `services/orchestrator/deps/commands.py`, Scheduler и `docs/extension-identity-migration.md`; команды и AGENTS.md для модулей и миграций. Применить `module-context-builder`, если меняется bounded context.

## Объём работ

1. Привяжи персистентный guard к авторитетному приёму задач; выбирай с учётом конкурентной транзакции и совместимости старого перехода. Определи судьбу существующих queued/started/running задач, цепочек NODE и расписаний. Сценарий для предшественников без guard закрывает авторитетные входы и сохраняет разрешённые текущие цепочки или останавливает операцию до окна.
2. Жди завершения работ с дедлайном и предусмотренным операторским действием; останови все старые процессы записи либо гарантируй отсутствие записи, включая постоянные файлы. Приостановка должна переживать замену и не разрешать работу на несовместимой схеме. Зафиксируй метаданные и действия в журнале.
3. Создай согласованную копию PostgreSQL и постоянных данных, включая extension, identity и конфигурацию; manifest копии хранит digest, ревизию, параметры и ID. Проверь читаемость и целостность, права и возможность сохранения вне рабочего диска; покажи политику хранения и предполагаемую границу потери.

## Не входит в этап

Мигратор и полное применение, восстановление целевого экземпляра (этап 06). Не добавляй отдельную политику ретраев задач в Orchestrator.

## Контракты и инварианты

PostgreSQL авторитетен по задачам. WORKER_LOST не повторяет работу; дочерние допустимы для уже начатой цепочки. Существующая очередь и due schedules обрабатываются по зафиксированной политике; перед изменением схемы старых писателей нет.

## Критерии приёмки

- [ ] `SAC-01`: Гонка с новым внешним запуском закрывается в авторитетном пути; API и Scheduler блокируются, активная NODE-цепочка может завершиться.
- [ ] `SAC-02`: Политика queued/Scheduler видна, worker loss не создаёт повтор, прерывание исполнителя сохраняет защиту.
- [ ] `SAC-03`: После завершения записей копия полная, содержит совпадающие метаданные и проходит проверку целостности, включая отдельный каталог копий.

Python запускать через venv соответствующего репозитория с абсолютным корнем в `PYTHONPATH` там, где это требует AGENTS.md.
