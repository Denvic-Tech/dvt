# Этап 08: Офлайн-архив из того же комплекта

- **Статус:** см. [план](../../plan.md).
- **Утверждённое ТЗ:** [spec.md](../../spec.md), приложение A.
- **План:** [plan.md](../../plan.md).
- **Зависимости:** 02–07 — manifest, Linux bootstrap, применение и Distributor.
- **Покрытие:** REQ-04, 09, 11, 27, 29, 32; AT-12.

## Цель этапа

Дать поддерживаемый офлайн bootstrap и общий lifecycle вместо отдельного shell-потока применения.

## Контекст

Backend: `scripts/offline/`; Distributor: `services/offline_download/{application/build_service.py,infra/archive.py,seed_data/dvt/}` и docs о Docker packages. Не менять DCC.

## Объём работ

1. Сформируй archive из того же signed manifest: Compose, образы всех зависимостей, bootstrap, скрипты, хеши контейнерных архивов и пакеты Docker для заявленных платформ. Ограничь распаковку проверенными путями/размерами; обнаруживай недостающие ресурсы до применения.
2. Проверь подпись/содержимое с установленными корнями доверия, платформу, локальные image ID/manifest digest и mapping после импорта; исключи выбор неподтверждённого локального тега. Подготовь локальные пакеты расширений и зависимости профиля; при недоступной зависимости остановись до maintenance.
3. Передай результат обычному исполнительному пути, сохраняя ID, блокировки, порядок миграции, контроль ресурсов и восстановление. Старые CLI входы должны вести в тот же согласованный жизненный цикл при поддерживаемом переходе.

## Не входит в этап

Незаявленные платформы/профили расширений, production публикация архива, отдельный обход обязательных проверок.

## Контракты и инварианты

Офлайн не требует DNS/TLS/Registry. Никаких подмен digest тегом и доверия к файлам до проверки. Linux путь использует тот же checkpoint и схему приёма задач.

## Критерии приёмки

- [ ] `SAC-01`: Подмена содержимого, препятствующие распаковке пути и несовместимость отвергаются до изменений.
- [ ] `SAC-02`: На проверенной платформе при отключённой сети проходят холодная установка, обновление и восстановление, включая заявленные расширения.
- [ ] `SAC-03`: Офлайн, UI и CLI конкурируют за общую блокировку и переиспользуют закреплённый комплект.

## Проверки

Из venv тесты офлайн сборки Distributor и DVT; bash syntax; VM с отключённой сетью и холодным кэшем для AT-12; проверить сохранность старого DVT при неполном архиве. Python запускать через venv соответствующего репозитория с абсолютным корнем в `PYTHONPATH` там, где это требует AGENTS.md.

## Ожидаемые артефакты

- `report.md` по шаблону `$feature-coder`: изменения, наблюдаемые результаты, `PASS` / `FAIL` / `NOT_RUN`, команды и соответствие критериям.
- `artifacts/` при необходимости: только очищенные доказательства без секретов и больших пакетов.
- Для изменений DVT, требующих changelog, использовать `dvt-project-ops` и его helper; записать краткую запись по-русски.

## Правила выполнения

- Выполнять только этот этап по явному делегированию `$feature-coder`. Чужие незакоммиченные изменения сохранить.
- Не редактировать файлы мастера `spec.md`, `plan.md`, `task.md`, `fix_task.md`. Git-коммиты, теги и push не выполнять.
- Никаких сбойных экспериментальных действий на действующих установках. При блокере указать его и требуемое решение в отчёте и сообщении мастеру.
