# Этап 06: Продолжение, восстановление и переход со старых установок

- **Статус:** см. [план](../../plan.md).
- **Утверждённое ТЗ:** [spec.md](../../spec.md), приложение A.
- **План:** [plan.md](../../plan.md).
- **Зависимости:** 01–05 — полный путь применения.
- **Покрытие:** REQ-04, 20–22, 26–28, 29–31; AT-04–06, AT-08–09, AT-13.

## Цель этапа

Проверять состояние после рестарта, поддержать legacy и вернуть рабочую установку с согласованной копии.

## Контекст

`services/installation_manager`, `services/gateway/update_runtime`, `uninstall.sh`, старые Compose/режимы bootstrap, история релизов и кандидатные релизы; текущий наблюдаемый digest нельзя получать из `.env`.

## Объём работ

1. Добавь версионированный opt-in переход с legacy; сохрани identity, фактическую модель проекта и хранилищ, параметры и bind. Сверь работающие образы и схему; явные несоответствия вынеси в план. Не придумай миграцию для неподдерживаемого predecessor.
2. Реализуй матрицу безопасных операторских действий из §9 и возобновление по наблюдаемым ресурсам. При мёртвом мастере верни совместимый образ, адрес и ту же операцию независимо от судьбы приложения. Различай ошибки до начала, неизвестный результат и уже целевую схему; сначала завершай целевой запуск, когда поддерживается.
3. Реализуй контролируемый возврат: блокировать неподдерживаемый downgrade до изменений; для потери данных требуются показ времени копии и отдельное подтверждение. Восстанови БД, конфигурацию, identity, файлы и расширения на чистом тестовом хосте, проверь прежние образы, auth, ETL, договорённости по задачам и URL перед открытием приёма. Отдельно покажи destructive plan удаления, если покрывается выбранным входом.
4. Дай авторизованный исторический/диагностический пакет по ID с ограниченным безопасным выводом, стабильными кодами и указанием разрешённых операторских действий. При испорченной копии журнал и защита записи сохраняются.

## Не входит в этап

Публичная активация, реальные данные клиентов, обновление сторонних профилей без проверок.

## Контракты и инварианты

Никакого возврата старых образов к неподтверждённой схеме; после восстановления проверка обязательна. Штатный и ручной аварийный путь используют общий журнал и блокировку. Диагностика не выдаёт секретов.

## Критерии приёмки

- [ ] `SAC-01`: Старые сценарии совместимости и устойчивая identity подтверждены; несовпадающий .env не подменяет наблюдаемую версию.
- [ ] `SAC-02`: После обрыва новый владелец учитывает подтверждённую миграцию и сохраняет исходный отказ; сломанный новый мастер не теряет URL и журнал.
- [ ] `SAC-03`: Запрещённая схема блокируется, полное восстановление на чистой изолированной ВМ возвращает вход, файлы, проекты/extension и контрольный ETL; измерены время и граница потери.
- [ ] `SAC-04`: В диагностике нет секретов; повреждённый backup нельзя отметить успешным.

## Проверки

Регрессии venv мастера/Gateway; тест рестартов на нескольких стадиях; чистая изолированная ВМ для AT-09; AT-06 для исторических маршрутов и supported candidate. Зафиксировать digest и ревизии. Python запускать через venv соответствующего репозитория с абсолютным корнем в `PYTHONPATH` там, где это требует AGENTS.md.

## Ожидаемые артефакты

- `report.md` по шаблону `$feature-coder`: изменения, наблюдаемые результаты, `PASS` / `FAIL` / `NOT_RUN`, команды и соответствие критериям.
- `artifacts/` при необходимости: только очищенные доказательства без секретов и больших пакетов.
- Для изменений DVT, требующих changelog, использовать `dvt-project-ops` и его helper; записать краткую запись по-русски.

## Правила выполнения

- Выполнять только этот этап по явному делегированию `$feature-coder`. Чужие незакоммиченные изменения сохранить.
- Не редактировать файлы мастера `spec.md`, `plan.md`, `task.md`, `fix_task.md`. Git-коммиты, теги и push не выполнять.
- Никаких сбойных экспериментальных действий на действующих установках. При блокере указать его и требуемое решение в отчёте и сообщении мастеру.
