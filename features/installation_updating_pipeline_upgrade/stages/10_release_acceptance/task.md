# Этап 10: Release gate, документация и сквозная приёмка

- **Статус:** см. [план](../../plan.md).
- **Утверждённое ТЗ:** [spec.md](../../spec.md), приложение A.
- **План:** [plan.md](../../plan.md).
- **Зависимости:** 01–09 — приняты все продуктовые компоненты.
- **Покрытие:** REQ-08, 10–11, 28, 32; все AT-01–AT-13.

## Цель этапа

Не допускать выпуск неполных или не проверенных клиентским путём комплектов. Проверить и документировать весь сценарий на целевой матрице.

## Контекст

Backend release Bake и `services/ui` gitlink, sibling `../dvt_cicd` (`.ci/gitlab/jobs/{02-build-test,04-release-flow}.yml`), Distributor и отдельный UI. Локальный тестовый Registry/mirror допускается; production rollout и push запрещены без отдельного разрешения.

## Объём работ

1. Расширь сборку и promotion без пересборки: immutable digest всех образов/infra, Compose/bootstrap, build SHA backend и pinned UI, идентичный digest migrate/Gateway, тестовый манифест кандидата. Укажи владеющие сервисы и конфигурацию для настоящих ключей вне git. Доставь через изолированные клиентские каналы и фиксируй readiness атомарно после тестов; не используй подмену build context для официального release.
2. Реализуй воспроизводимый сценарий изолированных ВМ и прогони AT-01–AT-13: Debian 13, Ubuntu 24.04 LTS, `linux/amd64`; Debian 12 при охвате, обновление исторических маршрутов и кандидата, прожитые restart и failure cases, полное restore на другой чистой ВМ и offline без сети. Доказательства без секретов. Недоступные обязательные тесты блокируют принятие этапа.
3. Добавь руководства для bootstrap, основной UI, защищённой ссылки, CLI/офлайн, диагностики и аварийного восстановления. Измерь время, действия, сеансы, простой, продолжения и время восстановления, документируй условия и пороги и выведи неподтверждённые профили из заявленной поддержки.
4. Проверь dry run для неполного и подменённого release и для сбоя promotion: командный результат должен блокировать выдачу релиза как готового; подготовь документированную последовательность переключения проектов.

## Не входит в этап

Push, публичная публикация, production, развёртывание у клиентов, управление парком (P2).

## Контракты и инварианты

Список готовых версий видит лишь успешно проверенные неизменяемые комплекты. Отсутствие пройденного критического теста блокирует выпуск. Поэтапные коммиты остаются локальными, реальные секреты никогда не входят в отчёт.

## Критерии приёмки

- [ ] `SAC-01`: Все AT имеют ожидаемый результат и доказательства на заявленной матрице; пользовательские сценарии проверены на реальных Linux ВМ.
- [ ] `SAC-02`: Артефакты продвигаются по digest без пересборки; ошибки e2e, неполный набор и подмена не дают запись готовности.
- [ ] `SAC-03`: Документация и метрики совпадают с фактическими действиями и политикой профиля; готовность к локальной приёмке отделена от внешнего запуска.

## Проверки

CI/Bake config и синтаксис; интеграционные и E2E на кандидатах с клиентскими каналами. Для каждого AT фиксируй платформу, digest, Compose CLI, скрипт/шаги, фактический результат и ограничения. Моки могут дополнить, но не заменить обязательные прогоны на ВМ. Python запускать через venv соответствующего репозитория с абсолютным корнем в `PYTHONPATH` там, где это требует AGENTS.md.

## Ожидаемые артефакты

- `report.md` по шаблону `$feature-coder`: изменения, наблюдаемые результаты, `PASS` / `FAIL` / `NOT_RUN`, команды и соответствие критериям.
- `artifacts/` при необходимости: только очищенные доказательства без секретов и больших пакетов.
- Для изменений DVT, требующих changelog, использовать `dvt-project-ops` и его helper; записать краткую запись по-русски.

## Правила выполнения

- Выполнять только этот этап по явному делегированию `$feature-coder`. Чужие незакоммиченные изменения сохранить.
- Не редактировать файлы мастера `spec.md`, `plan.md`, `task.md`, `fix_task.md`. Git-коммиты, теги и push не выполнять.
- Никаких сбойных экспериментальных действий на действующих установках. При блокере указать его и требуемое решение в отчёте и сообщении мастеру.
