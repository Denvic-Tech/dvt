# Сквозная матрица подписанного релиза DVT

## Подготовка воспроизводимого прогона

1. Забронируйте изолированные Debian 13 и Ubuntu 24.04 LTS amd64 и отдельный
   пустой snapshot получателя для восстановления. Начальная конфигурация
   стенда 2 vCPU, 4 ГиБ RAM, 30 ГБ диска, один воркер, локальные PostgreSQL
   и Valkey. Это параметры первого эксперимента. Поддержку и цели по времени
   подтвердит серия измерений для подписанного профиля.
2. Подготовьте снимок каждой ОС без Docker, Compose и данных DVT и отдельный
   пустой Docker/containerd data root для холодного pull. Снимки со старым
   bootstrap создайте для каждого исторического маршрута с контрольными
   пользователем, проектом, файлом, настройкой, установленным расширением и
   источником ETL. Для заявленного Debian 12 добавьте отдельную строку на
   amd64, сценарии и подтверждённый маршрут. Поддержку arm64, внешней БД,
   иных сетевых профилей и количества воркеров описывайте после их испытаний.
3. Соберите все продуктовые образы из точного backend commit с pinned UI
   через release Bake. В изолированном registry используйте свои имена
   образов и CA. Привяжите к манифесту PostgreSQL и Valkey, полный Compose
   и самодостаточный bootstrap. Подпишите test signer с отдельным корнем,
   поместите статические файлы по путям из подписанного манифеста.
4. Запустите `python -m services.dvt_distribution.releases.candidate` из
   venv Distributor с `--manifest`, `--trust`, `--origin` и
   `--artifact-origin`. Процесс слушает loopback. Поместите его за закрытым
   HTTPS ingress и разрешите доступ выделенным ВМ. Offline Download
   направьте в этот каталог с тем же trust и с сертифицированным bundle
   signer. Используйте настоящее скачивание OCI слоёв и артефактов. Подписанный
   продуктовый комплект для официальной job остаётся тем же набором байтов,
   который подготовил CI, и может получать слои и артефакты через конечные
   client URL по digest. Handoff-окружение, DNS, сертификаты и ACL проверяются
   отдельно от внешнего адреса приложения.
5. Зафиксируйте идентификатор публичного корня и подписанта, digest манифеста,
   название снимка ОС, параметры ВМ, роли, версии Docker/Compose и профиль.
   Снимите факты до сценария и после него. На ВМ используйте
   `sudo bash scripts/release/capture_vm.sh PROJECT DATA TMP BACKUP [CONTAINERD_ROOT]`
   из доверенного checkout. Сохраняйте только digest, состояние ролей,
   численные замеры, санитизированные события и результаты проверок.
   Секреты, cookies, CA private key, bootstrap-коды, заголовки
   авторизации, полные `.env`/inspect и данные клиентов остаются вне evidence.
6. Пройдите AT-01 на обеих ОС. Распределите AT-02–AT-13 по ВМ матрицы и
   возвращайтесь к исходному снимку между независимыми сбоями. Оставьте управление хостом за отдельной консолью или
   интерфейсом. Отказы ограничьте isolated Docker/signing namespace и
   тестовыми адресами. При смене байтов bootstrap, Compose, манифеста или
   образа заведите новую строку доказательств для нового комплекта.

## Сценарии

| Код | Действия в изолированном стенде | Наблюдение для PASS |
| --- | --- | --- |
| AT-01 | Пустой snapshot без Engine и Compose. Подайте подготовленный bootstrap и разрешите установку Docker. Зафиксируйте холодный кеш. Пройдите путь в браузере до первого входа. Повторите команду с теми же параметрами и затем запросите другой каталог с тем же project/портом. | Системные изменения после разрешения, один ID экземпляра, первый администратор входит, данные и ports сохранены, конфликт отказал. Запишите действия, SSH-сеансы и время от вызова до входа. |
| AT-02 | С работающего источника начните подготовку. По очереди внесите временный обрыв на HTTPS listener, незнакомый CA в тестовом TLS профиле, отключение scoped Registry, задержку вызываемой команды Compose сверх policy, уменьшение MTU на тестовом пути исполнителя. Для кратких отказов затем верните доступ. | Краткий отказ продолжился с тем же ID. Постоянный показал причину и действие. Зафиксированы время, повторы и выход зависшей команды. Старый комплект проходит контрольный запрос. |
| AT-03 | На копии снапшота размещайте Docker, containerd, data и backup в отдельных тестовых ФС. Для каждого варианта задайте безопасный ограниченный размер либо число inode. Измерьте дефицит до операции. В отдельном повторе исчерпайте ресурс после начала скачивания. | Указана конкретная ФС и дефицит. Применение не началось. Старые образы и публичный DVT рабочие при отказе в процессе подготовки. |
| AT-04 | С нестандартным портом мастера примените полный Compose. В отдельных опытах остановите переход нового менеджера на `Created` и вызовите неуспешный старт контролируемой тестовой конфигурацией. Повторите с уже записанным результатом миграции. | Исполнитель продолжает независимо от мастера. Старый совместимый образ возвращает HTTPS, исходные адрес и ID открываются в той же вкладке. Подтверждённая миграция не повторяется. |
| AT-05 | Прервите ответ на POST после того, как приложение зафиксировало допуск. Повторите с исходным ключом, в другой вкладке и одновременно с CLI. Перезапустите мастер при подготовке. Перезапустите ВМ между подтверждёнными checkpoint до и после миграции. | Один владелец и ID. Журнал и наблюдаемое состояние дают безопасный следующий шаг. Запишите число отказов с продолжением и сколько возобновились автоматически. |
| AT-06 | Зафиксируйте версии и схему старых установок. Пройдите исторические 1.22.0 → 1.23.0 и 1.23.0 → 1.24.0-rc2 на историческом канале. Затем выполните актуальный выбранный переход с поддерживаемого подписанного источника. Включите AI MCP. Проверьте вход, проект, файл, настройки, установленное расширение, identity и пригодность прежних ключей. Проверьте ревизию, воркеры, ETL и вызов инструмента MCP. | Точные образы и исходные данные подтверждены. Контрольные ETL и MCP успешны. Запишите отдельно подготовку, загрузку, окно обслуживания и HTTP-недоступность. Исторические маршруты доказывают регрессии, доступные новые переходы определяет подписанный манифест. |
| AT-07 | Запустите ETL с дочерней цепочкой, длительную запись и задание по расписанию. Откройте обслуживание, попробуйте независимый старт и прервите выбранного тестового воркера во время работы. | План объясняет причину ожидания и возможность переноса. Ранее принятая цепочка обслужена, новые независимые работы блокированы, потерянный воркер не вызвал повтор записи. |
| AT-08 | В отдельных снимках целенаправленно внесите отказ до миграции, во время известной миграционной транзакции, на установке тестового расширения и на старте Gateway после подтверждённой схемы. | Журнал различает фактическую ревизию, расширение и готовность Gateway, Proxy и MCP. Фиксация контекста предотвращает записи старого комплекта при несовместимой схеме. Отказ оставляет действие для диагностики или восстановления. |
| AT-09 | Попытайтесь подготовить несовместимое понижение. Создайте проверенную логическую копию, отделите её от исходного диска, на пустом получателе проверьте `portable_restore plan` и восстановите данные. Выполните `restore_runtime start` и `finalize`, вход, проект с расширением и контрольный ETL. | Понижение остановилось до применения, восстановлен предыдущий комплект и состояние на точку копии. Замерьте длительность и потерю записей после согласованной точки. |
| AT-10 | На действующем экземпляре сохраните параметры и один валидный MCP secret. Запустите мастер с пустым одноимённым значением в его окружении. Пройдите план и применение с выбранным profile, портом и репликами, вызовите MCP и ETL. | Действует сохранённая конфигурация, все роли профиля находятся в манифесте и имеют те же digest. Значения секретов отсутствуют в UI и доказательствах. |
| AT-11 | В private namespace приготовьте неполную поставку и остановите ready-проверку. В другом запуске смените тестовый latest после pin, подайте ошибочную подпись, подтвердите RC и выключите private каталог после очистки сети или после завершения проверки пакета. | Не прошедший gate набор отсутствует в ready-каталоге, изменённая подпись/bytes отклоняются. Выбор RC явный. Проверенная операция продолжает использовать свой digest, ошибки каталога видны. |
| AT-12 | Получите install и update bundle через настоящий Offline Download для exact digest. Снимите список локальных зависимостей и отключите сеть получателя в изолированном профиле, сохранив консоль. Выполните команды офлайн установки и обновления, затем локальное восстановление и проверку контрольного проекта. | В журнале подтверждены подпись, платформа, профиль, образы и та же миграция. Все операции работают автономно, захват попыток сетевого доступа и состояние сети сохранены. |
| AT-13 | Из отдельного браузера попробуйте вызвать привилегированный API и `/setup` без привязки. Повторите и просрочьте код. Выполните законный вход, настройку администратора после bootstrap и выгрузку диагностики. | Отказы ожидаемые, setup требует свой одноразовый вход. Авторизованный путь после открытия мастера выполняется в браузере. Диагностика проверена на раскрытие конфигурации и секретов. |

## Измерения и receipt

Действием считайте команду, подтверждение или отправку формы. Сеанс SSH считайте
при установлении нового соединения. Время до входа начинается до вызова bootstrap
и заканчивается успешным входом администратора. Замерьте начало и конец подготовки
и загрузки по журналу, окно обслуживания по замороженному планировщику/gate,
недоступность по регулярным HTTP-пробам с рабочей станции каждые 1–2 секунды.
Укажите интервал и критерий готового запроса. Долю автоматического продолжения
рассчитывайте как количество автоматически возобновлённых сценариев из всех
сценарных отказов AT-05. Для restore замеряйте время от запуска подготовки
на чистой ВМ до проверки входа/ETL и время между точкой копии и началом отказа.
Храните численный объём данных и inode вместе со временем, чтобы сравнивать
сопоставимые прогоны.

Создайте пустую матрицу из зафиксированного пакета через DVT venv.

~~~sh
PYTHONPATH="$DVT_CHECKOUT" "$DVT_VENV/bin/python" -m scripts.release.acceptance \
  --manifest "$PACKAGE/manifest.json" --trust "$TRUST" --pipeline-id "$PIPELINE_ID" \
  --template "$PRIVATE_CATALOG_ORIGIN" --output "$EVIDENCE_DIR/matrix.json"
~~~

Заполните идентификатор ВМ, версии Docker/Compose без префикса `v`, карту
наблюдённых repository@digest и замеры. Для AT-06 и AT-10 включите в карту
образ AI MCP. Для AT-09 заполните `restore_target` с идентификатором отдельной
чистой ВМ, её ОС, платформой и версиями Docker/Compose. Для каждого сценария
укажите `PASS`, `FAIL` или `NOT_RUN`. Матрица требует AT-01 в каждой строке
и совокупное покрытие остальных сценариев. В `evidence`
укажите имена соседних файлов и их `sha256:<hex>`. Свяжите в файлах имя
snapshot, профиль, операции и события со всеми подпунктами конкретного AT.
Публикующий receipt может сформировать только защищённая job, после успешного
backend integration и полного набора реальных доказательств.

Целевое время и пороги поддержки зафиксируйте после серии сопоставимых
измерений на каждой заявленной ОС и нагрузке. Вне охвата остаются сценарии
без прогона, в том числе большой ETL, нестандартные сети и восстановление
без отдельной проверенной копии.
