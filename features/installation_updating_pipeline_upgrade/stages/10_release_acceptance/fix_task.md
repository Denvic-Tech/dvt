# Повторный запуск установки при исчезновении bootstrap-мастера

- **Статус ревью:** `CHANGES_REQUESTED`.
- **Связь:** AT-04, AT-05, REQ-02 и REQ-14.
- **Исполнитель:** исходная сессия этапа 10.

Стенд Ubuntu 24.04, Compose 5.7.1, Engine 29.10.0, подписанный кандидат
`sha256:3befb0aeb9c55eec995fa192e218b7da210c9d842457006ec731f34ce523ab8f`.
После временного снятия bootstrap-контейнера перезапущенный хостовый
исполнитель продолжил подготовку операции
`803dc50a-fe6f-4de1-b7c0-8e419075073d`. Загрузка прошла,
журнал записал `prepared` при пустом составе исходных контейнеров.
Применение остановилось с `manager_unavailable`. После запуска прежнего
закреплённого образа мастера на том же адресе действие «Продолжить операцию»
вернуло 202 и привело к `incompatible_release` в том же `prepared`.
Gateway, БД или применение миграции к этому моменту отсутствовали.
Доступна штатная отмена до изменения приложения.

Критерий исправления. Установка при временном отсутствии bootstrap-мастера
оставляет работающий путь продолжить тот же ID после его восстановления.
Проверь, что подготовка диска и образов может пережить перезапуск и что
документы применения сохраняют проверенный исходный digest. Возврат
доверенного закреплённого мастера до переключения не должен стать основанием
для отмены или новой операции. Запуск с неожиданным контейнером, digest,
портом или другим экземпляром по-прежнему отклоняется. Не допускай замены
уже применённого мастера или ослабления защиты схемы. Сохрани offline
и guard-capable update контракты. Нужны адресная регрессия и обновлённый отчёт.

## Потерянный ответ при новой установке после отмены подготовки

Chromium сохранил отменённую операцию из истории. Затем реальный POST
допустил новый экземпляр намерения для того же тестового релиза
`sha256:3befb0aeb9c55eec995fa192e218b7da210c9d842457006ec731f34ce523ab8f`.
Ответ 202 намеренно прерван. На Debian новая операция
`76249e8f-3385-4b7c-b15e-0006d467ce7a` скачала слои. На Ubuntu
`99df0ede-7bde-4175-8edb-dd8a68b00a2b` дошла до применения со схемой
`0070`. Обе вкладки продолжили показывать отменённую строку.
Таймер браузера завершился с timeout. На первом запуске без истории
потеря ответа ранее проходила.

Критерий исправления. Обнаруживать операцию, допущенную сохранённым новым
намерением. Переход с отменённой строки должен выбрать тот же UUID после
потери 202, в том числе если операция уже завершилась до следующего GET.
При переключении между старыми строками без ожидающего намерения адресный
просмотр сохраняется. Учитывать совпадение закреплённого манифеста и вида
операции, не выдавать чужую операцию за подтверждённую. Нужна регрессия
с существовавшей terminal-записью, защищённой ссылкой или явным просмотром
истории и потерянным 202.

## Порядок проверки доставки и записи тегов

В текущем release job `promote_dvt_release` вызывается до проверок
`services.dvt_distribution.releases.publish`. Первый шаг допускает
запись тегов версии и stable latest при совпадении receipt по SHA.
Второй шаг сверяет подпись, Git commit и UI, Compose/bootstrap по HTTPS
и полноту OCI. ReadyStore при таком сбое остаётся закрытым, однако прежний
клиент, читающий тег, может увидеть комплект до строгой проверки.

Критерий исправления. До записи любого тега release job выполняет строгий
read-only контроль того же подписанного пакета и полного пути доставки.
Сбой этого контроля не запускает promotion. После promotion остаётся
проверка и единственная условная запись готовности. Подтвердить порядок
тестом с отказом до вызова Registry writer.

## Повторный прогон Ubuntu. Профиль без AI MCP блокируется на готовности

Исправленный образ мастера
`sha256:60d9dc979cdc8eeef4461af1f0d62a67508dc792a2f074c870c87c2f8b168006`,
новый private manifest
`sha256:323d428f8de585dec0ab6171f1f3a9a2e3beaacf46a0e6645069f5f233b62f97`.
Chromium после потери 202 восстановил новый ID
`59bb593a-ac4f-480f-82f2-79fda31c28a7` с прежней отменённой строкой
в истории. Без контейнера мастера продолжение дошло до проверки и осталось
`preparing/manager_unavailable` без plan. Штатный host resume восстановил
закреплённый мастер и тот же ID. Мигратор завершился с кодом 0, схема
`0070`. Gateway, UI, Worker и Scheduler прошли собственные проверки.

Операция осталась в `verifying`. С отключённым в подписанном профиле
AI MCP сервис отсутствует в Compose, но публичный GET /mcp на реальном
Proxy возвращает HTTP 200 `text/html`. Проверка готовности требует 404.
В Caddyfile обработчик disabled написан отдельной директивой `respond`,
запрос попадает в общий `handle` UI.

Критерий исправления. На штатном Proxy выключенный профиль отвечает 404
для /mcp и его подмаршрутов, UI и API сохраняют обработчики, включённый
профиль по-прежнему маршрутизируется в AI MCP. Пройти проверку на Caddy
и затем на частном Ubuntu кандидате с обновлённым Proxy. Readiness
для выключенного профиля должен по-прежнему требовать 404.
Исходный release pin зависшей операции сохраняется.

## Восстановление копии защищённой онлайн-установки

Реальное обновление Debian `1.24.0-rc2 → 1.24.1-rc1` со схемой
`0070` завершилось по ID `939f34cd-26f0-4cea-a432-1f474f0f9dbc`.
Исходный проект и аккаунт прошли проверку, реальный ETL и project-scoped
MCP вернули ожидаемый результат. Манифест точки восстановления
`sha256:33bcbd6987ffde087353380011d2a580427a4b679c2b4f740658dea2cec4bb7c`,
граница данных `2026-11-17T06:43:38.519909+00:00`.

На отдельной Ubuntu PostgreSQL и постоянные файлы восстановились за
4,014 с в отсутствовавший канонический каталог, gate остался заморожен,
файл после отсечки отсутствовал. Допуск запуска перешёл в
`recovering/compose` до создания контейнеров. В закрытом Compose
копии только Gateway имеет обязательную пару read-only Gateway bind
`/run/dvt-operator/ca.pem` и `/run/dvt-operator/gateway-token` и
дополнительную сеть мастера `default`. Мигратор остаётся в `dvt-net`
с исходными монтированиями приложения. `_validate_runtime` при
восстановлении сравнивает уже расширенный Gateway с мигратором целиком.

Критерий исправления. При проверке закрытого сохранённого Compose
распознавать точную пару root-owned source bindings из канонического
каталога и точную сеть мастера, сверить форму и принадлежность обоих
перед сравнением базовых mounts и сетей. Сохранить все защищённые bind и
сети в фактически применяемой модели. Не принимать частичную пару,
подмену source, writable bind, лишние сети или изменения мигратора.
Переиспользовать общую проверку там, где она сохраняет контракт.
Продолжить восстановление проверенного point с прежним ID, сохранить
проверки авторизации/проекта и открыть gate только после их PASS.
Нужна регрессия с ранее расширенным Compose, покрытием допустимых
offline/legacy и отказом на постороннее расширение.


### Функциональное доказательство при замороженном приёме

После исправления Compose этот же ID запускает закреплённые роли и
достигает `verifying`. Реальный исходный администратор получает HTTP 200
на вход и GET /api/user/info. GET сохранённого проекта и GET /api/extensions
отвечают HTTP 503 `SYSTEM_UPDATING` и через Proxy, и через loopback Gateway.
`finalize` не может доказать прежний проект, gate остаётся закрытым. В
прошлом офлайн испытании источник не имел этой конфигурации защищённого
монитора.

Критерий исправления. Перед открытием gate подтвердить исходного
администратора, доступ к указанному проекту и сохранённые расширения
при закрытом публичном API. Использовать штатные read-only проверки
или ограниченный локальный эквивалент, работающий с исходным
закреплённым Gateway. Сохранить прежние образы, gate и ограничения
обычных запросов до подтверждения. Проверить отказ для ошибочного proof
и возобновление того же ID после корректного. После resume проверить
прежний вход, проект, расширения и выполнение реального ETL.


## Глобальное имя контейнера занято другим Compose-проектом

В отдельном offline namespace Ubuntu операция
`a00b91e6-551f-4623-b787-2a8d35b538e8` проверила подписанный архив
`3bef…` и дошла до `prepared`. Её Compose для PostgreSQL
содержит буквальное `container_name: dvt-postgres`. На том же Docker
это имя удерживает штатно остановленный контейнер другого тестового
проекта `dvt-s10-debian`. Подготовка смотрела только label текущего
Compose-проекта, пропустила коллизию, а применение застряло в
`migrating/database_unavailable` до создания PostgreSQL.

Критерий исправления. При нормальной проверке Compose перед plan
проверять глобальную принадлежность явно заданных имён контейнеров,
включая остановленные контейнеры. Имя другого проекта или другой роли
вызывает понятную блокирующую ошибку до применения. Пустая площадка
и своё совпадающее service name продолжают работу. Сохранить исходные
проверки digest, mounts, ports и label. Для диагностики продукта
добавить регрессию с другой Compose-меткой. Продолжение уже подготовленного
лабораторного восстановления после освобождения имён идёт по тому же
ID и манифесту.

## Публичная команда установки запускает прежний мастер

На Debian 13 команда `bash <(sudo curl -fsSL https://raw.distribution.denvic.tech/dvt/install.sh)`
запустила публичный HTTP-мастер из `installation_manager:latest`. Этот
мастер ответил 404 на `/api/operations/active`. Старый API сообщил
`installed=false, running=true`, и браузер показал «Обновление».
Публичный каталог вернул 404. Новая документация предлагала оператору
самостоятельно получить `bootstrap.py`, digest и файлы TLS. Пользователь
подтвердил, что внешняя команда установки должна остаться прежней.

- Исправить текущий этап 10 без изменения утверждённого ТЗ. Сохранить URL,
  команду и одно начальное действие на чистом хосте. Имя `bootstrap.py`
  может использоваться внутри поставки и рантайма. Убрать его ручную
  подготовку из основного клиентского сценария.
- Довести сценарий от точки выдачи до защищённого мастера. Публичный
  запуск получает утверждённый комплект для чистой установки по HTTPS.
  Использовать проверенную цепочку доверия, точный хеш загружаемого
  bootstrap и digest образа из подтверждённой поставки. Отказ каталога,
  отсутствие утверждённого комплекта, подмена или ошибка TLS завершают
  запуск понятной ошибкой до изменения хоста. Не переключаться автоматически
  на старый HTTP-мастер. Согласованный маршрут старых установок и
  аварийный ручной путь должны оставаться доступны.
- Подготовить конфигурацию каталога и локальный TLS мастера без ручной
  загрузки файлов оператором на чистый хост. Допускаются интерактивные
  подсказки в том же запуске и доступ к мастеру через существующий SSH
  административный канал. Сохранить явное согласие на установку системных
  пакетов, проверку TLS и повтор с прежним ID и привязкой. По уточнению
  пользователя публичный `install.sh` использует синтаксис POSIX shell.
  Первоначальная установка, повтор и автоматическое продолжение после
  перезагрузки работают на ВМ без системного Python. Внутреннюю логику
  мастера и подготовленные артефакты можно выполнять в закреплённом образе.
  Публичный URL DVT и адрес мастера остаются отдельными.
- В документации описать прежнюю однострочную команду и подготовку её
  публичной выдачи, включая чёткую проверку готовности каталога. Для
  непубличной приёмки обеспечить тот же путь с тестовой конфигурацией
  источника. Не менять публичные сервисы, production или состояние чужих
  установок в ходе исправления.
- Добавить регрессионную проверку на запуск через Bash из process
  substitution, передачу проверенной конфигурации и отказ на подменённых
  артефактах или недоступности источника. Проверить повтор без смены
  мастера и TLS. По остальным сценариям переиспользовать целевые тесты.

## Автоматический выпуск RC и stable

После push тега задачи DVT должны снова автоматически собрать образы один раз,
проверить кандидатов по digest и присвоить версию. Для stable также обновляется
`latest`. Перед изменением тегов проверяются исходные digest и конфликты уже
опубликованных версий. Сохранить диагностические артефакты неуспешной сборки.
Использовать имеющийся runner DVT и текущие учётные данные Registry.

Удалить ручную приёмку из выпуска образов, её окружение, evidence directory и
обязательную передачу receipt в обычный выпуск образов. По решению пользователя
подписанный комплект доставляется через приватный S3. Публичный Distributor
выдаёт проверенные Compose и bootstrap по хешу, а запись готовности и подписанный
манифест появляются после автоматической сквозной проверки и продвижения версии.
Образы распространяются через существующий Docker Registry. При подготовке подписанного комплекта повторно использовать
оценки для того же digest только из проверенного ранее подписанного манифеста.
Обычный RC образов доступен с прежней конфигурацией раннера.
