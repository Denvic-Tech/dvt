# Этап 09: Пользовательский путь в мастере и основном UI

- **Статус:** см. [план](../../plan.md).
- **Утверждённое ТЗ:** [spec.md](../../spec.md), приложение A.
- **План:** [plan.md](../../plan.md).
- **Зависимости:** 03–08 — защищённый API, жизненный цикл и каталог.
- **Покрытие:** REQ-06, 12–14, 16, 22–23, 27, 29–32; AT-01, AT-04–05, AT-10–11, AT-13.

## Цель этапа

Выстроить браузерный путь от bootstrap до входа и от плана обновления до результата или предупреждения о восстановлении.

## Контекст

DVT: `services/installation_manager/frontend`, Gateway: `services/gateway/routes/installation/update.py`, `services/gateway/update_runtime`, маршруты setup. Основной React UI — отдельный checkout `../dvt-ui`, не `services/ui`. Прочитать `../dvt-ui/AGENTS.md` перед изменениями. Для схем Gateway соблюдать правило о генерации API и использовать тестовый экземпляр.

## Объём работ

1. Доработай форму мастера: рекомендуемый stable, отдельно RC и переходы, минимальная форма и advanced, одноразовая привязка к /setup и валидация email на входе. Различай доступность мастера, pending/recovery, готовность к setup и готовность DVT.
2. Свяжи профиль суперадмина, серверную проверку прав, план с реально наблюдаемой версией, простой, условия очереди, apply/continue/cancel/restore и историю с тем же ID. Browser API защищён; бизнес-решения о возможности действий берутся из журнала/исполнителя.
3. Покажи защищённый независимый URL мастера до переключения, автоматическое продолжение по тому же ID после смены мастера и обновление версии UI. Gateway/Proxy не обязательны для диагностики. RBAC, отдельное подтверждение разрушительного восстановления, отсутствие токенов и конфигурации в диагностике.

## Не входит в этап

Новые несвязанные UX разделы и ручная правка services/ui. Публикация UI не входит в этап; в приёмочном CI можно использовать изолированный mirror с точным SHA.

## Контракты и инварианты

Нельзя выдать успех до readiness и подтверждения resume, а URL мастера не является обходом прав. Совместимые клиенты получают безопасные ответы, не могут открыть второй тип жизненного цикла.

## Критерии приёмки

- [ ] `SAC-01`: Оператор после единственного bootstrap завершает установку и защищённый /setup; в браузере выдаются ошибки полей, включая email.
- [ ] `SAC-02`: Суперадмин видит план и может продолжить ровно тот же ID при обновлении мастера/Gateway; unauthorized, replay и CSRF отклоняются.
- [ ] `SAC-03`: Интерфейс предлагает только применимые версии/действия, показывает объяснимый переход, потерю данных при восстановлении и не раскрывает секреты.

## Проверки

Backend pytest конкретных Gateway/manager маршрутов; в отдельном `dvt-ui` тесты и build скрипт из package.json; инженерная генерация Gateway клиента из изолированного API; браузерные сценарии с перезапуском контейнеров. Python запускать через venv соответствующего репозитория с абсолютным корнем в `PYTHONPATH` там, где это требует AGENTS.md.

## Ожидаемые артефакты

- `report.md` по шаблону `$feature-coder`: изменения, наблюдаемые результаты, `PASS` / `FAIL` / `NOT_RUN`, команды и соответствие критериям.
- `artifacts/` при необходимости: только очищенные доказательства без секретов и больших пакетов.
- Для изменений DVT, требующих changelog, использовать `dvt-project-ops` и его helper; записать краткую запись по-русски.

## Правила выполнения

- Выполнять только этот этап по явному делегированию `$feature-coder`. Чужие незакоммиченные изменения сохранить.
- Не редактировать файлы мастера `spec.md`, `plan.md`, `task.md`, `fix_task.md`. Git-коммиты, теги и push не выполнять.
- Никаких сбойных экспериментальных действий на действующих установках. При блокере указать его и требуемое решение в отчёте и сообщении мастеру.
