# Этап 01: Постоянное состояние экземпляра и операций

- **Утверждённое ТЗ:** [spec.md](../../spec.md), приложение A.
- **План:** [plan.md](../../plan.md).
- **Зависимости:** —.
- **Покрытие:** REQ-01, 03, 20, 23, 29–30; фундамент AT-05.

## Цель этапа

Создать и проверить локальный контракт identity, durable admission и журнала, которым затем пользуются мастер, CLI и исполнитель.

## Контекст

Сейчас `services/installation_manager/infrastructure/job_store.py` хранит текущий объект только в памяти, а `infrastructure/dvt_lib.py` работает с существующим каталогом и identity. Посмотри `domain/models.py`, `domain/ports.py`, `config.py` и тесты мастера. Зафиксируй в отчёте протокол для этапов 02–09.

## Объём работ

1. Добавь модель неизменяемой identity (ID, канонический путь данных, имя Compose-проекта, адрес и порт мастера, публичный URL) и версионированное локальное хранение. Повтор с теми же значениями возвращает существующую identity, несовместимые значения сообщают о конфликте без изменений.
2. Реализуй персистентное хранилище намерений и событий (например, локальный SQLite на ФС хоста с межпроцессной сериализацией транзакций). Сохраняй запись до подтверждения приёма, атомарно резервируй одну активную операцию на экземпляр; повтор ключа с тем же запросом возвращает ранее созданный ID, смена параметров или конкурирующая активная операция даёт конфликт с ID для авторизованного вызывающего. Сохраняй закреплённые идентификаторы релиза и ссылки на артефакты, тип операции, этап, наблюдения и время; чтение по ID, активная, история и ограниченная выборка событий.
3. Дай исполнителю межпроцессный механизм исключительного владения на локальном Linux-хосте (например, удерживаемая ядром блокировка). Оставленная запись о владельце сама по себе не даёт права продолжить операцию. После освобождения блокировки новый процесс видит тот же журнал; запись чекпоинта только от актуального владельца и проверка допустимых переходов. Чётко раздели бронирование операции и владение исполнением.
4. Формат записи и права доступа: журнал хранится вне контейнера и PostgreSQL приложения. Секретам нужны отдельные защищённые файлы или ссылки; API хранилища не принимает произвольный чувствительный вывод и не логирует payload. Закрепи контракт путей, совместимости формата и типы отдельно от FastAPI. Не заменяй действующий production API на незавершённый путь.

## Не входит в этап

HTTP и CLI, сеть, изменение рабочих Compose, передача на Docker, миграции, реальное применение, восстановление. Не меняй публичные интерфейсы и не трогай текущие установки.

## Контракты и инварианты

Публичное хранилище использует один ID на операцию; связка экземпляра, нормализованного несекретного запроса, ключа идемпотентности и манифеста после приёма неизменяема. Учитывай независимые процессы, а не только потоки. Исполнение после перезапуска требует сверки, которую реализуют последующие этапы.

## Критерии приёмки

- [ ] `SAC-01`: Повтор identity не перезаписывает запись, конфликт параметров оставляет существующую запись неизменной.
- [ ] `SAC-02`: Новый процесс видит принятую операцию, checkpoint и завершённую историю; параллельные процессы не создают два активных задания или двух владельцев.
- [ ] `SAC-03`: Повтор запроса ведёт к тому же ID, другой запрос получает конфликт; неверный владелец не может изменить чекпоинт. После завершения можно начать новую операцию, не теряя историю.
- [ ] `SAC-04`: Версия формата, отсутствие секретов и права на Linux подтверждены; ранее работавшие маршруты мастера не изменились.

## Проверки

Из venv: `python -m pytest tests/unit/services/installation_manager`. Добавь проверку конкурентного приёма и удержания/освобождения владения отдельными процессами в тестовом временном каталоге. Нужна реальная семантика Linux для контроля прав и блокировки: запусти её в доступном изолированном Linux/Docker/WSL, без доступа к пользовательской установке. Непроверенную семантику не подменяй моками. Python запускать через venv соответствующего репозитория с абсолютным корнем в `PYTHONPATH` там, где это требует AGENTS.md.
