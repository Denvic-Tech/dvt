# Предложение: дата-каталог потоков DVT

Статус: проект изменений, без реализации backend и UI. Основа: локальная ветка `dev`, commit `0bd249b`; предложение подготовлено в `codex/data-catalog-inheritance-proposal`. Целевой интерфейс — существующий редактор проекта, а не отдельный каталог вместо графа.

REST API: [план методов и профиля OpenMetadata](DATA_CATALOG_REST_API.ru.md). Native API следует соглашениям OpenMetadata; branch inheritance и атомарный Save имеют явные расширения DVT. Совместимость внешних клиентов проверяется отдельно для закреплённого подмножества.

## Что уже есть

`src/modules/data_catalog/domain/value_objects.py` содержит `ColumnSchema` и `TableSchema`: название, dtype, описание, nullable, default, ограничения и произвольный metadata. `BuildSchema` собирает контракт, `DataFrameSchemaMapper` читает **таблицу описания схемы**, а не произвольный поток данных. Фасад используется нодами TableSchema и ConvertToSchema; SchemaPolicy применяет отдельные правила обработки данных.

Фактическая мета датафреймов формируется в `core/metadata/df_metadata.py` и `MetadataNodeMixin`. В `core/types/column.py` уже есть `comment`; поддержка комментариев БД не должна быть потеряна. Эта мета и `TableSchema` сейчас являются разными представлениями. В изученном модуле отсутствуют каталог терминов, идентификаторы происхождения полей, версии аннотаций и разрешение наследования.

## Предлагаемая модель

Разделить структурную схему, происхождение и описательную часть. Сохранить существующий публичный контракт `TableSchema`; новые сущности добавлять рядом, с явными мапперами.

| Сущность | Содержание |
|---|---|
| SchemaRevision | Версия структурной схемы конкретного порта, поля и типы, источник наблюдения, статус inferred/observed/declared |
| FieldIdentity | Устойчивый ID смыслового происхождения поля; имя колонки не является ID |
| FieldOccurrence | Вхождение поля в порт конкретной ноды и версии схемы; ссылка на FieldIdentity |
| FieldLineage | Связи входных и выходных вхождений: passthrough, rename, derived, unknown |
| BusinessTermRevision | Версия термина: название, синонимы, определение; общий справочник |
| AnnotationPatch | Изменённые свойства поля в выбранной точке графа: термин, описание, домен, теги |
| EffectiveAnnotation | Вычисленный результат и источник каждого свойства; не новый пользовательский документ |
| RegistryBinding | Внешний registry, subject, schemaType, schema ID, subject version; независимо от ID поля |

Домен — принадлежность/область ответственности, тег — классификационная метка, термин — бизнес-смысл. Синонимы принадлежат термину; технические aliases схемы решают другую задачу. В первой версии разрешить один домен и один основной термин на поле, несколько тегов. При расширении возможны дополнительные связи терминов.

## Наследование без копирования

Пользователь сохраняет patch на **выходном порту** ноды. Для поля на следующем шаге resolver проходит подтверждённые связи происхождения и применяет ближайшие изменения **по каждому свойству**. Редактирование у ноды-приёмника относится к конкретному входному ребру и действует только там: интерфейс явно показывает эту область. Кеш результата допустим, но не становится источником истины.

Пример реального проекта: описание `region` задано на `01.output`. Оно доступно на 03, 05, 06, 10, 11; через 03 — на 04 и 13, если преобразования подтвердили сохранение поля. Изменение термина на `03.output` действует на 04 и 13, не меняет 01 и соседние ветви 05/06/10/11. SQL-нода 08 — независимый источник, совпадение названия `region` не связывает её с 01.

Изменение общего определения термина и замена привязки поля — разные операции. В текущем представлении привязка содержит устойчивый term ID и следует актуальному определению общего термина. Редактор перед сохранением показывает область влияния. Для воспроизводимости запуск фиксирует версию термина, graph revision, schema revisions и catalog revision; история отображается по этому снимку, даже если текущий каталог изменился. Новая версия определения не создаёт новые patches на каждой ноде.

Patch имеет три состояния свойства: `UNSET` — наследовать; `SET(value)` — задать; `CLEAR` — явно убрать и перекрыть предка. Для тегов в MVP использовать замену всего набора: UNSET наследует, SET([]) задаёт пустой набор. Кнопка «Вернуть наследование» удаляет свойство patch, а не записывает копию предыдущего значения. Отдельное описание поля перекрывает определение термина только для данного контекста.

После изменения upstream пересчитывать только достижимые зависимые результаты; кеш ключуется версиями графа, схем, patches и терминов. Сохранение с expected revision предотвращает потерю параллельных правок. При переподключении ребра пересчитываются lineage и наследование, прежний patch нельзя молча привязать к другому полю с таким же именем.

### Преобразования

| Операция | Правило |
|---|---|
| Фильтр, выбор колонок | Сохранить идентичность оставшихся полей |
| Rename | Сохранить ID только при явной карте переименования |
| Новая вычисляемая колонка | Новый ID и derived-связи; термин автоматически не переносить |
| Перезапись существующего имени новым выражением | Новый ID даже при совпадении имени |
| Join | Сохранить доказанное происхождение каждого выхода; неоднозначность показать как конфликт |
| Union | Объединять аннотации только при согласованном происхождении и значениях; иначе конфликт по свойствам |
| Произвольный Python/SQL | Без явного контракта происхождения — unknown; совпадение имени и dtype недостаточно |
| Разветвление | Один предок, независимые downstream patches |

Первым добавить декларацию lineage к известным безопасным преобразованиям. Для ExecutePython и DataFrameExecCode предложить явную карту полей либо подтверждение пользователем; до этого показывать «Происхождение не подтверждено». Сигналы, подключения и VARIABLE не считать потоками датафреймов. В реальном проекте `12.output → 15.variables_df` содержит поля датафрейма, несмотря на название порта.

## Новые и неописанные поля

Отображать независимые признаки: изменение структуры (`added`, `removed`, `type_changed`, `unchanged`) и состояние описания (`unannotated`, `inherited`, `overridden`, `conflict`, `review_required`). «Новое» означает появление относительно предыдущей подтверждённой версии данного выхода, а при известной трансформации — также создание нового field ID относительно входа. Первый снимок без baseline обозначается «Первая схема», а не выдаётся за обнаруженное изменение.

Описание считается заполненным при привязке термина либо содержательном локальном описании. Комментарий БД подставляется как источник описания с отметкой «Из БД», но не выдумывает термин. Изменение типа сохраняет известную идентичность при подтверждённом преобразовании и ставит review_required, если прежний смысл мог измениться. При unknown нельзя утверждать ни наследование, ни создание нового поля; показать неопределённость.

Очередь «Требуют описания» группирует проблему по field ID и точке происхождения. Одно новое поле на десяти downstream нодах даёт одну задачу; отдельные конфликты и локальные overrides остаются видимыми. Удалённое поле сохраняется в истории, но не отображается среди текущих колонок.

## Интерфейс и тексты

Левая панель — альтернативный режим рядом с «Активные ноды». Граф, расположение карточек и порты сохраняются. Панель содержит только поиск, фильтры, раскрытие, навигацию и просмотр. **Редактируемых input/select/textarea метаданных в панели нет.** Поиск и фильтры не являются редактированием меты.

В списке несколько нод; внутри раскрытой ноды поля идут последовательно: `id`, `amount`, `region`. У каждой строки техническое имя, тип, термин/описание и текстовый статус. Выбор поля фокусирует соответствующую ноду и показывает read-only карточку: термин, описание, домен, теги и происхождение каждого свойства. Предусмотреть группировки «Ноды», «Домены», «Теги», «Термины» и фильтр «Требуют описания».

Кнопка «Редактировать метаданные» открывает отдельное модальное окно. Заголовок: «Метаданные поля region». Контекст: «03 · output · Изменение действует на эту ветку и её продолжение». Поля: «Бизнес-термин», «Описание в этом потоке», «Домен», «Теги». Рядом с наследуемым значением: «Унаследовано из 01 · output» и действие «Переопределить». Действия: «Вернуть наследование», «Отмена», «Сохранить». Сохранение меняет только patch; закрытие без сохранения не влияет на каталог.

В модальном окне показать предварительное влияние: «Будет использовано в 04 и 13; в 04 есть собственное описание — оно сохранится». Если lineage неизвестен, явно ограничить расчёт подтверждёнными путями. Создание/изменение общего термина — отдельное явно выбранное действие с собственным контекстом внутри того же окна, а не побочный эффект сохранения привязки.

### Термины на лету: уточнение интерфейса

Вместо закрытого select использовать поле поиска по названию и синонимам с результатами «название — краткое определение». В том же модальном окне доступны «Создать термин “…”», «Изменить выбранный термин» и «Без термина». Создание и редактирование раскрывают встроенный блок: «Название», «Определение», «Синонимы». Не открывать вложенное модальное окно и не отправлять пользователя в отдельный справочник.

Выбор результата меняет привязку только в черновике. Ввод поискового текста сам по себе не создаёт термин и не заменяет выбранный. Перед общим изменением показать количество вхождений и доступный список затронутых потоков. Текст: «Общий термин используется в N вхождениях полей. Сохранение обновит его название и определение во всех текущих привязках. Описание в этой ветке останется отдельным». Количество вхождений не называть количеством уникальных полей или независимых привязок.

«Применить к черновику» завершает правку встроенного блока, но ничего не сохраняет в каталоге. Главная кнопка «Сохранить» атомарно сохраняет новый термин/новую версию определения и patch выбранного поля. «Отмена» и Escape отбрасывают все изменения этого окна, включая новый термин. В HTML это демонстрация в памяти страницы; после перезагрузки изменения пропадают. В реализации необходим серверный use case `SaveFieldMetadata` и транзакция через domain contract; две независимые HTTP-записи не должны оставлять случайно созданный термин после ошибки привязки.

Название и определение обязательны. Синонимы — нормализованный список, без пустых значений и повторов. Проверять совпадение нормализованного названия в области выбранного глоссария и предлагать существующий термин; сервер выполняет ту же проверку. Ошибка сохранения или конфликт expected revision сохраняет черновик и не закрывает окно. Общая правка не меняет term ID и не переписывает техническое имя колонки. Снятие привязки не удаляет общий термин.

Отдельное поле «Описание поля в этой ветке» хранится в AnnotationPatch. Оно не редактирует общее определение; при наследовании отображать его источник. Поле «Название поля в этом потоке» — локальная подпись, не синоним справочника. Переименование общего термина обновляет его отображаемое название, но не меняет локальную подпись. Слайдер остаётся только для чтения.

HTML-макеты `dvt-catalog-view.html` и `dvt-catalog-modal.html` показывают поиск, создание, редактирование, снятие привязки и отмену черновика. Область воздействия в макете ограничена показанным проектом; реальный сервер учитывает все доступные использования термина. Это демонстрация взаимодействий, а не подключённая реализация каталога.

### Домены на лету

«Домен поля» — поиск существующего домена с действиями «Создать домен», «Изменить выбранный домен» и «Без домена». Создание и редактирование раскрывают блок внутри того же модального окна: обязательные «Название» и «Описание». Иерархия доменов пока не редактируется; слэш в демонстрационных названиях не является реализованной иерархией.

Выбор принадлежности записывает `domain_id` в patch выбранного поля и наследуется по подтверждённой ветке до следующего override. «Без домена» — явный CLEAR, перекрывающий предка; это не удаление общего домена и не возврат наследования. Поиск не меняет выбранную принадлежность сам по себе.

Правка общего домена сохраняет его устойчивый ID и меняет название/описание во всех текущих привязках. Перед правкой показать количество вхождений и список доступных затронутых потоков: «Общий домен используется в N вхождениях полей. Его название и описание обновятся во всех текущих привязках. Принадлежность полей останется прежней». В истории запусков используется закреплённая версия домена.

«Применить к черновику» не пишет в каталог. Общая кнопка «Сохранить» атомарно сохраняет изменения домена, термина и patch поля. Отмена/Escape отбрасывают все черновики. Не допускать сохранение незавершённого открытого редактора справочника; ошибки и version conflicts сохраняют ввод. Название проверять на дубли в согласованной области каталога. Права создания/правки справочников и изменения принадлежности проверять отдельно; отсутствие права общей правки не блокирует выбор доступного существующего домена.

В HTML изменение домена отражается в read-only карточке и группировке «Домены»; созданный домен доступен в последующем поиске. При сохранении принадлежности другой ветке её домен не меняется. Все записи живут в памяти страницы и сбрасываются при перезагрузке. В backend добавить `DomainRevision`, отдельный репозиторий справочника и обработку domain draft в `SaveFieldMetadata` через domain contracts.

Основные статусы: «Новое поле · требуется описание», «Нет описания», «Из БД», «Унаследовано из …», «Переопределено здесь», «Конфликт источников», «Проверьте описание после изменения типа», «Происхождение не подтверждено». Не полагаться только на цвет. Модальное окно поддерживает focus trap, Escape, возврат фокуса; ошибки и конфликты версий сохраняют введённые данные.

Предыдущий HTML-эскиз с формой в слайдере следует считать устаревшим в части редактирования. Требование этой версии: карточка только для чтения и отдельная модальная форма.

## Профиль Schema Registry

Согласованный ориентир: формат Confluent Schema Registry + Avro. Требование пользователя — похожесть представления и лёгкий будущий перенос меты, а не управление версиями внешнего registry. В первой очереди нужен переносимый документ, без подключения к registry и без его compatibility checks. Локальные версии и снимки нужны для воспроизводимости наследования DVT независимо от этого требования.

Структура экспортируется как Avro record с явно заданными name/namespace. Типы конвертируются через отдельную таблицу соответствий с логическими типами; неоднозначный OBJECT, timezone, unsigned и вложенные типы требуют явного решения. Нельзя молча преобразовывать неизвестное в string. `nullable=None` означает неизвестность, а не nullable=true. Default необходимо расширить состоянием «не задан»: текущий `default=None` не отличает отсутствие от явного null. Сохранить старую семантику для существующих потребителей через версионированный транспорт/экспорт, прежде чем менять domain default.

| DVT | Экспорт |
|---|---|
| Техническое имя и тип | Avro field name/type |
| Итоговое описание | Avro doc |
| Технические переименования | Avro aliases при подтверждённой истории |
| Синонимы термина | Расширение dvt.*, не Avro aliases |
| Термин, домен, теги, field ID | JSON-совместимые dvt.* аннотации; при поддержке Confluent — metadata properties/tags |
| Schema revision | Локальная версия; внешний subject/version хранится отдельно |
| Lineage | Данные DVT; Schema Registry references не заменяют происхождение по пайплайну |

Профиль описывает namespaces и точные ключи расширений; например `dvt.term_id`, `dvt.term_version`, `dvt.domain_id`, `dvt.field_id`. Значения registry properties сериализуются в требуемые строки; сложные структуры — в отдельный JSON payload или локальный каталог. Путь field tags задаётся адаптером. Произвольный Python metadata из существующего mapper нельзя отправлять без JSON-валидации. Термин и локальное описание хранятся раздельно, чтобы обратный импорт doc не создавал выдуманный термин.

Пример переносимого документа (иллюстрация, а не подтверждённая схема production):

```json
{
  "type": "record",
  "name": "SalesRow",
  "namespace": "tech.denvic.dvt.demo",
  "fields": [
    {
      "name": "region",
      "type": "string",
      "doc": "Регион продажи",
      "dvt.field_id": "sales-region",
      "dvt.term_id": "sales-region-term",
      "dvt.term_version": 1,
      "dvt.domain_id": "sales",
      "dvt.tags": ["geography"]
    }
  ]
}
```

Пользовательские свойства Avro несут аннотации, но стандартная сериализация данных их не переносит в каждую запись. Сохранять исходный документ схемы: инструменты, отдающие только canonical form, могут удалить расширения. На экспорт идёт разрешённая мета выбранного порта; patches и lineage остаются в DVT.

Разделить structural revision и annotation revision: parsing canonical form Avro исключает описательную часть. Дополнительно учитывать semantic properties вроде logicalType в локальном structural hash; один canonical fingerprint не отражает все различия. Изменение doc/термина не считать доказательством структурной несовместимости. Но регистрация изменённого документа может создавать внешнюю версию — это решает конкретный registry и его нормализация.

Для будущей интеграции: compatibility проверять отдельной операцией по настроенному режиму subject, а не через SchemaPolicy. Добавление nullable поля само по себе не заменяет корректный default для чтения старых данных. Registry schema ID и номер версии subject — разные значения. Эти проверки и внешние статусы не входят в текущую первую очередь.

MVP: модель меты, близкая к Avro, и валидируемый экспорт с документированными dvt.* расширениями. REST, compatibility, регистрация и импорт — возможное последующее развитие, а не условие готовности каталога. Kafka serializer/deserializer и его wire format — отдельная задача. Не добавлять обязательный контейнер Schema Registry.

Источники: [Avro specification](https://avro.apache.org/docs/1.12.0/specification/), [Confluent evolution](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html), [Confluent data contracts](https://docs.confluent.io/platform/current/schema-registry/fundamentals/data-contracts.html), [Confluent REST API](https://docs.confluent.io/platform/current/schema-registry/develop/api.html). Расширения Confluent и доступность дополнительных функций необходимо сверить с версией установленного сервиса.

## План файлов и границы

1. `domain`: dataclasses происхождения, аннотаций и версий; resolver policy; contracts репозиториев и registry; именованные exceptions. Никаких Pydantic, ORM, Dask и HTTP.
2. `flow/use_cases`: классы `ResolveAnnotations`, `SaveAnnotationPatch`, `CompareSchemaRevisions`, `ListDescriptionGaps`, `ExportRegistrySchema`; у каждого `execute`. Получают данные через domain contracts.
3. `infra`: ORM и миграции, репозитории, JSON/API schemas, мапперы и Avro/Confluent adapter; не импортирует flow.
4. Composition/facade связывает слои вне domain/flow/infra. Существующий фасад сборки TableSchema остаётся совместимым.
5. Интеграция metadata mixin добавляет ссылки на schema/annotation snapshots к мета-событию, сохраняя нынешние поля ответа. Runtime наблюдение схемы не создаёт пользовательские patches. DB comments импортируются с provenance.
6. Gateway: read-only resolved catalog, lineage и gaps; мутация patch с expected revision; справочник терминов отдельными операциями. Маршруты/DTO вне domain. После изменения OpenAPI выполнить предусмотренное проектом обновление клиента через Gateway.
7. UI реализуется в отдельном `dvt-ui`, не в `services/ui` этого репозитория: режим панели, read-only карточка, модальное окно. Предложение не изменяет production проект.

## Приёмка будущей реализации

- Одна привязка на 01 видна на подтверждённых downstream шагах без дополнительных записей patch.
- Override на 03 не затрагивает соседние ветви; следующий override перекрывает только изменённые свойства.
- CLEAR блокирует наследование; удаление override возвращает его. Изменение upstream обновляет зависимые значения с сохранением overrides.
- Rename сохраняет происхождение; вычисление под прежним именем создаёт новый ID. Для Python без контракта показана неопределённость.
- Merge с противоречивыми терминами показывает конфликт, а не выбирает первый вход. Переподключение не переносит старую привязку по имени.
- Новая колонка создаёт одну задачу описания в точке возникновения; повторное наблюдение той же схемы не создаёт новую задачу.
- Старый запуск отображает прежний снимок меты; конкурентное сохранение не затирает чужую правку.
- В панели нет редактора; Save/Cancel находятся в модальном окне. До Save мета не меняется.
- Avro export валидируется реальным парсером; проверяются missing default/null, decimal, технические aliases, ограничения имён и сохранность бизнес-аннотаций. Подключение к registry и Kafka serialization не нужны для приёмки первой очереди.
- Старые тесты TableSchema, ConvertToSchema, SchemaPolicy и dump/load продолжают проходить; новые тесты защищают resolver, branches/merge, revisions и adapter.

Для этой ветки достаточны чтение источников и проверка согласованности предложения: исполняемое поведение не менялось. Реализацию начинать после согласования модели и профиля registry.
