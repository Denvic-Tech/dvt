# Этап 2. Происхождение и наследование в сложном графе

Зависит от завершённого [этапа 1](STAGE_01_MVP_UI.ru.md). Цель — расширить достоверное наследование и объяснить конфликтующие/неопределённые случаи, сохраняя простой Save.

## Работы

1. Ввести контракт lineage для преобразования: passthrough, rename, derived, unknown; отдельно декларировать достоверность и связь input occurrence → output occurrence. Не выводить идентичность только из имени/dtype.
2. Поддержать доступные rename/select/вычисления и join/union после проверки реальных определений нод. Переименование сохраняет ID только с явной картой; новое выражение под прежним именем создаёт новый ID и requires-description. Слияние не выбирает первый вход произвольно.
3. Для произвольного Python/SQL добавить доступный контракт/редактор карты происхождения. Автоматические догадки — inferred, не подтверждённый lineage. Пользователь может подтвердить карту, её версия связана с конфигурацией ноды; правка кода сбрасывает подтверждение затронутых полей.
4. Resolver возвращает конфликты по свойствам и источникам. Если разные предки согласны — наследовать; если расходятся — conflict. Override одного свойства не скрывает конфликт другого. Решение конфликта сохраняется один раз в точке слияния.
5. Обработать переподключение, удаление, восстановление ноды и повторное появление имени. Patch старого field ID не перепривязывается к новому автоматически. История остаётся, неактивный patch явно обозначается; перенос — отдельная подтверждаемая операция.
6. Инвалидация кеша по изменениям graph/schema/catalog и зависимостям. Один resolver и для UI, и для runtime snapshots. Фильтры и сохранённые данные stage 1 не теряют идентичность после обновления.
7. Расширить gaps: type-review, conflict, unknown lineage. Дедуплицировать происхождение, но не объединять локальные overrides и различные конфликтные точки.

## UI

Карточка каждого свойства показывает origin и цепочку; навигация фокусирует соответствующую ноду. Отдельный просмотр lineage — read-only. Модальное окно показывает кандидатов источников, выбор наследования/локальное решение и предварительную область влияния с сохранёнными downstream overrides.

Для карты Python использовать отдельный режим того же editor UI или штатный редактор ноды; список каталога остаётся без inline редактирования. Unknown не маскировать зелёным inherited статусом. В UI различать техническое переименование и смену бизнес-термина.

## API

GET dataframes/{id}/lineage, schemaChanges; расширить DTO provenance/conflicts и preview. Добавить версионированную декларацию lineage к существующему контракту конфигурации графа либо узкий специальный ресурс после проверки владельца графа. Не вводить второй независимый API записи рёбер. Read-only column lineage export отложен до этапа 4.

## Не входит

Полный статический анализ произвольного Python/SQL, «AI угадывает значение поля», внешние каталоги, массовая правка справочников, универсальная система трансформационных plugins. Ограничения конкретных нод явно документировать.

## Приёмка

- Rename сохраняет описание; вычисление под тем же именем требует нового описания. Связь с несколькими входными полями отражена как derived, термин не копируется автоматически.
- Join/union согласованных и конфликтующих источников дают соответствующий статус. Решение действует на продолжение ветки и не меняет предков.
- Переподключение не переносит старый patch по имени; текущий resolver и snapshot выполняемого графа не смешивают версии.
- Unknown карта и подтверждённая карта различимы; смена кода инвалидирует устаревшее подтверждение.
- Meaningful tests: branch/merge/rename/overwrite/reconnect и cache restore; UI сценарий разрешения конфликта; совместимость миграции данных stage 1. Результат этапа — несколько сложных графов на dev со сверенным lineage.
