# Этап 3. Управление метаданными и работа в масштабе

Зависит от [этапа 2](STAGE_02_LINEAGE.ru.md). Цель — сделать каталог удобным для совместной работы, больших проектов и анализа истории; не откладывать сюда базовую безопасность, уже требуемую MVP.

## Работы

1. Полноценные списки/редакторы glossaries, terms, domains, classifications и tags; soft delete/restore, usage и версии. Иерархию добавлять только при подтверждённой необходимости и поддержке FQN/родительских ссылок. Не менять технические имена при обычной правке displayName.
2. UI истории схемы, аннотаций и справочников. Просмотр snapshot выбранного запуска, сравнение версий и указание кто/когда изменил. Restore старого значения создаёт новую актуальную ревизию, не переписывает прошлое; scope восстановления показывается до Save.
3. Уточнить матрицу governance: право менять локальное поле, создавать сущность справочника, править общую сущность, читать usage и управлять taxonomy. Использовать существующий механизм прав DVT, не создавать параллельную auth-систему.
4. Массовое дополнение группы полей — одна reviewable операция с preview, ограниченным размером и проверкой ревизий. Атомарный небольшой batch либо явно определённый результат по элементам; не выдавать partial успех за общую транзакцию. UI предлагает уже имеющийся термин, не создаёт дубли для каждого поля.
5. Полноценные группировки «Домены», «Теги», «Термины», расширенные фильтры gaps, поиск синонимов/описаний, lazy pagination списка нод и полей. Загружать тяжёлую историю/provenance по запросу; не заставлять browser строить весь граф для поиска.
6. Показать счётчики origin проблем и usage, не раскрывая чужие проекты. Активные concurrent правки получают конфликт с сохранением черновика и выбором обновить/повторить. Политики удаления не уничтожают используемые аннотации.
7. Замерить resolver/cache/search на согласованных размерах графа и каталогов. Зафиксировать тестовый fixture и целевую задержку после первого замера, затем оптимизировать выявленные узкие места. Не изобретать числовую гарантию без окружения. MVP поиск по БД сохранить, если его достаточно.

## API

Завершить нужные PATCH/DELETE/versions/name lookup из draft; добавить управляемый restore и batch changes в контракт. GET usage/версии/история потоков, cursor pagination с snapshot consistency, выбор fields. PUT upsert для ingestion реализовать только если появился реальный потребитель; не включать его ради симметрии CRUD.

Расширения batch/restore отсутствуют в исходном draft: сначала описать и проверить DTO, затем генерировать клиент. Сохранить атомарный modal Save и корректную авторизацию при новых возможностях.

## Не входит

Автоматическая организация доменов, бизнес-workflow согласования/уведомлений, обязательный Elasticsearch, внешний OpenMetadata сервер и его полная модель roles/policies. Эти функции требуют отдельного пользовательского сценария.

## Приёмка

- История запуска показывает прежние версии терминов/доменов после общей правки; сравнение объясняет structural и descriptive изменения отдельно.
- Soft delete используемой сущности блокируется понятным usage; неиспользуемая удаляется и восстанавливается без потери ID.
- Пользователь без права общей правки может выбрать доступный термин, но не изменить его определение; скрытые usage не раскрываются.
- Batch не оставляет случайных частичных изменений, conflict сохраняет черновик; фильтры/курсор устойчивы к смене снимка.
- Значимые tests authorization/history/restore/batch concurrency; измерения большого графа и UI lazy loading. Процессы DVT не получают новый обязательный контейнер.
