# Этап 4. Переносимость и интеграции

Зависит от устойчивого snapshot/lineage этапов 1–2; выпуск после [этапа 3](STAGE_03_GOVERNANCE.ru.md), если нужен полноценный governance. Цель — перенос разрешённой меты в Avro/OpenMetadata и определение безопасных точек расширения.

## Avro и Confluent

Реализовать Avro export snapshot выбранного порта: record name/namespace, типы/logical types, doc, технические aliases, JSON-совместимые dvt.* annotations. Unknown/ambiguous dtype не превращать молча в string. Различать не заданный default и явный null; nullable unknown требует решения. Отдельно сохранить термины/домены/теги и field ID.

Ориентир пользователя — похожесть формата и лёгкий будущий перенос в Confluent Schema Registry. REST-регистрация, compatibility checks внешних версий и Kafka wire serialization **не являются обязательной частью этапа**. Не добавлять Schema Registry контейнер. При потребности в отдельном коннекторе оформить дополнительное задание.

## OpenMetadata

1. Закрепить целевую версию schemas/SDK, таблицу DTO соответствий и поддерживаемое подмножество. В текущем плане 1.12.0-release — baseline для проверки, не гарантированная версия клиента.
2. Реализовать экспорт read-only проекций: поток → виртуальная Table, поля → columns, термин → Glossary TagLabel, classification tags, domains на уровне asset, pipeline/column lineage. Для per-field domain и provenance — проверенный extension/sidecar с отчётом о потерях.
3. Создать отдельный draft и реализовать `/api/openmetadata/v1` только для согласованного read-only подмножества. Проекция не добавляет собственные поля в строгие стандартные DTO. Проверить необходимые service/database/databaseSchema контейнеры и FQN escaping для конкретного клиента.
4. В UI дать выбор порта/snapshot/формата и показать unmapped properties/losses. По умолчанию lossless экспорт; lossy требует явного выбора. Unknown lineage не выдаётся за доказанную связь.
5. Проверить реальным SDK list/get/by-name и поддержанное чтение lineage. Только прошедшие операции обозначаются совместимыми. Полный write API, roles/policies/ingestion/service lifecycle OpenMetadata не обещать.

## Подход расширений

Следовать решению [головного плана](IMPLEMENTATION_PLAN.ru.md): field identities, snapshots и resolver остаются в ядре. Выделить domain gateway для export и минимальный публичный facade snapshots для адаптеров. Без нужного API внешнее расширение не импортирует внутренние src/core.

Результат основной задачи — встроенные стандартные адаптеры и документированные границы. Публичную регистрацию сторонних adapters/host actions реализовать только после согласования API, а не автоматически строить framework. Отдельный `.dvtx` коннектор может стать следующим независимым заданием. Builder skill и технология пакета доступны, но сами по себе не предоставляют вкладку каталога или глобальное наблюдение всех нод.

При согласованной пилотной упаковке предусмотреть отдельный extension repo, профиль сборки, manifest/backend/frontend/dependencies и установленный пакет. Проверить отключение/удаление адаптера без потери каталога, обновление/ошибку/откат на непустых данных. Native/licensing/release-private — только при отдельно заданной коммерческой поставке. Private builder code не переносится в DVT.

## API и приёмка

Native GET exports/avro и exports/openmetadata; отдельная спецификация совместимой read-only проекции. Источник — разрешённый snapshot, внешняя материализация не создаёт patches на каждой ноде DVT.

- Avro-парсер принимает fixtures string/int/decimal/date/null/default/aliases; неоднозначные случаи возвращают понятную ошибку. Экспорт сохраняет бизнес-аннотации в исходном документе.
- OpenMetadata schemas принимают fixtures; выбранный SDK читает поддержанное подмножество; пер-field domain потери отражены явно.
- Унаследованное описание наружу экспортируется, но количество внутренних patches не увеличивается. Экспорт старого запуска воспроизводим.
- UI показывает формат, snapshot, ошибки и ограничения. Базовый каталог работает без внешнего сервера/коннектора.
- Если пакет расширения включён в отдельный согласованный scope: проверен именно установленный `.dvtx` и его lifecycle. Иначе отчёт честно указывает, что выполнена встроенная интеграция, а не поставка расширения.
