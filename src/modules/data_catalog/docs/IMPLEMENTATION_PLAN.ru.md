# План разработки дата-каталога DVT

Статус: задания на будущую реализацию. Четыре последовательных этапа; каждый заканчивается работающим пользовательским результатом, а не только backend. Этот план определяет приоритеты. Общая модель и большой draft OpenAPI описывают целевую систему, но не требуют реализовать все 59 операций на первом этапе.

## Этапы

| Этап | Результат | Задание |
|---|---|---|
| 1. MVP с UI | Пользователь видит поля реального потока, описывает их в модальном окне, выбирает/создаёт/правит термин и домен. Описание наследуется через поддержанные связи, новые поля заметны | [STAGE_01_MVP_UI.ru.md](STAGE_01_MVP_UI.ru.md) |
| 2. Полное происхождение | Rename, новые вычисления, join/union, конфликты, переподключение; интерфейс объясняет источники и последствия изменения | [STAGE_02_LINEAGE.ru.md](STAGE_02_LINEAGE.ru.md) |
| 3. Управление и масштаб | История и сравнение, права общей правки, расширенные справочники и поиск, массовое заполнение, устойчивость на больших графах | [STAGE_03_GOVERNANCE.ru.md](STAGE_03_GOVERNANCE.ru.md) |
| 4. Переносимость и интеграции | Проверяемый Avro export, OpenMetadata export/совместимое read-only подмножество, публичные контракты для адаптеров расширений | [STAGE_04_INTEROPERABILITY.ru.md](STAGE_04_INTEROPERABILITY.ru.md) |

Сроки не оценены: сначала проверить текущее хранилище графа, интеграцию мета-событий и UI. Предлагаемый порядок внутри каждого этапа: согласовать небольшой контракт → сквозной сценарий backend/UI → meaningful tests → проверка на непустом проекте → демонстрация и описание ограничений. UI реализуется в отдельном checkout `dvt-ui`; `services/ui` не редактируется.

## Что нельзя отложить за MVP

- Просмотр слева и отдельное модальное редактирование.
- Сохранение в БД, общий Save и отмена всего черновика; термины/домены на лету.
- Устойчивый field ID, связь с конкретным портом, отличие нового поля от одноимённого старого.
- Один patch в точке изменения вместо копий на каждом шаге; ветви независимы.
- Базовые UNSET/SET/CLEAR и provenance. Unknown видим и не превращается в автоматическое наследование по имени.
- Проверка project access, общих прав справочников, параллельных правок и атомарность.
- Версионный снимок для выполненного запуска. Полный пользовательский UI истории можно отложить, но воспроизводимость нельзя достроить задним числом без сохранённых данных.

Не добавлять обязательные сервисы/контейнеры, поисковый кластер, Schema Registry или OpenMetadata. Не менять существующую обработку данных SchemaPolicy ради каталога. Профиль Avro учитывать в модели с первого этапа: JSON-совместимые значения, различие отсутствующего default и явного null, описание отдельно от термина. Реальный экспорт и адаптеры приходят на этапе 4.

## Можно ли применить технологию расширений DVT

Вывод: **подходы — да; весь каталог как готовое расширение без изменений платформы — сейчас не доказан**. Рекомендуемая архитектура: минимальное ядро в `src/modules/data_catalog`, UI-вкладка в DVT UI; дополнительные адаптеры могут поставляться расширениями после появления нужных публичных контрактов.

Исследованы локальные `dvt-extensions-builder/README.md`, skill `skills/dvt-extension-development/SKILL.md` и references development/build/verification, DVT `dvt_extension_api/README.md`, `v1/metadata.py`, `v1/gateway.py`, extension manifest/runtime, `dvt-ui/src/app/extensions/types.ts`. Это чтение исходников, не тест установки расширения.

| Возможность | Найдено сейчас | Применение к каталогу |
|---|---|---|
| backend gateway_entrypoint | APIRouter, проверки маршрутов; собственный lifespan запрещён | Подходит REST адаптерам расширения; не подменяет встроенный Gateway native API |
| frontend bundle, публичный host | React/MUI и возможности редакторов нод | Переиспользовать компоненты/host. В изученном host нет явного registerSidebarPanel для вкладки каталога |
| Публичная мета | Получение схемы и типы через facade V1 | Не обнаружен API регистрации глобального observer/resolver каталога для всех встроенных нод |
| migrations_dir в manifest | Манифест предусматривает миграции | Нужна проверка фактической установки/отката; наличие поля само по себе не гарантирует безопасный lifecycle |
| Сборка `.dvtx`, профили и зависимости | Dev/private режимы, frontend staging, wheelhouse, native target | Подходит поставке отдельного адаптера; не является сборкой основного DVT или гарантией готовности продукта |

Встроенный каталог нужен всему графу, включая ноды без расширений. Его стабильные идентификаторы и snapshots должны сохраняться независимо от включения/отключения адаптера. Перенос основы в отключаемый пакет до появления публичного контракта увеличивает объём MVP и риск потери функции.

### Что переиспользовать уже в этапах 1–3

Перенести дисциплину разработки из skill: сначала граница продукта и версия runtime, затем узкий сквозной сценарий, отдельные backend/UI contracts, ленивое извлечение схем без compute всего dataframe, проверка миграций на непустых данных и обратного перехода, раздельное подтверждение source/container/installed artifact. Эти принципы применимы к встроенному модулю без упаковки в `.dvtx`.

Не копировать приватный builder, licensing/Cython code или профили другого продукта в DVT. Наличие коммерческого режима по умолчанию в skill не задаёт бизнес-модель каталога: лицензирование здесь не запрошено. Native защита и коммерческая поставка не входят в четыре этапа ядра.

### Что потребуется для отдельного расширения

На этапе 4 определить публичный `CatalogSnapshot` API, регистрацию export adapters и права обращения к каталогу; при необходимости UI slot для каталога/дополнительных действий. Нужные операции явно предлагаются как изменение Extension API и согласуются до реализации; нельзя обходить их прямыми импортами `src/core` из расширения. Отсутствие API не блокирует стандартный встроенный экспорт этапа 4.

Расширение не владеет snapshots/field IDs и не внедряется monkey-patch в MetadataNodeMixin. При выключении адаптера каталог работает, исходная мета остаётся. Gateway маршруты расширений используют существующий mount; совпадение native путей не обещать. Адаптер OpenMetadata может сначала быть встроенным mapper, а `.dvtx` — отдельной последующей задачей после готовности контракта.

Если будет принято решение о `.dvtx`, следовать builder skill целиком: конкретная совместимая версия DVT, Linux x86_64/CPython 3.13 для текущего native target, frontend артефакты, offline wheelhouse, dev сборка → проверка установленного пакета → обновление/ошибка/откат. Не запускать сборку сейчас: текущая задача — планирование. Альтернативный вариант «весь каталог — расширение» потребует отдельного platform-enablement этапа до MVP и потому не рекомендован для сокращения объёма.

## Управление объёмом

Definition of Done каждого этапа находится в его задании. Не включать в первый PR все миграции и DTO будущих этапов. Заложить только границы для последующего расширения; не строить заранее универсальный plugin framework. Каждый этап допускает несколько небольших PR backend/UI, но считается завершённым только после сквозной приёмки.

Все новые текстовые документы используют `<filename>.ru.md`. HTML и OpenAPI YAML остаются в своих форматах: переименование их в Markdown сломает назначение артефактов.
