# Этап 1. MVP дата-каталога с UI

Основа: [головной план](IMPLEMENTATION_PLAN.ru.md). Цель — рабочая функция в реальном редакторе с сохранением данных и UI.

## Пользовательский сценарий

Открыть проект → включить «Каталог данных» рядом с «Активные ноды» → раскрыть несколько нод → выбрать поле → увидеть тип, описание, термин, домен, теги и источник → открыть модальное окно → найти/создать/править термин или домен → сохранить → увидеть значение на подтверждённом продолжении ветки. Перезагрузка страницы сохраняет результат. Cancel/Escape ничего не сохраняют.

## Объём backend

1. Сохранить ColumnSchema/TableSchema и текущие потребители. Добавить минимальные field identities, port occurrences, schema revisions, annotations/patches, общий glossary/domain и ревизии справочников. DDD-lite: dataclasses/contracts в domain, use-case классы в flow, ORM/HTTP/DTO в infra.
2. Подключить сбор уже доступной схемы выходов/входов, без запуска проекта ради открытия каталога и без compute всего датафрейма. Если схемы нет — «Схема ещё не получена», не пустая подтверждённая схема. Использовать текущие мета-события; загрузка из БД учитывает comment и показывает его происхождение.
3. Декларировать passthrough для DataFrameFilter и чтения входа конечной ноды. Преобразования Python/SQL без явной карты — unknown. Начать с проверенных нод реального проекта 01 → 03 → 04 и входов 10/11. Нода 08 — самостоятельный источник. Участвуют только DATAFRAME-порты.
4. Resolver применяет patches по свойствам и подтверждённым рёбрам. SET меняет свойство, CLEAR блокирует предка, UNSET удаляет override. На ветвлении наследовать один источник без записи копий. При локальной правке не материализовать остальные унаследованные свойства.
5. Сравнивать наблюдения схемы: новое field ID/колонка, removed и type_changed. Первый снимок — «Первая схема». Не выдавать unknown за новое доказанное происхождение. Смена имени пока не распознаётся автоматически; сохраняет unknown до этапа 2.
6. Справочники минимальные: один начальный glossary, плоские домены, одна базовая classification для тегов. Термины: displayName, definition/description, synonyms; домены: displayName/description. Одно поле — один основной термин и домен, несколько существующих/созданных меток. Раздельные стабильные technical name и displayName.
7. Атомарный Save для term/domain drafts и patch, expected revisions, idempotency key, проверка ссылок и прав; usage preview показывает доступные затронутые поля. Повтор Save не создаёт вторую сущность. На error/conflict окно остаётся открытым.
8. Сохранить минимальный snapshot запуска: graph/schema/catalog revisions и версии использованных справочников. Пользовательский просмотр старых запусков/полная история ещё не реализуются. После cache restore не терять ссылки на snapshot.

## Объём UI

Панель только для просмотра: поиск/раскрытие нод, последовательные строки полей, read-only карточка и фильтр «Требуют описания». Группировки по справочникам можно добавить позднее. Источник каждого значения и unknown показываются текстом. Минимальная очередь дедуплицируется по origin field ID; rename и сложные конфликты пока не поддерживаются.

Модальное окно: поиск/select результата, создание и общая правка терминов/доменов встроенными блоками без второго modal, локальная подпись и «Описание поля в этой ветке», теги. «Применить к черновику» не пишет на сервер. Главная кнопка Save пишет всё атомарно; «Без домена/термина» выполняет CLEAR; «Вернуть наследование» — UNSET. Общая правка отображает влияние, локальное описание не правит общий термин. Нельзя отправлять весь resolved DTO как локальный patch.

Добавить loading/empty/error/conflict states, доступную клавиатурную навигацию и возврат фокуса. HTML — источник сценариев, а не код для прямой вставки. UI разрабатывается в dvt-ui.

## API первой очереди

Реализовать только нужное экрану подмножество draft:

- GET glossaries; GET/POST glossaryTerms и domains; GET их карточек и usage. Общие PATCH вне Save не нужны первому экрану.
- GET tags и classifications, POST tags в базовую classification; отдельные общие редакторы тегов отложить.
- GET dataframes, карточки/columns/одного поля; GET annotationOverrides для редактирования; GET projects/{projectId}/gaps.
- POST schemaObservations для runtime при необходимости выбранного транспорта; пользователь не имеет runtime-права.
- POST metadataChanges/preview и metadataChanges. Для общих правок используются вложенные drafts.

Сначала уточнить конкретные request/response schemas MVP и обновить draft. Форматы, auth и revision semantics не менять произвольно между этапами. Native API остаётся в стиле OpenMetadata; совместимая внешняя проекция не нужна MVP.

## Не входит

Автоматический rename/derived lineage, join/union, массовые действия, иерархия доменов/терминов, полный CRUD всех справочников, полноценная история UI, импорт/экспорт, external registry, SDK OpenMetadata, упаковка `.dvtx`. Все остальные ноды честно показывают unknown, не предполагают наследование по совпадению имени.

## Порядок и приёмка

Сначала один сквозной сценарий field → patch → DB → UI; затем термин/домен drafts, потом цепочка фильтров/ветвление и gaps. Миграции аддитивны, не разрушают существующие графы. Проверить непустую БД и чтение старых мета-ответов; не добавлять сервисы.

- Сохранение region на 01 видно на 03/04/входах 10/11 без дополнительных patches; изменить на 03 — 04 обновляется, соседняя ветка и 01 не меняются.
- Отмена создания домена/термина не оставляет записи; сохранение одновременно создаёт справочник и привязку. Общая правка обновляет текущее отображение всех привязок, старый snapshot остаётся прежним.
- Добавление наблюдаемого поля показывает одну задачу описания; первый snapshot не выдаёт ложный structural diff. Python unknown обозначен.
- UNSET/CLEAR различаются после перезагрузки; параллельное сохранение не затирает чужую правку; старые API потребители продолжают читать мету.
- Проверены domain resolver unit tests, transaction rollback/retry/conflict и одна UI e2e цепочка с save/cancel. Existing TableSchema/ConvertToSchema/SchemaPolicy tests проходят. Критерий завершения — работающий MVP на dev-инсталляции с зафиксированными ограничениями.
