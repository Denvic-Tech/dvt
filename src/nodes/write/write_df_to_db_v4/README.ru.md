# Запись DataFrame в БД V4

## Назначение и выбор

`WriteDataFrameToDBV4` записывает DataFrame в существующую таблицу БД. Подходит для добавления, полной замены или замены по ключу. Целевые БД, схема и таблица не создаются: подготовьте и проверьте их заранее.

## Входы и настройка

Подайте DataFrame в `df`, а `GetExistDBConnection.connection` — в `connection`. Задайте `table_name`, при необходимости `database_name` и `schema_name`. `write_mode` по умолчанию `append`; `truncate` заменяет все строки; для `upsert` нужен `upsert_config={"key_column":"id"}` с именем целевого ключа. Передавайте `upsert_config` только для upsert. `column_mapping` содержит пары `source_name` / `target_name` и необязательные `dtype` / `nullable`. `on_extra_df_columns` по умолчанию `ignore`, `on_missing_df_columns` — `ignore_if_default`. `rows_per_batch` (строк в одном INSERT; для COPY в PostgreSQL — строк в одном CSV-буфере, для массовой вставки в SQL Server и MySQL — строк в одном вызове `executemany`) по умолчанию пуст: тогда каждая партиция пишется пакетами, размер которых считается по оценке ширины её строки, поэтому широкие строки идут меньшим числом строк в пакете (см. описание БД ниже); обычный INSERT использует 1000 строк. Заданное значение определяет число строк в пакете точно на любом пути, кроме SQL Server, который снижает его так, чтобы один вызов занимал в буферах не больше 64 МБ; память на один пакет растёт вместе с ним, а малые значения добавляют обмены с сервером. Экземпляр, который администратор вернул к legacy-политике, везде использует 1000 строк в пакете, если `rows_per_batch` не задан. `chunksize` устарел и не используется: сохранённые пайплайны могут по-прежнему содержать его (форма ноды сохраняла 1000), но он ни на что не влияет. `async_insert` (только ClickHouse, по умолчанию `false`; другие БД его игнорируют) отправляет вставки режима append через серверный буфер асинхронных вставок. `sync_column_descriptions` по умолчанию `true`: после каждой успешной записи нода переносит описания входных колонок из Data Catalog в комментарии целевых колонок.

Через MCP проверьте точную цель и известную схему входа до настройки writer. При первой настройке или изменении схем вызовите `resolve_write_columns`: `typed_create` для отсутствующей таблицы, иначе `existing_table`. Отсутствующие объекты создайте через `create_database`, `create_schema`, `create_table`; create_table не изменяет существующую таблицу. Для колонок используйте `apply_table_column_actions`: перед каждым пакетом preview с `dry_run=true` (по умолчанию), проверка SQL/диагностики, затем тот же пакет с `dry_run=false`. Перечитайте `get_database_table`, повторите согласование после изменений и задайте явный `column_mapping`. Для неизменившегося настроенного пайплайна повторное согласование перед каждым запуском не требуется. Разовая MCP-подготовка не требует DDL-ноды или signal-ребра; DDL во время выполнения либо неподдерживаемая MCP-операция могут использовать обоснованную специализированную/SQL-ноду с нужной зависимостью.

Предложенные действия — рекомендации, не разрешение применять их. Удаление/пересоздание требуют явно согласованной потери данных; `recreate_column` удаляет и создаёт колонку без сохранения значений. Preview не сканирует существующие NULL; применение проверяет их перед `nullable=false`. Для такого изменения на ClickHouse исключите конкурентную запись. После ошибки/тайм-аута проверьте состояние перед планированием оставшихся действий. Preview сам по себе не требует дополнительного подтверждения пользователя. Для удаления комментария задайте явный `comment: null`; для `set_column_nullable` передайте boolean и не передавайте column/comment. При preview поле `applied_actions` описывает план, а не выполненный DDL.

## Результат

Это нода записи: выходного порта DataFrame нет. Системные переменные `target_table` и `rows_written` описывают завершённую запись. `rows_written` — число записанных входных строк, а не итоговый размер таблицы.

## Поведение и ограничения

Служебные колонки DVT удаляются. Сопоставление колонок не меняет схему таблицы. Для отсутствующих колонок действуют default/nullability целевой БД и выбранная политика. Upsert использует одну ключевую колонку: загружает вход во временную таблицу, удаляет совпавшие целевые строки и вставляет подготовленные строки. Это не частичное обновление отдельных полей; входные дубли не устраняются. Truncate/upsert требуют прав на временные таблицы и поддержки диалекта. Для блоков и этапов могут использоваться разные транзакции; атомарность всего запуска не гарантируется. Повтор append может создать дубли; неудачная запись может иметь частичные последствия.

Партиции записываются параллельными рабочими потоками. Положительное число потоков в настройках проекта задаёт их количество; иначе экземпляр использует значение по умолчанию для типа БД, которое администратор может переопределить или вернуть к одному фиксированному числу для всех БД. Всегда действует верхний предел экземпляра. Эти же потоки вычисляют и вышестоящие партиции `df`, включая чтение из БД-источника. Больше потоков — не всегда быстрее: драйверы вроде psycopg и pyodbc замедляются из-за конкуренции потоков, а ClickHouse может ускориться.

Вставки в ClickHouse по умолчанию синхронные: INSERT завершается, когда его строки записаны в part таблицы, поэтому все строки видны после завершения ноды, а ранние чанки видны уже во время записи. При `async_insert=true` вставки режима append идут через серверный буфер асинхронных вставок с `wait_for_async_insert=1`: каждый INSERT ждёт сброса своего буфера, поэтому строки видны в тот же момент, но большие записи заметно медленнее. Включайте его только для множества мелких частых записей. Truncate и upsert его никогда не используют. Каждый синхронный INSERT создаёт хотя бы один part на партицию таблицы. Множество мелких INSERT заставляет сервер постоянно сливать parts и может завершиться ошибкой "Too many parts", когда партиция превысит настройку таблицы `parts_to_throw_insert`. ClickHouse рекомендует около одного INSERT в секунду на таблицу крупными пачками: без `rows_per_batch` один INSERT несёт около 16 МБ данных партиции, не больше 1000000 строк. Нода работает с ClickHouse через HTTP-интерфейс: подключение с драйвером native на стандартном native-порту (9000, с TLS — 9440) перенаправляется на стандартный HTTP-порт (8123 или 8443) с предупреждением в логе, а native-подключение на любом другом порту завершается ошибкой с просьбой выбрать драйвер http и HTTP-порт сервера.

Данные в ClickHouse отправляются в формате Arrow, если каждая вставляемая колонка имеет тип Int8–Int64, UInt8–UInt64, Float32/Float64, Bool, String, Date, Date32, DateTime, DateTime64 или Decimal, в том числе внутри Nullable или LowCardinality. Колонка любого другого типа (Array, Map, Tuple, UUID, Enum, IPv4/IPv6, FixedString, Int128/Int256, ...) переводит всю запись на Native-вставку по колонкам. Оба пути преобразуют значения одинаково: datetime без часового пояса считаются UTC, с часовым поясом переводятся в UTC; разряды ниже точности колонки отбрасываются (округление вниз); Date из колонки datetime с часовым поясом берёт дату по UTC; Decimal усекается до scale колонки; float в целочисленных колонках усекается; прочие значения в колонках String преобразуются через `str()`. Пропуски в non-Nullable числовой колонке прерывают запись. На пути Arrow пропуск в другой non-Nullable колонке становится значением колонки по умолчанию, а значение вне диапазона типа (DateTime раньше 1970 или позже 2106-02-07, Date позже 2149-06-06, точность Decimal, разрядность целого) прерывает запись, а не переполняется или обрезается сервером.

Подключения к PostgreSQL с драйвером psycopg 3 записывают каждую партицию одним `COPY ... FROM STDIN` в формате CSV, в одной транзакции на партицию, если цель — таблица без правил INSERT и каждая вставляемая колонка имеет тип smallint, integer, bigint, real, double precision, numeric, boolean, text, varchar, char, date, timestamp, timestamptz или uuid. Колонка любого другого типа (json/jsonb, массивы, bytea, interval, time, enum, домены, ...) переводит всю запись на пакетный INSERT, так же как представления, внешние таблицы и подключения psycopg2. Партиция, значения которой COPY не может сохранить в точности как INSERT (например, float в текстовой колонке или смешанные объекты Python), отдельно идёт через INSERT, а если сервер отклоняет сам COPY, остаток записи идёт через INSERT; в каждом случае в лог пишется предупреждение. Значения сохраняются так же, как их сохраняет INSERT: NaN/NaT/None/NA становятся NULL, пустые строки остаются пустыми; float в целочисленных колонках округляется до ближайшего чётного; float в numeric-колонках сохраняет 15 значащих цифр, затем применяется scale колонки; datetime без часового пояса в колонках timestamptz считается местным временем часового пояса сессии, а datetime с часовым поясом в колонках timestamp/date переводится в него; разряды меньше микросекунды отбрасываются (округление вниз). Ошибка данных (нарушение ограничения, значение вне диапазона, символ NUL в тексте) прерывает запись с указанием строки партиции и колонки; транзакция этой партиции откатывается и не оставляет ни одной её строки, а партиции, зафиксированные раньше, остаются. Без `rows_per_batch` один CSV-буфер, отправляемый серверу, содержит около 4 МБ данных партиции (не больше всей партиции); `rows_per_batch` задаёт число строк в нём. Партиция по-прежнему пишется одним COPY в одной транзакции. Запись через COPY идёт в 4 потока — значение по умолчанию для массовой записи в PostgreSQL; положительное число потоков в настройках проекта или переопределение администратора для записи в PostgreSQL задаёт число потоков вместо него и тогда имеет приоритет, а верхний предел экземпляра действует всегда. Запись через INSERT сохраняет значение PostgreSQL по умолчанию — 1 поток, потому что больше потоков её замедляют. Администратор может отключить COPY для экземпляра настройкой `DB_PG_COPY=false`.

Подключения к SQL Server с драйвером pyodbc и Microsoft ODBC Driver for SQL Server записывают каждую партицию одним параметризованным INSERT через pyodbc `fast_executemany`, в одной транзакции на партицию, если цель — таблица, каждая вставляемая колонка имеет тип bit, tinyint, smallint, int, bigint, real, float, decimal, numeric, char, varchar, nchar, nvarchar, date, datetime, datetime2, smalldatetime, datetimeoffset, time или uniqueidentifier и ни одна из них не является колонкой IDENTITY. Колонка любого другого типа (binary/varbinary, text/ntext/image, xml, money, sql_variant, пространственные типы, hierarchyid, псевдонимы типов, ...), вставляемая колонка IDENTITY, представления, другие ODBC-драйверы и неудачное чтение каталога переводят всю запись на пакетный INSERT. Партиция, значения которой нельзя отправить в точности так, как их отправляет INSERT (например, float в текстовой колонке, бесконечные float, целые вне диапазона bigint, целые кроме 0 и 1 в колонке bit), отдельно идёт через INSERT; в каждом случае в лог пишется предупреждение. Значения сохраняются так же, как их сохраняет INSERT: каждый параметр объявляется тем типом, с которым его передаёт INSERT (bigint, float, bit, numeric, datetime2(7), uniqueidentifier, varchar или nvarchar), и сервер приводит его к типу колонки как прежде. NaN/NaT/None/NA становятся NULL, пустые строки остаются пустыми; float в колонках decimal округляется от своего двоичного значения; разряды меньше микросекунды отбрасываются (округление вниз); datetime с часовым поясом сохраняется по местному времени своего пояса, кроме колонок datetimeoffset, которые сохраняют смещение. Ошибка данных (нарушение ограничения, переполнение, усечение) прерывает запись с указанием строк партиции в сбойном вызове, а не отдельной строки: `fast_executemany` её не сообщает. Транзакция этой партиции откатывается и не оставляет ни одной её строки, а партиции, зафиксированные раньше, остаются. Без `rows_per_batch` один вызов `executemany` берёт около 8 МБ строк, но не больше 10000, посчитанных по объявленным размерам параметров или, если так больше, по оценке значений (строки, передаваемые как max, например nvarchar(max), учитываются по своей длине); `rows_per_batch` задаёт число строк в вызове, а для очень широких строк оно снижается, чтобы один вызов занимал в буферах не больше 64 МБ; партиция по-прежнему пишется в одной транзакции. Запись сохраняет значение SQL Server по умолчанию — 8 потоков. Администратор может отключить этот путь для экземпляра настройкой `DB_MSSQL_FAST_EXECUTEMANY=false`.

Подключения к MySQL и MariaDB с драйвером PyMySQL вставляют каждую партицию через PyMySQL `executemany` в одной транзакции на партицию, если цель — базовая таблица, каждая вставляемая колонка имеет тип tinyint, smallint, mediumint, int, bigint, float, double, decimal, bit, year, char, varchar, один из типов text, date, datetime, timestamp, time, binary, varbinary или один из типов blob и ни одна из них не является генерируемой колонкой. Колонка любого другого типа (json, enum, set, пространственные типы, uuid/inet в MariaDB, ...), представления и неудачное чтение каталога переводят всю запись на пакетный INSERT, а партиция со значением, отличным от bytes, в бинарной колонке отдельно идёт через INSERT; в каждом случае в лог пишется предупреждение. Каждое значение отправляется тем же SQL-литералом, что и при INSERT, поэтому сохраняется так же. PyMySQL собирает строки одного вызова в многострочные INSERT размером не больше 4 МБ и никогда не больше серверного `max_allowed_packet`. Ошибка данных прерывает запись с сообщением сервера; номер строки в нём считается внутри сбойного INSERT, а не партиции. С транзакционным движком (InnoDB) транзакция этой партиции откатывается и не оставляет ни одной её строки, а партиции, зафиксированные раньше, остаются. Без `rows_per_batch` один вызов `executemany` берёт около 16 МБ данных строк по оценке, но не больше 10000 строк, то есть несколько полных INSERT, потому что каждый INSERT — это обмен с сервером, а вызов заканчивается неполным INSERT; `rows_per_batch` задаёт число строк в вызове; партиция по-прежнему пишется в одной транзакции. Запись сохраняет значение MySQL по умолчанию — 4 потока. Администратор может отключить этот путь для экземпляра настройкой `DB_MYSQL_BULK_INSERT=false`.

Синхронизация комментариев выполняется после записи данных при каждом прогоне и в любом режиме. Описания берутся из lineage входа `df` в Data Catalog (описания полей таблиц-источников, описания колонок нод и унаследованные тексты) и переводятся в целевые имена через `column_mapping`. Обновляются только расхождения; каталог побеждает там, где у него есть текст, а пустое описание в каталоге никогда не стирает существующий комментарий. Диалекты без комментариев колонок пропускаются; ошибка обновления комментария пишется предупреждением в лог и не валит ноду.

## Примеры

Предположим, `public.order_totals(id, total)` уже существует с совместимыми типами. Подключите объект БД и DataFrame с `id, amount`.

```json
{"table_name":"order_totals","schema_name":"public","write_mode":"append","column_mapping":[{"source_name":"id","target_name":"id"},{"source_name":"amount","target_name":"total"}],"on_extra_df_columns":"error"}
```

Это только значения параметров. Две входные строки добавят две строки. Для замены строк с совпадающим `id` задайте `write_mode="upsert"` и `upsert_config={"key_column":"id"}`, предварительно проверив смысл ключа и уникальность входа.

## Типовые ошибки

Нет целевой таблицы: создайте отдельно и перечитайте её схему. Повторные целевые имена в mapping, несовместимые типы или запрещённые null: исправьте сопоставление/данные по фактической таблице. Нет ключа/config для upsert: задайте целевой ключ. После ошибки проверьте таблицу перед повтором. Truncate используйте только для запланированной полной замены.
