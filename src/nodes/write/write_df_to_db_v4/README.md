# Write DataFrame to DB V4

## Purpose and selection

`WriteDataFrameToDBV4` writes a DataFrame into an existing database table. Use it for controlled append, full replacement or key-based replacement. It never creates the target database, schema or table; prepare and inspect the target first.

## Inputs and configuration

Connect a DataFrame to `df` and `GetExistDBConnection.connection` to `connection`. Set `table_name`, optional `database_name` and `schema_name`. `write_mode` defaults to `append`; `truncate` replaces all rows; `upsert` requires `upsert_config={"key_column":"id"}` using the target key name. Supply `upsert_config` only for upsert. `column_mapping` contains `source_name` / `target_name` pairs, with optional `dtype` / `nullable`. `on_extra_df_columns` defaults to `ignore`; `on_missing_df_columns` defaults to `ignore_if_default`. `chunksize` (rows per INSERT; for PostgreSQL COPY rows per CSV buffer, for the SQL Server and MySQL bulk insert rows per `executemany` call, see below) is empty by default and then follows the database type: 100000 for ClickHouse, 1000 for other databases; an instance an operator switched back to the legacy policy uses 1000 everywhere. An explicit value wins over the database default, except that the SQL Server and MySQL bulk inserts raise a smaller value to 10000 (see below); memory per chunk grows with it. `async_insert` (ClickHouse only, default `false`; other databases ignore it) sends append inserts through the server async insert buffer. `sync_column_descriptions` defaults to `true`: after each successful write the node copies Data Catalog descriptions of the input columns into the target column comments.

Through MCP, inspect the exact target and known input schema before configuring the writer. Call `resolve_write_columns` on initial setup or schema changes: `typed_create` for a missing table, `existing_table` otherwise. Prepare missing objects with `create_database`, `create_schema`, `create_table`; create_table never alters an existing table. For column changes use `apply_table_column_actions`: preview each batch with `dry_run=true` (default), review SQL/diagnostics, then apply the same batch with `dry_run=false`. Reread `get_database_table`, resolve again after changes and set explicit `column_mapping`. Unchanged configured pipelines need no repeated resolution for every run. One-time MCP preparation needs no DDL node or signal edge; runtime DDL or unsupported MCP operations may use a justified specialized/SQL node with the appropriate dependency.

Suggested actions are recommendations, not authorization. Drop/recreate require explicitly agreed data loss; `recreate_column` drops and adds a column and does not preserve its values. Preview does not scan existing NULLs; apply checks them before `nullable=false`. Pause concurrent ClickHouse writes for that change. After failure/timeout inspect actual state before planning remaining actions. Preview alone requires no additional user confirmation. For comment removal supply explicit `comment: null`; for `set_column_nullable` provide a boolean and omit column/comment fields. During preview, `applied_actions` describes planned actions, not executed DDL.

## Outputs

This is a sink: there is no DataFrame result port. System variables `target_table` and `rows_written` describe the completed write. `rows_written` counts inserted input rows, not the final table size.

## Behavior and limitations

Internal DVT columns are removed. Mapping does not alter the target schema. Missing columns remain subject to target defaults/nullability and the chosen policy. Upsert uses one key column, stages input, removes matching target rows and inserts staged rows; it is not a partial update of selected fields. It does not deduplicate input. Truncate/upsert need temporary-table permissions and dialect support. Writes may use separate transactions for chunks and stages; do not assume whole-run atomicity. Repeating append can duplicate data; a failed write can have partial effects.

Partitions are written by parallel worker threads. A positive project worker count sets their number; otherwise the instance uses a default per database type, which an operator can override or switch back to one fixed count for all databases. An instance-wide upper limit always applies. The same threads also compute the upstream partitions of `df`, including source database reads. More threads are not always faster: drivers such as psycopg and pyodbc can slow down under thread contention, while ClickHouse can gain.

ClickHouse inserts are synchronous by default: an INSERT returns once its rows are in a table part, so all rows are visible when the node finishes, and earlier chunks are visible while it runs. With `async_insert=true`, append inserts go through the server async insert buffer with `wait_for_async_insert=1`: each INSERT waits for its buffer flush, so rows are visible at the same point, but large writes are much slower. Use it only for many small, frequent writes. Truncate and upsert never use it. Each synchronous INSERT creates at least one part per table partition. Many small INSERTs keep the server merging and can fail with "Too many parts" once a partition exceeds the table setting `parts_to_throw_insert`. ClickHouse recommends about one INSERT per second per table, in large batches, hence the 100000-row default. The node uses the ClickHouse HTTP interface: a connection with the native driver on the default native port (9000, or 9440 with TLS) is redirected to the default HTTP port (8123 or 8443) with a warning in the log, and a native connection on any other port fails with an error asking for the http driver and the server HTTP port.

ClickHouse data goes in Arrow format when every inserted column is Int8–Int64, UInt8–UInt64, Float32/Float64, Bool, String, Date, Date32, DateTime, DateTime64 or Decimal, also inside Nullable or LowCardinality. Any other column type (Array, Map, Tuple, UUID, Enum, IPv4/IPv6, FixedString, Int128/Int256, ...) sends the whole write through the Native column insert. Both paths convert values alike: naive datetimes are UTC and aware ones are converted to UTC; digits below the column precision are floored; a Date from an aware datetime column takes the UTC date; Decimal is truncated to the column scale; floats in integer columns are truncated; other values in String columns are converted with `str()`. Missing values in a non-Nullable numeric column fail the write. On the Arrow path a missing value in another non-Nullable column becomes the column default, and a value outside the column type (DateTime before 1970 or after 2106-02-07, Date after 2149-06-06, Decimal precision, integer width) fails the write instead of being wrapped or clamped by the server.

PostgreSQL connections with the psycopg 3 driver write each partition with one `COPY ... FROM STDIN` in CSV format, in one transaction per partition, when the target is a table without INSERT rules and every inserted column is smallint, integer, bigint, real, double precision, numeric, boolean, text, varchar, char, date, timestamp, timestamptz or uuid. Any other column type (json/jsonb, arrays, bytea, interval, time, enums, domains, ...) sends the whole write through batched INSERT, as do views, foreign tables and psycopg2 connections. A partition whose values COPY cannot store exactly as INSERT would (for example floats in a text column or mixed Python objects) goes through INSERT on its own, and a server that rejects COPY itself switches the rest of the write to INSERT; each case logs a warning. Values are stored as INSERT stores them: NaN/NaT/None/NA become NULL and empty strings stay empty; floats in integer columns are rounded half to even; floats in numeric columns keep 15 significant digits before the column scale is applied; naive datetimes in timestamptz columns are local time of the session time zone and aware datetimes in timestamp/date columns are converted to it; digits below microseconds are floored. A data error (constraint violation, out-of-range value, NUL character in text) fails the write naming the partition row and column; that partition's transaction is rolled back and leaves none of its rows, while partitions committed before it stay. Here `chunksize` is the number of rows per CSV buffer sent to the server; a partition is still one COPY and one transaction. COPY writes run 4 threads, the PostgreSQL bulk default; a positive project worker count or the operator's PostgreSQL write-worker override sets the number instead and then wins, and the instance upper limit always applies. Writes through INSERT keep the PostgreSQL default of 1 thread, because more threads slow them down. An operator can turn COPY off for the instance with `DB_PG_COPY=false`.

SQL Server connections with the pyodbc driver and Microsoft ODBC Driver for SQL Server write each partition with one parameterized INSERT sent through pyodbc `fast_executemany`, in one transaction per partition, when the target is a table and every inserted column is bit, tinyint, smallint, int, bigint, real, float, decimal, numeric, char, varchar, nchar, nvarchar, date, datetime, datetime2, smalldatetime, datetimeoffset, time or uniqueidentifier and none of them is an IDENTITY column. Any other column type (binary/varbinary, text/ntext/image, xml, money, sql_variant, spatial types, hierarchyid, alias types, ...), an inserted IDENTITY column, views, other ODBC drivers and a failed catalog lookup send the whole write through batched INSERT. A partition whose values cannot be sent exactly as INSERT sends them (for example floats in a text column, infinite floats, integers outside bigint, integers other than 0 and 1 in a bit column) goes through INSERT on its own; each case logs a warning. Values are stored as INSERT stores them: every parameter is declared with the type INSERT binds (bigint, float, bit, numeric, datetime2(7), uniqueidentifier, varchar or nvarchar), and the server converts it to the column type as before. NaN/NaT/None/NA become NULL and empty strings stay empty; floats in decimal columns are rounded from their binary value; digits below microseconds are floored; aware datetimes are stored by their wall time, except in datetimeoffset columns, which keep the offset. A data error (constraint violation, overflow, truncation) fails the write naming the partition rows of the failing call, not the single row: `fast_executemany` does not report it. That partition's transaction is rolled back and leaves none of its rows, while partitions committed before it stay. Here `chunksize` is the number of rows per `executemany` call, raised to at least 10000, because smaller calls only add round trips (this includes the 1000 of existing pipelines), and lowered for very wide rows so one call buffers at most 64 MB; a partition is still one transaction. The write keeps the SQL Server default of 8 threads. An operator can turn this path off for the instance with `DB_MSSQL_FAST_EXECUTEMANY=false`.

MySQL and MariaDB connections with the PyMySQL driver insert each partition through PyMySQL `executemany` in one transaction per partition, when the target is a base table and every inserted column is tinyint, smallint, mediumint, int, bigint, float, double, decimal, bit, year, char, varchar, the text types, date, datetime, timestamp, time, binary, varbinary or the blob types and none of them is a generated column. Any other column type (json, enum, set, spatial types, MariaDB uuid/inet, ...), views and a failed catalog lookup send the whole write through batched INSERT, and a partition with a value other than bytes in a binary column goes through INSERT on its own; each case logs a warning. Every value is sent as the same SQL literal that INSERT sends, so it is stored identically. PyMySQL packs the rows of one call into multi-row INSERT statements of at most 4 MB and never above the server `max_allowed_packet`. A data error fails the write with the server message; a row number in it counts rows of the failing statement, not of the partition. With a transactional engine (InnoDB) that partition's transaction is rolled back and leaves none of its rows, while partitions committed before it stay. Here `chunksize` is the number of rows per `executemany` call, raised to at least 10000 like on SQL Server, because every statement is a round trip to the server; a partition is still one transaction. The write keeps the MySQL default of 4 threads. An operator can turn this path off for the instance with `DB_MYSQL_BULK_INSERT=false`.

Column comment sync runs after the data write on every run and in every mode. Descriptions come from the Data Catalog lineage of the `df` input (field descriptions of source tables, node column descriptions and inherited texts) and are mapped to target names through `column_mapping`. Only differing comments are updated; the catalog wins where it has text, and an empty catalog description never clears an existing comment. Dialects without column comments are skipped; a failed comment update is logged as a warning and does not fail the node.

## Examples

Assume `public.order_totals(id, total)` already exists with compatible types. Connect the DB object and a DataFrame with `id, amount`.

```json
{"table_name":"order_totals","schema_name":"public","write_mode":"append","column_mapping":[{"source_name":"id","target_name":"id"},{"source_name":"amount","target_name":"total"}],"on_extra_df_columns":"error"}
```

Parameter values only. Two input rows append two rows. To replace rows with matching `id`, use `write_mode="upsert"` and `upsert_config={"key_column":"id"}` after verifying the intended key and input uniqueness.

## Common errors

Missing target: create it separately and inspect it again. Duplicate mapping targets, incompatible types or forbidden nulls: fix the mapping/data against the actual table. Missing upsert key/config: supply the target key. After a failed write, inspect the target before retrying. Use truncate only for an intended full replacement.
