# WriteDataFrameToDBV3

Node type: `WriteDataFrameToDBV3`.

## Назначение и выбор

Записывает DataFrame в существующую SQL-таблицу по совпадающим именам колонок. Для явного сопоставления имён источника и назначения выберите WriteDataFrameToDBV4.

## Входы и настройка

Подключите объект SQL-подключения к `connection`, DataFrame — к `df`. Задайте `table_name` и при необходимости `schema_name`/`database_name`. По умолчанию `write_mode=append`; `truncate` очищает таблицу перед вставкой; `upsert` требует `upsert_config` с одним ключом. `chunksize` (строк в одном INSERT) по умолчанию пуст, и тогда размер зависит от типа БД: 100000 для ClickHouse, 1000 для остальных БД; экземпляр, который администратор вернул к legacy-политике, везде использует 1000. Явное значение всегда имеет приоритет; память на один чанк растёт вместе с ним. Лишние колонки DataFrame по умолчанию обрабатываются как `on_extra_df_columns=ignore`. Для отсутствующих колонок назначения по умолчанию `on_missing_df_columns=ignore_if_default`; `ignore` пропускает их без такой проверки default, `error` отклоняет.

## Результат

Выхода DataFrame нет. Системные переменные `target_table` и `rows_written` сообщают целевую таблицу и счётчик записи.

## Поведение и ограничения

База, схема и таблица должны уже существовать; нода не выводит и не создаёт их структуру. Внутренние колонки DVT удаляются. Null в существующей колонке остаётся значением; отсутствие колонки отличается и может позволить использовать default БД. Ограничения таблицы продолжают действовать. Данные вычисляются и записываются пакетами/партициями; этапы могут фиксироваться отдельно, поэтому ошибка не гарантирует откат всего запуска. Повтор append может дублировать данные; truncate удаляет прежние строки; поддержка upsert и SQL-поведение зависят от диалекта назначения.

Партиции записываются параллельными рабочими потоками. Положительное число потоков в настройках проекта задаёт их количество; иначе экземпляр использует значение по умолчанию для типа БД, которое администратор может переопределить или вернуть к одному фиксированному числу для всех БД. Всегда действует верхний предел экземпляра. Эти же потоки вычисляют и вышестоящие партиции `df`, включая чтение из БД-источника. Больше потоков — не всегда быстрее: драйверы вроде psycopg и pyodbc замедляются из-за конкуренции потоков, а ClickHouse может ускориться.

Вставки в ClickHouse синхронные: INSERT завершается, когда его строки записаны в part таблицы, поэтому все строки видны после завершения ноды, а ранние чанки видны уже во время записи. Каждый INSERT создаёт хотя бы один part на партицию таблицы. Множество мелких INSERT заставляет сервер постоянно сливать parts и может завершиться ошибкой "Too many parts", когда партиция превысит настройку таблицы `parts_to_throw_insert`. ClickHouse рекомендует около одного INSERT в секунду на таблицу крупными пачками, отсюда значение по умолчанию 100000 строк. Для множества мелких частых записей в V4 есть необязательный `async_insert`.

## Примеры

Пусть существует таблица orders(id INTEGER, amount INTEGER), а вход содержит строки (1,10), (2,20). Соедините выход объекта подключения с `connection`, DataFrame — с `df`:

```json
{
  "table_name": "orders",
  "write_mode": "append",
  "on_extra_df_columns": "error",
  "on_missing_df_columns": "error",
  "chunksize": 1000
}
```

При соблюдении ограничений добавятся две строки; rows_written сообщит 2. Прежние строки останутся.

## Типовые ошибки

Таблица отсутствует: сначала создайте и проверьте её. Разные имена источника/назначения: переименуйте колонки выше по графу или используйте mapping V4. Для отсутствующей обязательной колонки нужны данные либо допустимый default БД/политика. Ошибки типов, nullable и уникальности требуют согласовать вход с существующей таблицей. Перед повтором проверьте частично выполненную запись.
