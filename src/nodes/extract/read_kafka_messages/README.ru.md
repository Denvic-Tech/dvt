# Read Kafka Messages

Тип ноды: `ReadKafkaMessages`.

## Назначение и выбор

Читает конечный снимок одного Kafka-топика в ленивый DataFrame. Подходит для порций по расписанию
с явным подтверждением offsets. Нода не выполняет commit, не подписывается на группу,
не создаёт топики и не ждёт будущих сообщений. Получает готовое подключение Kafka Connection.
Kafka-ноды пока исключены из MCP-каталога до отдельного этапа открытия каталога.

## Входы и настройка

| Вход | По умолчанию | Значение |
| --- | --- | --- |
| `connection` | обязателен | KafkaConnectionRecord по ребру подключения |
| `topic` | обязателен | Точное имя существующего топика |
| `group_id` | обязателен | Непустая группа для сохранённых позиций |
| `partitions` | null | Все текущие partitions; явный список непустой, уникальный, только существующие номера |
| `start_mode` | committed | committed, earliest, latest, timestamp или explicit |
| `missing_offset_policy` | earliest | earliest, latest или error; только при отсутствии committed-позиции |
| `start_timestamp` | null | Для timestamp обязателен datetime с часовым поясом |
| `start_offsets` | null | Для explicit: JSON со строковыми ID всех выбранных partitions и их позициями |
| `max_messages` | 100000 | Строгий общий лимит сообщений; положительное целое или null для отключения |
| `max_bytes` | 67108864 | Строгий общий лимит исходных байтов; положительное целое или null |
| `key_format` / `value_format` | binary / text | binary или text |
| `key_encoding` / `value_encoding` | utf-8 | Строгое декодирование text; для binary игнорируется |
| `isolation_level` | read_committed | Стабильная транзакционная граница; read_uncommitted выбирается явно |
| `rows_per_partition` | 10000 | Максимум строк части Dask, независимо от количества Kafka partitions |
| `target_partition_bytes` | 8388608 | Мягкая цель исходного размера части; допускает превышение на одно разрешённое сообщение |
| `max_message_bytes` | 16777216 | Жёсткий предел одного сообщения, не лимит RAM процесса |

Унаследованные `input_variables` и `signal_in` работают штатно. Настройки поддерживают
стандартные ссылки на переменные. Оба общих лимита могут быть null: чтение ограничит снимок.
Если план требует больше runtime-предела в 10000 потенциальных задач чтения, он завершится
ошибкой до чтения payload. Уменьшите общие лимиты или увеличьте целевой размер части.

## Результат

`output` — ленивый DataFrame с Arrow-колонками:

- `topic`: string, `partition`: int32, `offset`: int64.
- `timestamp`: nullable UTC timestamp с точностью execution settings;
  `timestamp_type`: nullable строка CreateTime / LogAppendTime.
- `key`, `value`: nullable string или binary согласно настройкам.
- `headers`: список структур `{key: string, value: binary}` без null на уровне списка;
  отсутствие headers представлено пустым списком.

Headers сохраняют порядок, повторяющиеся имена и null-значения. Tombstone остаётся null,
отличным от пустых строки/байтов. Пустой результат имеет ту же типизированную схему.
JSON, Avro и Protobuf внутри payload не разбираются.

В `output_variables` доступны `kafka_topic`, `kafka_group_id`, `kafka_read_id` (новый UUID
плана), `kafka_partitions` (JSON). Обычные итоговые переменные изначально unresolved:
`kafka_offsets` (JSON), `kafka_messages_read` (целое), `kafka_bytes_read` (целое),
`kafka_stop_reason` (snapshot_exhausted / max_messages / max_bytes). Обращение к переменной
не вычисляет DataFrame. Полное успешное вычисление обновляет прежние ссылки на переменные
и их метаданные до успешного сигнала назначения.

JSON offsets содержит schema_version=1, topic, group_id, read_id, доступные ID подключения/
кластера, isolation_level, статистику и список partitions. В список входят только partitions,
вернувшие сообщения. next_offset — offset последнего принятого сообщения плюс один, а не
позиция consumer после prefetch. Пустая порция публикует partitions=[] только после вычисления.

## Поведение и ограничения

План фиксирует partitions и верхние позиции без чтения payload. Новые сообщения и partitions
относятся к следующему запуску. Сохранённая позиция вне доступного диапазона даёт ошибку
без автоматического reset. Latest, включая fallback для отсутствующей позиции, даёт пустой
снимок и не инициализирует группу. Повторные latest-запуски могут постоянно оставаться пустыми.
Для «начать сейчас, затем читать» один раз явно задайте позиции группы и используйте committed.

Части читаются последовательно с детерминированным циклическим обходом partitions по возрастанию.
Часть может включать несколько Kafka partitions; преобразования и запись могут идти параллельно
с последующим чтением. Порядок внутри partition сохраняется; общего порядка timestamp нет.
Байты считаются по исходным key/value, UTF-8 именам headers и значениям headers, без Kafka
overhead и памяти pandas. Если сообщение не помещается в остаток бюджета, порция заканчивается
перед ним. Превышение всего max_bytes или max_message_bytes — ошибка.

Head, выбор частей и сокращённый граф не публикуют offsets всей порции, пока весь исходный
план не прочитан и все исходные части не переданы потребителю. Повторное вычисление перечитывает
принятые диапазоны и сверяет отпечаток без двойного учёта. Изменение прочитанных данных,
ошибка декодирования и отмена инвалидируют чтение: нужен новый запуск.
Retention/compaction могут удалить историю; численные пропуски offsets сами по себе не
доказывают потерю данных.

Поддержаны только локальные synchronous/threaded scheduler. Reader хранит компактные receipts,
а не весь payload. Часть ограничена строками/мягкой целью байтов плюс одно допустимое сообщение.
Fetch-буферы и декодирование требуют дополнительной памяти; downstream compute может собрать
весь DataFrame. Режим метаданных не подключается к Kafka и не читает payload.

Каждый запуск строит свежий план. Ни store_enabled этой ноды, ни старый downstream snapshot
не заменяют путь живого чтения. Downstream-снимки остаются пригодными для просмотра.
Autocommit выключен на всех путях, включая закрытие consumer.

Группа должна использоваться эксклюзивно: конкурентные читатели и внешние commit — ответственность
пользователя. При явном commit после успешных сигналов назначения семантика at-least-once.
Сбой между записью и commit может повторить уже записанные сообщения. Exactly-once и общая
транзакция Kafka с назначением не обеспечиваются. Фильтрация строк не уменьшает исходную
порцию, позиции которой будут подтверждены.

## Примеры

Для существующего топика orders и подключения:

```json
{"topic":"orders","group_id":"dvt-orders","start_mode":"committed","missing_offset_policy":"earliest","max_messages":1000,"value_format":"text"}
```

Соедините `GetExistKafkaConnection.connection` → `ReadKafkaMessages.connection`,
затем `ReadKafkaMessages.output` → преобразования → DataFrame-вход назначения.
Для SQL сначала выберите/преобразуйте поддерживаемые колонки: поддержка binary/nested зависит
от назначения. Передайте `ReadKafkaMessages.output_variables` во вход `input_variables`
потребителя явного commit и соедините успешный `signal_out` назначения с его сигнальным входом.
Один сигнал Read-ноды не доказывает завершённую запись назначения.
Для подтверждения используйте [Commit Kafka Offsets](../../tool/commit_kafka_offsets/README.ru.md);
подключите signal_out каждого обязательного назначения к её signal_in.

Точное чтение с позиции 100 partition 0:

```json
{"topic":"orders","group_id":"dvt-orders","partitions":[0],"start_mode":"explicit","start_offsets":{"0":100},"max_messages":50}
```

При наличии всех 50 сообщений offsets 100..149 и достаточном byte budget next_offset будет 150.
При пропусках message_count может отличаться от next_offset-start_offset.

## Типовые ошибки

- Неизвестный topic/partition, отсутствующая позиция с политикой error или недоступный offset:
  проверьте топик и выберите допустимое начало; отсутствующая и устаревшая позиции различаются.
- Unresolved offsets: вычислите исходную порцию полностью и поставьте зависимость от успешного
  сигнала записи; обращение к переменной само не запускает чтение.
- Ошибка декодирования: укажите фактическую кодировку или binary; замены неверных байтов нет.
- Слишком большое сообщение: увеличьте соответствующий лимит либо исправьте payload producer.
- Изменившийся снимок или STOP: не подтверждайте частичный результат, создайте новый запуск.
- Неподдерживаемый scheduler или слишком большой план: используйте локальное выполнение
  и уменьшите порцию.
- Ошибки авторизации/TLS: проверьте сохранённое подключение и CA; секретов в выходном JSON нет.
