# Чтение таблицы БД V3

## Назначение и выбор

`ReadTableFromDBV3` читает таблицу БД в DataFrame с партициями. Используйте для обычного извлечения таблиц, затем применяйте специализированные фильтры, проекции, соединения и агрегаты. `ReadQueryFromDBV3` нужен, когда необходим SQL на стороне источника.

## Входы и настройка

Соедините `GetExistDBConnection.connection` → `connection`; порт принимает объект, а не ID. Задайте `table_name` и при необходимости `database_name` / `schema_name`. Сначала изучите каталог таблицы и передайте явный непустой `columns`; для чтения всех колонок перечислите их все. `partition_col` — точное исходное имя колонки без SQL-кавычек; выбирайте стабильную скалярную колонку без null. `partition_grouping`, `npartitions` и `max_rows_per_partition` настраивают партиционирование чтения. `max_concurrent_queries` ограничивает число одновременно выполняемых запросов партиций этой ноды; если параметр не задан, используется значение экземпляра по умолчанию для типа БД. `limit` ограничивает запрошенное чтение. `TTL_CACHE` по умолчанию 0. Параметр `time_zone` объявлен, но текущий путь чтения этой ноды его не применяет.

Определения входов содержат краткие локализованные подсказки UI и отдельные нелокализуемые рекомендации `agent_description`. Прочитайте рекомендации перед настройкой; описанный ниже порядок профилирования применяется и при пропуске настроек партиционирования.

## Результат

`output` — Dask DataFrame. Выходные метаданные сохраняют доступные комментарии таблицы и колонок источника. Системные переменные: `source_table_name`, `source_schema_name`, `source_db_name`; передавайте их стандартными портами переменных.

## Поведение и ограничения

Группировка партиций управляет физическим чтением, а не бизнес-агрегацией. Партиционирование не гарантирует порядок строк. В режиме метаданных строится пустой DataFrame по схеме источника; это не подтверждает успешность полного чтения. Невычисленные переменные целевой таблицы могут оставить метаданные пустыми. Комментарии источника служат описанием данных. В сохранённом графе нельзя использовать null в `columns` вместо всех колонок: null при обновлении входа через MCP удаляет сохранённое значение.

`npartitions` задаёт целевое число партиций; если его нет, планировщик оценивает число по количеству строк, ширине выбранных колонок и настройкам экземпляра. Ширина берётся из статистики БД, если она есть (несжатые размеры колонок ClickHouse, статистика `ANALYZE` PostgreSQL, статистика колонок Oracle), иначе по выборке строк. Без явной группировки упорядочиваемые ключи без null используют диапазоны, nullable или неупорядочиваемые — hash-сегменты. Границы диапазонов читаются одним сортирующим запросом на ClickHouse, PostgreSQL, SQL Server, MySQL 8 и Oracle; на SQLite, сервере без оконных функций или при ошибке этого запроса — одним запросом на каждую границу. Явное `{"mode":"range"}` отклоняет null-ключи; `{"mode":"hash","buckets":8}` задаёт hash-сегменты. `max_rows_per_partition` — предел строк одного сегмента. В пользовательских режимах `partition_grouping` (кроме `range` и `hash`) группа, точное число строк которой превышает предел, разбивается на `ceil(строки / floor(0.8 × max_rows_per_partition))` подсегментов по hash полного значения ключа, а не префикса или периода. Если слишком большую группу нельзя разбить — это группа null, группа из одного значения ключа (например, `as_is`, одно значение `explicit_values` или булево значение) или разбиение потребовало бы больше сегментов, чем допускает лимит партиций экземпляра, — планирование завершается ошибкой до чтения данных с указанием группы, числа её строк и причины. Hash не распределяет одинаковые значения ключа, поэтому одно значение, повторяющееся чаще предела внутри группы префикса, периода или диапазона, по-прежнему вызывает ошибку при чтении, и ошибка называет сегмент. Автоматические и явные range/hash-сегменты не разбиваются. Перед их построением планировщик находит самое частое значение ключа: точным подсчётом в ClickHouse, по оценке `pg_stats` для целой таблицы PostgreSQL. Если это значение или группа null сами по себе больше `max_rows_per_partition`, планирование завершается ошибкой до чтения данных с указанием ключа, значения, числа строк и предела. Другие источники эту проверку пропускают, и такой ключ по-прежнему вызывает ошибку при чтении. Ключ также может стать индексом DataFrame; выбранная колонка ключа остаётся в данных. Сегменты читаются отдельно; нельзя предполагать единый согласованный снимок изменяющегося источника между чтениями.

Одновременно выполняется не больше `max_concurrent_queries` запросов сегментов одной ноды. Если параметр не задан, экземпляр применяет значение по умолчанию для типа БД, которое администратор может переопределить или отключить. Остальные сегменты ждут свободного места независимо от числа потоков ноды-потребителя. Больше одновременных запросов — не всегда быстрее: драйверы вроде psycopg и pyodbc замедляются из-за конкуренции потоков, а источники, ограниченные сервером, например ClickHouse, могут ускориться. Ограничение не меняет сегменты, строки и их порядок.

Для ClickHouse запросы сегментов одной ноды используют небольшой пул подключений драйвера вместо нового подключения на каждый сегмент. Если каждая читаемая колонка — целое число до 64 бит, Float32/Float64, Bool, String, Date/Date32, DateTime/DateTime64 или Decimal, в том числе внутри Nullable или LowCardinality, сегменты читаются в формате Arrow, который быстрее преобразует строки и Decimal; значения и типы результата те же, что на обычном пути. Любой другой тип колонки, например UUID, FixedString, Enum, IPv4, Int128, Array, Map, Tuple или JSON, отправляет все сегменты обычным путём. Сегмент, который формат Arrow не может преобразовать так же, например с невалидным текстом UTF-8 или датой вне поддерживаемого диапазона, перечитывается обычным путём, поэтому результат или ошибка не меняются. DateTime64 с точностью, отличной от 0, 3, 6 и 9, читается только через Arrow: если другая колонка отправляет чтение обычным путём, такая колонка вызывает ошибку.
Ключ также может стать индексом DataFrame; выбранная колонка ключа остаётся в данных.

## Выбор партиций перед построением графа

Для каждого нового или перенастраиваемого чтения изучите каталог таблицы и оцените данные через `suggest_read_partitioning` и `query_database_readonly` (либо используйте свежий профиль того же источника и объёма чтения). `suggest_read_partitioning` (MCP; Gateway `POST /db-connections/{connection_id}/partitioning-advice`) принимает таблицу, планируемый `columns` как `read_columns` и планируемые `npartitions` / `max_rows_per_partition`, если они есть. Он возвращает статистику по колонкам (точную либо помеченную как оценка выше порога выборки), целевое число партиций и предел строк планировщика, ранжированные значения `partition_col` / `partition_grouping` / `npartitions` / `max_rows_per_partition` с причинами и предупреждениями и исключённые колонки с причиной и нужным пределом или числом партиций. Не выбирайте исключённую колонку; оценку, близкую к пределу, проверьте точным подсчётом. Оцените число строк и ширину выбранных колонок. Для кандидатов в ключ проверьте типы, индексы, null, кардинальность и перекос. Предпочитайте доступную статистику источника и небольшие агрегированные результаты; точные подсчёты и запросы распределения выполняйте, когда их стоимость приемлема. `max_rows` ограничивает результат запроса, а не работу БД. Небольшой preview сам по себе не доказывает размер таблицы или отсутствие null и перекоса. Явно отмечайте приблизительные оценки и ограничения выборки. Узел фильтра после reader не уменьшает объём чтения из источника.

Выберите и зафиксируйте политику чтения:

- **Подтверждённое небольшое чтение:** например, около 1 000 обычных узких строк можно читать с `npartitions=1` без пользовательской группировки и hash buckets. Текущему планировщику всё равно нужен ключ партиционирования. Перед фиксацией одной партиции для регулярного чтения учитывайте рост таблицы.
- **Автоматический размер:** обычно не задавайте `npartitions`, чтобы планировщик оценивал число по строкам, ширине выбранных колонок и настройкам экземпляра. Осознанный пропуск `partition_grouping` выбирает автоматический range/hash; он не заменяет исследование данных. Десятки или сотни тысяч строк сами по себе не определяют подходящее число партиций.
- **Явная стратегия:** `{"mode":"range"}` требует упорядочиваемого ключа без null. `{"mode":"hash"}` подходит для поддерживаемых nullable/неупорядочиваемых ключей с автоматическим числом buckets; задавайте `buckets` только с обоснованием. Hash не распределяет одинаковые значения или большую группу null между buckets. Первичный ключ или дата — кандидат, а не достаточное основание выбора.
- **Временная группировка:** перед выбором года, месяца или дня проверьте число строк в предполагаемых периодах, особенно в самом большом. Наличие даты или периода бизнес-отчётности само по себе не обосновывает временные группы чтения. Пользовательские группы определяют сегменты независимо от целевого числа; `npartitions=1` не отменяет несколько временных групп или явное число hash buckets.

В комментарии reader кратко укажите факты (измеренные или оценочные), выбранный ключ, решение о группировке, политику числа партиций и причину. Если профилирование недоступно или завершилось тайм-аутом, укажите неизвестное и при возможности используйте автоматическое число партиций с проверенным совместимым ключом; не заявляйте оптимальность и не фиксируйте одну партицию без оснований. После запуска изучите доступную диагностику партиций и памяти. Не полагайтесь на `max_rows_per_partition` при слишком большой группе: разбиение по hash ключа не делит группу null и одно часто повторяющееся значение.

## Примеры

Предположим, в PostgreSQL `public.orders` есть целочисленный `id` без null и числовой `amount`. Подключите объект соединения с БД.

```json
{"table_name":"orders","schema_name":"public","columns":["id","amount"],"partition_col":"id"}
```

Это только значения параметров. Пример осознанно сохраняет автоматический расчёт числа партиций и выбор range/hash после оценки данных. Если проверка того же источника показала около 1 000 узких строк без ожидаемого значительного роста, добавьте `"npartitions":1` для чтения одной партицией. Результат содержит выбранные колонки таблицы. Для проверенной колонки даты с измеренными размерами периодов группировка `{"mode":"granularity","granularity":"year"}` задаёт годовые группы чтения, а не годовые итоги.

## Типовые ошибки

Не найдена таблица/колонка: перечитайте каталог, проверьте БД, схему, регистр и права. Ошибки партиционирования: используйте исходное имя колонки и группировку, совместимую с её типом. Слишком много партиций: изучите распределение данных и настройки вместо произвольного сочетания переопределений. Группа или сегмент больше `max_rows_per_partition`: ошибка планирования называет группу, которую нельзя разбить; ошибка чтения называет сегмент, в котором всё ещё слишком много строк, обычно из-за одного повторяющегося значения ключа. Увеличьте `max_rows_per_partition`, выберите более мелкую группировку или другой ключ. Ошибка планирования со значением ключа партиционирования означает, что это значение или группа null сами по себе больше предела range/hash-сегментов: выберите ключ из рекомендаций `suggest_read_partitioning` или поднимите `max_rows_per_partition` выше указанного числа.
