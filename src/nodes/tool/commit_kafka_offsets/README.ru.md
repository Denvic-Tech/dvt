# Commit Kafka Offsets

Тип ноды: `CommitKafkaOffsets`.

## Назначение и выбор

Явно подтверждает конечную порцию Kafka после успешного завершения назначений.
Используйте с Read Kafka Messages либо самостоятельно с сохранённым разрешённым JSON.
Нода не читает payload сообщений и не вычисляет DataFrame.

## Входы и настройка

- `connection`: обязательный доступный объект Kafka Connection с правами на топик/группу.
- `offsets`: обязательный JSON. Используйте обычное одиночное выражение `kafka_offsets`,
  подключив Read.output_variables к input_variables.
- `signal_in`: подключите успешный signal_out **каждого обязательного назначения**.
  Все подключённые сигналы должны быть активны. Read.signal_out сам по себе не является
  барьером записи. Отсутствие сигнала допустимо для явно запущенного самостоятельного
  commit сохранённого JSON.
- `input_variables`: штатные входные переменные DVT.

JSON требует schema_version=1, непустые topic/group_id и список partitions.
В каждой записи обязательны уникальный целочисленный неотрицательный partition и
целочисленный неотрицательный next_offset. Bool, дроби, дубликаты и неизвестная версия
недопустимы. Необязательный isolation_level по умолчанию read_committed;
также поддержан read_uncommitted.
Если задан cluster_id, он должен совпасть с фактическим; недоступная идентификация
кластера тоже приводит к ошибке. connection_id — диагностика: другое авторизованное
подключение к тому же кластеру разрешено.
Необязательные read_id, start_offset, last_message_offset, message_count, payload_bytes,
messages_read, bytes_read и stop_reason соответствуют JSON-контракту Read.

## Результат

- `signal_out`: true только после всех требуемых подтверждений.
- `signal_error`: штатный сигнал ошибки пайплайна.
- `output_variables.kafka_commit_result`: JSON со списком partitions.
  Запись содержит partition, requested, current (null при отсутствии), resulting и status:
  committed, unchanged либо already_ahead.
- `output_variables.kafka_partitions_committed`: число partitions, продвинутых этим вызовом.

До успеха итоговые переменные unresolved. Выхода DataFrame нет.

## Поведение и ограничения

next_offset — **позиция следующего сообщения**, обычно last_message_offset + 1,
а не количество сообщений. Подтверждается вся исходная порция, включая сообщения,
удалённые downstream-фильтрами или агрегацией.

Все записи, контекст кластера, топик/partitions и верхние границы проверяются до явного
синхронного commit. Позиция выше текущей верхней границы запрещена.
Граница учитывает isolation_level; read_committed использует стабильную границу транзакций.
Пустой partitions — успешное отсутствие изменений после проверки контекста.
Равная позиция — unchanged; более старый JSON — already_ahead без уменьшения позиции.
Перемотки группы назад нет.

Autocommit, балансировка группы, межпроцессные блокировки и атомарный compare-and-set
отсутствуют. Пользователь обеспечивает эксклюзивное использование группы между проектами
и внешними клиентами. Монотонность предполагает отсутствие конкурирующих commit.
Подтверждение Kafka и внешняя запись — разные операции: at-least-once допускает повторную
запись после сбоя между ними. Exactly-once и дедупликация не предоставляются.
Произвольный JSON не доказывает успешность обработки.

Временные транспортные ошибки имеют ограниченные повторы (три попытки, задержки 0.5/1 секунду,
таймаут запроса 30 секунд). Постоянные ошибки авторизации/валидации не повторяются.
Частичный сбой, потеря ответа или отмена после отправки могут оставить сохранённые offsets.
Откат не выполняется; после устранения причины повторите исходный JSON.
STOP до отправки предотвращает commit. Клиенты закрываются без autocommit.
Режим метаданных не имеет побочных эффектов и успешного сигнала. Полный запуск заново
проверяет Kafka; сохранённый результат не подменяет Commit.

## Примеры

Пусть топик orders существует, partition 0 заканчивается не раньше позиции 201,
а группа dvt-orders сохранила позицию 100:

```json
{
  "offsets": {
    "schema_version": 1,
    "topic": "orders",
    "group_id": "dvt-orders",
    "partitions": [{"partition": 0, "next_offset": 201}]
  }
}
```

Подключите GetExistKafkaConnection.connection к CommitKafkaOffsets.connection.
Самостоятельный запуск продвинет группу до 201 и вернёт:

```json
{"partitions":[{"partition":0,"requested":201,"current":100,"resulting":201,"status":"committed"}]}
```

Для обычного пайплайна соедините:
ReadKafkaMessages.output → преобразования → WriteDataFrameToDBV3.df;
ReadKafkaMessages.output_variables → CommitKafkaOffsets.input_variables;
WriteDataFrameToDBV3.signal_out → CommitKafkaOffsets.signal_in.
Kafka Connection.connection подключите к обеим Kafka-нодам.
В offsets задайте штатное одиночное выражение `kafka_offsets`.
Для двух обязательных назначений подключите оба успешных сигнала.
Повтор сохранённого примера при позиции 201 вернёт unchanged и ноль продвинутых partitions.

## Типовые ошибки

- Unresolved offsets: полностью вычислите исходную порцию и завершите все назначения.
  Обращение к переменной не запускает чтение.
- Неверный кластер, топик, partition или позиция выше границы: проверьте подключение,
  JSON и isolation level. JSON не заменяет авторизацию.
- Сбой назначения или неактивный сигнал: Commit не запустится. Исправьте назначение,
  учитывая возможность повторной записи.
- Неопределённый результат commit: проверьте сохранённые позиции либо повторите тот же JSON.
  Ошибка не доказывает, что offsets не изменились.
