# Замена значений

Тип ноды: `DataFrameReplaceValues`.

## Назначение и выбор

Заменяет целые значения одной колонки по словарю. Для изменения подстрок по шаблону используйте `DataFrameRegexReplace`.

## Входы и настройка

Подключите `df`; задайте `column_to_replace` и `dictionary` (старое значение → новое). В JSON ключи словаря — строки.

## Результат

`output` сохраняет все колонки и меняет выбранную.

## Поведение и ограничения

Числовые и datetime-ключи приводятся к типу колонки. Несовпавшие значения сохраняются. Псевдонимы null-ключа: `null`, `none`, `nan`, `nil` и пустая строка. Некоторые несовместимые замены переводят колонку в строки. Для обычных строковых ключей значения замены преобразуются в строки; JSON null не обязательно становится пропуском. При сопоставлении дат учитывается часовой пояс колонки.

## Примеры

Во входном `status` значения `new, done, pending`.

Значения параметров (без оболочки MCP patch):

```json
{
  "column_to_replace": "status",
  "dictionary": {
    "new": "open",
    "done": "closed"
  }
}
```

Результат — `open, closed, pending`.

## Типовые ошибки

Неожиданный тип или обработка null: проверьте небольшой результат и при необходимости явно приведите тип. Нет колонки: проверьте метаданные. Для частичного совпадения строк используйте regex-ноду.

## Обработка нескольких колонок

Необязательный `column_rules` заменяет одиночные настройки. Если он не задан,
старые графы продолжают работать с прежними параметрами и поведением.

Каждое правило содержит уникальный `id`, `selector` и `params`.
Токены `selector.tokens`: `name` — точное имя, `mask` — маска с `*` и `?`,
`all` — все колонки. Выбор объединяется без дубликатов, затем сужается через
`types` (text, number, datetime, boolean, timedelta, other), `exclude` и
необязательный `name_regex`. Маски чувствительны к регистру; остальные символы
маски буквальные. Маски и все колонки пересчитываются на каждом запуске.

Для колонки действует первое подходящее включённое правило сверху.
`enabled: false` отключает правило. Все операции читают исходную таблицу:
новые колонки не попадают под последующие правила. Отсутствующее точное имя —
ошибка; пустая динамическая выборка ничего не меняет и записывает предупреждение.
Конфликты имён результатов и повторные целевые имена — ошибки.

По умолчанию результат заменяет источник. Для новых колонок задайте `output: {"mode": "new", "suffix": "_result"}`. `output.names` переопределяет имена отдельных результатов (источник → результат). Новые имена не могут совпадать с исходными.

В новых правилах `params.pairs` содержит пары `old`/`new`: JSON null и пустая строка различаются. Ключи и значения приводятся к типу каждой колонки; несовместимые замены переводят результат в строки. Замены сопоставляются с исходными значениями, без каскада. `legacy_dictionary` используется редактором для сохранения прежней семантики существующих словарей до их редактирования.

В DVT UI точные имена, маски и «Все колонки» вводятся в одном поле.
Типы, исключения, имена результатов, порядок и отключение правил находятся
под «Дополнительно». Там же доступен предпросмотр схемы «Что изменится»;
проверка на образцах данных не запускается.

Пример (поля `field_*` должны существовать во входе):

```json
{
  "column_rules": [
    {
      "id": "group-1",
      "selector": {
        "tokens": [
          {
            "kind": "mask",
            "value": "field_*"
          }
        ]
      },
      "params": {
        "pairs": [
          {
            "old": "new",
            "new": "open"
          },
          {
            "old": null,
            "new": "unknown"
          }
        ]
      }
    }
  ]
}
```

## Переход сохранённых графов

Миграция БД `0063` автоматически переводит существующие ноды на новый контракт.
Для перенесённых правил `compatibility: "v1"` сохраняет прежние преобразования типов,
пустые значения параметров и разрешённую ранее перезапись. В частности, дробные
смещения усекаются как прежде, а не становятся ошибкой новой схемы.
`input_bindings` сохраняет параметры из выражений и подключений: они вычисляются
при каждом запуске через исходные входы. Редактирование соответствующего поля в UI
заменяет только его привязку явным значением. Другие привязки сохраняются.

Старые входы и служебные данные миграции остаются для обратимого отката. Повторный
upgrade не перезаписывает настроенный контракт. Downgrade восстанавливает исходную
запись, если контракт не редактировался; при наличии правок сохраняет новые данные,
а предыдущая версия использует оставленные старые входы.
