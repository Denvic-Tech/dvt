# Интеграции и кодовые узлы

Прежде чем использовать `ExecutePython`, `DataFrameExecCode` или `HTTPRequest`, проверь, что специализированной low-code ноды недостаточно, затем сверь схему и поведение узла на установленной версии. Держи код читаемым многострочным текстом с реальными переводами строк. В JSON переносы закономерно экранируются как `\n`; оценивай декодированное поле `code`, не заменяй escape-последовательности во всём экспорте. Не прячь модуль в `exec(repr(source), ...)`.

Для Dask выполняй pandas-операции над партициями через `map_partitions` с корректным `meta`, особенно при новых колонках. Сохраняй ожидаемые имена, порядок и dtype выхода; после операций, меняющих число или порядок строк, учитывай `clear_divisions=True`. Для совместимых агрегаций используй поддерживаемые `groupby(...).agg(...).reset_index()`. Проверяй уникальность ID и рост строк перед записью. После вычисления новых колонок обновляй физическую схему приёмника и `column_mapping`.

В одной изученной версии `ExecutePython` выполнял `exec(code, globals, locals)` с разными словарями; функции не видели соседние импорты. Обход `globals().update(locals())` после импортов и объявлений применим только после подтверждения такого поведения. Там же `json_out` шёл в `output_json`, `df_out` — в `output`, а `output_variables` требовали типизированный payload, например `{"type":"STRING","value":"..."}`. `print()` не попадал в доступный журнал, а форматирование `logger.info("Result: %s", value)` оставляло `%s`; проверенно работала уже сформированная строка. Логи проверяй через предоставленный `logger`; не включай URL с токенами, тела запросов и секреты.

Храни постоянные настройки в переменных проекта, а параметры одного запуска — в `runtime_variables`. Проверяй имя и тип без вывода секрета. Если MCP не умеет сохранять переменные проекта, дай пользователю точные имена и типы для заполнения через UI. Не добавляй части базового URL дважды. В выражениях различай `single` (`input_variables.request_url.value`) и `template` (`{{ input_variables.request_url.value }}`); Jinja-текст в `constant` не вычисляется. Наблюдавшийся сбой прямого доступа к `project_variables` в `HTTPRequest.url` не считай универсальным: сначала воспроизведи на нужной версии. При необходимости передай типизированную переменную через Python-узел и порт `input_variables`; проверь `.value` и доступный формат. В одной версии `project_variables.get(...)` в выражении входа валидатор трактовал неверно, хотя в Python-ноде метод работал.

Для одиночного запроса предпочитай `HTTPRequest`: явно задавай метод, параметры, заголовки, timeout и проверку TLS. В изученной версии JSON находился в порту `output`. Проверяй HTTP-статус, тело и бизнес-результат; `200` само по себе не доказывает изменения. Обрабатывай пустой или не-JSON ответ и всю пагинацию (`items`, `total`, `next`). Текст исключения может содержать секретный URL, поэтому очищай логи перед отчётом. Редирект на другой origin не должен автоматически пересылать секреты и POST-тело. После `503` или timeout проверь фактическое состояние сервера и задачи, затем решай вопрос повтора.

Если проект предусматривает режимы, различай `self_test` (фикстуры без сети), `read_only` (чтение реальных API без записи) и `live` (реальные изменения). Указывай режим в отчёте и что именно он подтверждает; не переноси default `live` из одного проекта в другой. Адресный read-only может проверять запись вне рабочих стадий; адресный live не должен обходить проверку стадии без бизнес-правила. Временные ID и диагностические ветки с `target_node_ids` убирай после проверки, чтобы полный запуск не обратился неожиданно к реальному API.

При синхронизации нескольких API выполняй финальное изменение статуса только после успешных шагов. Сохраняй ID созданного внешнего объекта для безопасного повтора. После timeout сначала сверяй состояние, чтобы избежать дублей. Учитывай частичный успех: ошибки собирай по ID, независимые записи продолжай, в отчёте указывай числа успехов и ошибок. Не запускай параллельно без защиты от гонок. Общей транзакции между внешними системами обычно нет.

Обязательность полей определяй по бизнес-контракту конкретного проекта; не приравнивай `401`, `403` или timeout к отсутствующему клиенту.
