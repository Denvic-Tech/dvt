# Выгрузка Битрикс24 в DVT

Перед настройкой проверь схему установленной версии `ReadDataFromBitrix24` и фактический граф проекта. Поведение фильтров дат, границ интервала и режимов зависит от версии расширения; пример ниже описывает рабочий подход, а не универсальную гарантию коннектора.

## Первичная загрузка большого объёма

Если полная выгрузка сущности Битрикс24 срывается из-за ошибки, обрыва соединения или ограничений со стороны Битрикс24, используй `mode=full` и выгружай историю отдельными небольшими интервалами. Начни с окон по 1–2 месяца; при нестабильности уменьши окно. Перед этим проверь на установленной версии, что `start_date` и `end_date` действительно ограничивают нужную сущность в режиме `full`.

Для каждого окна зафиксируй даты, запусти выгрузку и дождись конечного `SUCCESS`. После сбоя прочитай логи и проверь, какие строки уже записаны, прежде чем повторять окно. Сверяй диапазон и число строк в приёмнике; продолжай, пока не будет выгружена вся история сущности. Если приёмник использует `upsert` по стабильному ID, повтор того же окна может обновить уже записанные строки, но семантику повтора и границы дат всё равно нужно проверить. Не переключайся на `incremental`, пока исторические окна не завершены и не проверены.

## Инкрементальная загрузка после истории

Типовой граф строит обратную связь через целевую таблицу:

`GetExistDBConnection → ReadVariablesFromDB → ReadDataFromBitrix24 → WriteDataFrameToDBV4`; DB connection также подаётся в writer

- `ReadVariablesFromDB` в режиме `manual` читает `MAX(updatedTime)` из уже заполненной таблицы сделок и выдаёт переменную, например `updated_time`. Значение по умолчанию применяется, если результат пустой; отсутствующую таблицу оно не создаёт.
- `ReadDataFromBitrix24` получает переменную во вход `last_modified`, использует `entity=deal` и `mode=incremental`. Подключение к Битрикс24 передаётся через переменную проекта без раскрытия секрета. Явно выбирай нужные поля, включая ID и дату изменения.
- `WriteDataFrameToDBV4` пишет в существующую таблицу через `upsert` по ID сделки. Сверь `selected_columns` с `column_mapping`; ID и `updatedTime` должны сохраняться с подходящими типами. Следующий запуск вновь читает максимальную дату из приёмника.

В изученном проекте `28f5d5af-1eec-4467-b3f1-c004a07c413e` переменная `updated_time` берётся как `MAX(updatedTime)` из `deals_v2`, при пустом результате задано `1970-01-01`; `Deals` использует `last_modified=updated_time`, `mode=incremental`, `entity=deal` и переменную проекта `hook_Bitrix`. `Write deals_v2` делает `upsert` по `id`; 266 выбранных полей соответствуют 266 полям записи. В этом снимке графа заданы `start_date=2025-12-30T21:00:00Z`, `end_date=2026-12-30T21:00:00Z`, пакет чтения 200, пул запросов 5, ограничение 2 запроса в секунду и пакет записи 50 000. Эти числа относятся только к данному проекту. Отдельная ветка загружает комментарии сделок в `deal_timeline`.

Перед переносом подхода проверь на текущем расширении, как совмещаются `start_date`, `end_date` и `last_modified`, включены ли записи на границе времени и что происходит с поздними изменениями при одинаковом `updatedTime`. Фиксированный `end_date` может остановить дальнейшую инкрементальную выгрузку после этой даты. Не выдавай эти детали за подтверждённое поведение без исходников или проверки версии коннектора.
