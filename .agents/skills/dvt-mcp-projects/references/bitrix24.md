# Выгрузка Битрикс24 в DVT

## Доступность расширения

Расширение Битрикс24 для DVT является коммерческим и поставляется по отдельной лицензии. По вопросам получения и лицензирования обращайся на [страницу продукта Denvic](https://bi.denvic.ru/products/read-data-from-bitrix24-noda-konnektor-bitriks24/). Перед использованием узлов проверь наличие расширения и лицензии в установке заказчика.

Перед настройкой проверь схему установленной версии `ReadDataFromBitrix24` и фактический граф проекта. Поведение фильтров дат, границ интервала и режимов зависит от версии расширения; пример ниже описывает рабочий подход, а не универсальную гарантию коннектора.

## Имена сущностей и полей

[Официальный Bitrix24 MCP](https://apidocs.bitrix24.ru/ai-tools/mcp.html) — источник актуальной документации REST API, а не данных портала заказчика. Он не вызывает методы на портале и не знает созданные там пользовательские поля. Для поиска нужного REST метода используй `bitrix-search`, затем `bitrix-method-details` по точному имени; не передавай этому MCP вебхуки, токены и пароли.

Для CRM сначала установи тип сущности: `crm.enum.ownertype` возвращает системные типы и смарт-процессы, а `crm.type.list` — настройки и `entityTypeId` смарт-процессов (для него нужен административный доступ к CRM). У сделки `entityTypeId=2`. Затем вызови на **нужном портале Битрикс24** `crm.item.fields` с этим `entityTypeId`: ключи `result.fields` — фактические имена доступных полей, включая пользовательские поля портала. Параметр `useOriginalUfNames=N` (значение по умолчанию) выдаёт пользовательские имена в camelCase, например `ufCrm...`; `Y` — исходные `UF_CRM_...`. Выбирай формат, соответствующий выходу установленного коннектора DVT и `selected_columns`/`column_mapping`. `crm.deal.fields` также возвращает поля сделки, но официальный справочник помечает его устаревшим и рекомендует `crm.item.fields`.

Для сущностей вне CRM и особенностей коннектора сначала найди соответствующие методы и параметры в Bitrix24 MCP, затем получай фактический список через разрешённый вызов REST конкретного портала. Имена сущностей в `ReadDataFromBitrix24.entity` сверяй с определением узла установленной версии: они не обязаны совпадать с именами REST методов или `entityTypeId`. Не строй схему выгрузки только по общему справочнику: набор пользовательских полей и смарт-процессов зависит от портала и прав токена.

Официальные методы: [`crm.item.fields`](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-fields.html), [`crm.enum.ownertype`](https://apidocs.bitrix24.ru/api-reference/crm/auxiliary/enum/crm-enum-owner-type.html), [`crm.type.list`](https://apidocs.bitrix24.ru/api-reference/crm/universal/user-defined-object-types/crm-type-list.html).
## Первичная загрузка большого объёма

Если полная выгрузка сущности Битрикс24 срывается из-за ошибки, обрыва соединения или ограничений со стороны Битрикс24, используй `mode=full` и выгружай историю отдельными небольшими интервалами. Начни с окон по 1–2 месяца; при нестабильности уменьши окно. Перед этим проверь на установленной версии, что `start_date` и `end_date` действительно ограничивают нужную сущность в режиме `full`.

Для каждого окна зафиксируй даты, запусти выгрузку и дождись конечного `SUCCESS`. После сбоя прочитай логи и проверь, какие строки уже записаны, прежде чем повторять окно. Сверяй диапазон и число строк в приёмнике; продолжай, пока не будет выгружена вся история сущности. Если приёмник использует `upsert` по стабильному ID, повтор того же окна может обновить уже записанные строки, но семантику повтора и границы дат всё равно нужно проверить. Не переключайся на `incremental`, пока исторические окна не завершены и не проверены.

## Выбор поля контрольной даты

Не переноси имя поля даты изменения из одного графа на другую сущность. Перед инкрементальной загрузкой проверь: есть ли у сущности поле последнего изменения, как оно называется в конкретном REST методе, в выходном DataFrame установленного коннектора и в целевой таблице, имеет ли пригодный тип даты, заполняется ли при нужных изменениях. Настрой `selected_columns`, сопоставление полей writer, запрос `MAX(...)` из приёмника и вход `last_modified` по **фактическим** именам. SQL-псевдоним выходной переменной может отличаться от имени исходной колонки.

Проверенные примеры:

| Сущность и API | Поле изменения | Наблюдение в DVT |
| --- | --- | --- |
| Лид, универсальный `crm.item.*` | `updatedTime` | Проект `7. Битрикс24 - Лиды` читает `MAX(updatedTime) AS DATE_MODIFY` из таблицы `leads` и передаёт вычисленную переменную в `last_modified`. Здесь `DATE_MODIFY` — псевдоним запроса, а не имя колонки в приёмнике. В старом `crm.lead.*` поле API называется `DATE_MODIFY`. |
| Сделка, универсальный `crm.item.*` | `updatedTime` | В проекте `Битрикс24 - Сделки` `MAX(updatedTime)` из `deals_v2` подаётся в `last_modified`. В старом `crm.deal.*` поле API называется `DATE_MODIFY`. |
| Задача, `tasks.task.*` | `changedDate` в ответе | Проект `Битрикс24 - Задачи и их время` читает `MAX(changedDate)` из таблицы `tasks`. В метаданных `tasks.task.getFields` и в фильтрах встречается `CHANGED_DATE`; в REST 3.0 поле называется `changed`. |

Форма `MODIFY_DATE` не подтвердилась для этих трёх примеров: не подставляй её по памяти. Название из документации REST само по себе не гарантирует то же имя в выходе DVT или колонке БД. Для другого типа сущности поле изменения может называться иначе или отсутствовать. Если надёжного поля нет, не строй инкрементальность через выдуманный `MAX(дата)`: выбери и проверь другой механизм обнаружения изменений (например, поддерживаемый журнал/события или периодическое полное сравнение) с учётом удалений и поздних изменений.

Источники: [поля CRM `crm.item.*`](https://apidocs.bitrix24.ru/api-reference/crm/universal/object-fields.html), [поля задач](https://apidocs.bitrix24.ru/api-reference/tasks/fields.html), [метаданные задач](https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-get-fields.html), [поля задач REST 3.0](https://apidocs.bitrix24.ru/api-reference/tasks/fields-rest-v3.html).

## Инкрементальная загрузка после истории

Если у сущности есть подтверждённое поле изменения, типовой граф строит обратную связь через целевую таблицу:

`GetExistDBConnection → ReadVariablesFromDB → ReadDataFromBitrix24 → WriteDataFrameToDBV4`; DB connection также подаётся в writer

- `ReadVariablesFromDB` в режиме `manual` читает максимум по проверенному полю изменения из уже заполненной таблицы сущности и выдаёт переменную для следующего шага. В изученном проекте сделок это `MAX(updatedTime)` → `updated_time`. Значение по умолчанию применяется, если результат пустой; отсутствующую таблицу оно не создаёт.
- `ReadDataFromBitrix24` получает переменную во вход `last_modified`, использует `entity=deal` и `mode=incremental`. Подключение к Битрикс24 передаётся через переменную проекта без раскрытия секрета. Явно выбирай нужные поля, включая ID и дату изменения.
- `WriteDataFrameToDBV4` пишет в существующую таблицу через `upsert` по ID сделки. Сверь `selected_columns` с `column_mapping`; ID и `updatedTime` должны сохраняться с подходящими типами. Следующий запуск вновь читает максимальную дату из приёмника.

В примере проекта сделок переменная `updated_time` берётся как `MAX(updatedTime)` из `deals_v2`, при пустом результате задано `1970-01-01`; `Deals` использует `last_modified=updated_time`, `mode=incremental`, `entity=deal` и переменную проекта `hook_Bitrix`. `Write deals_v2` делает `upsert` по `id`; 266 выбранных полей соответствуют 266 полям записи. В этом снимке графа заданы `start_date=2025-12-30T21:00:00Z`, `end_date=2026-12-30T21:00:00Z`, пакет чтения 200, пул запросов 5, ограничение 2 запроса в секунду и пакет записи 50 000. Эти числа относятся только к данному проекту. Ветка таймлайна описана ниже.

## Связанный таймлайн CRM

В изученном графе сделок выход `Deals.output` идёт в две ветки: напрямую в `Write deals_v2` и в `GetTaskDataFromBitrix24V2.df`. Вторая нода берёт ID сделок из `id_column=id`, использует то же подключение к Битрикс24 через переменную проекта, запрашивает `entity=timeline_deal` и выдаёт DataFrame записей таймлайна. Параметры этого примера: пакет 50, пул запросов 6, ограничение 2 запроса в секунду, `operating_limit=400`. Её выход поступает в `WriteDataFrameToDBV4`, который пишет в существующую `bitrix_data.deal_timeline` через `upsert` по `ID` пакетами по 1000 строк. В сопоставлении есть `ID` записи, `ENTITY_ID` сделки, `ENTITY_TYPE`, `CREATED`, автор, текст комментария, файлы и поля заметки (всего 12 полей). Отдельное ребро передаёт writer объект DB connection. Два writer получают общий DataFrame сделок; между ними нет ребра, задающего порядок записи.

Для лидов применяй тот же шаблон: инкрементально или окнами получи родительские лиды, передай их DataFrame и фактическую колонку ID в `GetTaskDataFromBitrix24V2` с `entity=timeline_lead`, затем пиши связанные записи в отдельную подготовленную таблицу через `upsert` по ID записи таймлайна. Схему и имена колонок сверяй по выходу установленной версии, а контрольную дату родительской выгрузки считывай из таблицы лидов.

Для смарт-процессов аналогичен принцип «выгрузка изменившихся родительских элементов → получение их таймлайна по ID → upsert связанных записей». Основная нода версии Bitrix24 Connector 0.10.2 допускает `ReadDataFromBitrix24.entity=spa` и вход `entity_type_id`. Но `GetTaskDataFromBitrix24V2.entity` в этой версии предлагает только `timeline_deal`, `timeline_lead`, `timeline_contact`, `timeline_company` (помимо данных задач); `timeline_spa` в списке нет. Поэтому не подставляй его без проверки: для таймлайна смарт-процесса найди поддерживаемый способ в установленной версии коннектора или через документированный REST метод и проверь результат на конкретном портале.

При инкрементальной загрузке связанных записей эта ветка получает только ID родительских элементов, попавших в текущую выгрузку. Проверь, меняется ли `updatedTime` родителя при добавлении или изменении комментария; иначе такой комментарий может не попасть в ветку без отдельной стратегии догрузки. При первоначальной `full` выгрузке окнами проверяй завершение обеих веток и отсутствие пропущенных ID. Повторное окно с `upsert` может обновить ранее записанные комментарии, но не заменяет проверку полноты.

Перед переносом подхода проверь на текущем расширении, как совмещаются `start_date`, `end_date` и `last_modified`, включены ли записи на границе времени и что происходит с поздними изменениями при одинаковом `updatedTime`. Фиксированный `end_date` может остановить дальнейшую инкрементальную выгрузку после этой даты. Не выдавай эти детали за подтверждённое поведение без исходников или проверки версии коннектора.

## Задачи, затраченное время, результаты и история

Образец четырёх веток — отдельный проект задач и связанных данных. Проект сделок с таймлайном — другой проект; не смешивай их графы.

Источник `Tasks` — `ReadDataFromBitrix24` с `entity=task`, `mode=incremental`. Перед чтением `ReadQueryFromDBV3` получает `MAX(changedDate) AS changedDate` из `bitrix_data.tasks`; `DataFrameSelectVariables` превращает результат в переменную `changedDate`, которая поступает на вход `last_modified` источника. Подключение Битрикс24 передаётся через переменную проекта `hook_Bitrix`. Для первичной истории применяй описанную выше загрузку `full` небольшими окнами, затем переключайся на инкрементальную.

Один DataFrame задач разветвляется по ID задачи (`id`):

| Данные | Ветка после `Tasks` | Приёмник в примере |
| --- | --- | --- |
| Задачи | Непосредственно `WriteDataFrameToDBV3` | `bitrix_data.tasks`, `upsert` по `id` |
| Затраченное время | `GetElapsedTimeFromBitrix24` с `task_id_column=id` | `bitrix_data.tasks_elapsedtimes`, `upsert` по `TASK_ID` |
| Результаты задач | `GetTaskDataFromBitrix24V2` с `entity=task_result`, `id_column=id` | `bitrix_data.task_results`, `WriteDataFrameToDBV4`, `upsert` по `id` |
| История задач | `GetTaskDataFromBitrix24V2` с `entity=task_history`, `id_column=id` | `bitrix_data.task_history`, `upsert` по `id` |

Все четыре writer получают объект подключения к БД. В примере пакеты записи — по 1000 строк; у связанных запросов пакет 50, пул 6, ограничение 2 запроса в секунду. Это настройки конкретного графа, их нужно подбирать по нагрузке и ограничениям портала. Для результатов задач writer явно сопоставляет `id`, `taskId`, `commentId`, `createdBy`, `createdAt`, `updatedAt`, `status`, `text`; два поля дат имеют тип `DATETIME`. Проверяй фактические имена и типы выхода установленной версии расширения.

В ревизии 8 у `bitrix_data.task_history.df` один источник — `Task history.output`; отдельное ребро передаёт writer подключение к БД. Для полноты связанных таблиц проверь, попадают ли в очередной инкремент задачи, у которых изменилось только затраченное время, результат или история: если `changedDate` родителя не обновляется, нужна отдельная стратегия догрузки этих данных. Также пересмотри фиксированный `end_date` перед запуском после указанной в графе даты.

## Организация проектов выгрузки

Группы сущностей Битрикс24 лучше оформлять отдельными дочерними проектами: например, сделки вместе с их таймлайном, лиды с таймлайном, задачи со временем, результатами и историей. Так каждую группу видно отдельно при исполнении, у неё собственные логи, граф и возможность исправить и перезапустить её без изменения остальных групп.

Свяжи нужные дочерние проекты в одном главном проекте нодами `ExecuteProject`. Для каждой ноды укажи `target_project_id`, дай ей понятное имя сущности и включи `wait_for_completion=true`, когда следующий шаг должен дождаться завершения предыдущего. Соединяй `signal_out → signal_in` в порядке требуемой выгрузки. Для строгой последовательности делай одну цепочку; параллельные ветки создавай только там, где они действительно допустимы. Настрой тайм-аут и поведение при нём под длительность выгрузки. В главном графе легко увидеть общий ход, переставить этапы или исключить ненужную сущность; подробности исполнения и исправления остаются в дочернем проекте.

Типовой главный проект использует `ExecuteProject` с `target_project_id`, `wait_for_completion=true` и сигнальные рёбра между этапами. Для последовательной выгрузки Битрикс24 строй одну цепочку в порядке зависимостей; параллельные ветки оставляй только для независимых этапов.
