# Построение графа DVT

## До изменений

Найди проект через `list_projects`, разреши неоднозначность имени и используй точный `project_id`. Получи `get_project`, полный `get_project_graph` со всеми страницами, актуальные `graph_revision` и `graph_etag`; изучи узлы, связи, входы и выходы, подграфы, комментарии и расположение. Найди подходящие узлы через `search_nodes` и прочитай их текущие определения через `get_node_definition`. Для нового проекта вызови `create_project` с непустым `name` и при необходимости известным `folder_id`, затем прочитай пустой граф. Создание требует токена с `projects.mode=all`; ограниченный токен не расширяется автоматически. Если из контекста неясно, нужен новый или существующий проект, сначала уточни намерение. На старой версии без этого инструмента используй поддерживаемый интерфейс или запроси ID созданного проекта. Прежде чем менять граф, убедись, что он пуст либо предназначен для задачи.

Подробный выбор узлов, соединений и таблиц — в [данные и low-code](data-nodes.md). Предпочитай специализированные low-code узлы для чтения, фильтрации, соединения, агрегации и записи. Не добавляй deprecated узлы. Для SQL/Python и обходных решений оставляй содержательный комментарий с причиной. ID подключения задавай как `connection_ref` у соответствующего `GetExist*Connection`; потребитель получает объект через порт `connection`. Не извлекай credentials.

Перед чтением таблицы проверь каталог: точные имена и типы колонок, nullable, ключи, индексы и колонку сегментации. У `ReadTableFromDBV3` укажи явный непустой список `columns`, включая поля фильтра, join и группировки. Для каждого нового или перенастраиваемого чтения оцени объём, ширину выбранных колонок, null, кардинальность и перекос ключа через read-only SQL либо свежий профиль того же источника и объёма чтения. Выбери одну партицию, автоматическое разбиение или обоснованную группировку по правилам [чтения и сегментации](data-nodes.md#чтение-и-сегментация) и запиши факты и причину в комментарии reader. Не выбирай первичный ID или временную сегментацию автоматически. Сегментация чтения и бизнес-группировка по месяцу — разные операции.

Ставь фильтр до агрегации, когда агрегируются выбранные строки. При вставке узла замени старое ребро двумя новыми и проверь источники обязательных входов. Для `DataFrameGroupByAgg` согласуй длины `source_cols`, `agg_funcs`, `new_cols`.

Перед join со справочником проверь уникальность правого ключа, null и типы по полной комбинации колонок. Нормализуй и дедублицируй детерминированным бизнес-правилом; не скрывай реальную связь многие ко многим. После join проверь кратность ключей и изменение числа строк.

`WriteDataFrameToDBV4` не создаёт таблицу. Разовую подготовку цели выполняй через MCP до применения графа: `resolve_write_columns`, создание отсутствующих объектов или preview/apply действий над колонками, повторное чтение схемы и явный `column_mapping`. Полный порядок — в [запись и DDL](data-nodes.md#запись-и-ddl). Разовая MCP-подготовка не требует DDL-ноды или signal-зависимости. DDL в графе нужен только как часть выполнения пайплайна либо при отсутствии нужной MCP-операции; для такого fallback обеспечь зависимость writer. `truncate` допустим только для согласованной полной перезаписи.

Для сравнения таблиц проверь схемы, бизнес-ключ и кратность дублей. Для Excel в S3 передавай `GetExistS3Connection.connection` в `SaveExcel.connection`; путь относителен к bucket/prefix. После `SUCCESS` проверь файл через storage catalog, включая размер и время изменения.

## Атомарные проекты и головной пайплайн

Для большой ETL-системы разделяй независимые выгрузки и трансформации на небольшие проекты с понятной целью и результатом. Складывай связанные атомарные проекты в одну папку (группу проектов), чтобы их было легко найти, отдельно запустить, прочитать логи, исправить и повторить. Головной проект собирает их в общий процесс через узлы `ExecuteProject` с точными `target_project_id` и понятными именами этапов.

Порядок исполнения задают рёбра `signal_out → signal_in`. Если следующий этап зависит от завершения дочернего проекта, установи `wait_for_completion=true`; для строго последовательного процесса соедини все этапы одной цепочкой. Независимые этапы можно разветвлять, а зависимые ветки сводить перед продолжением. Настрой тайм-ауты, отмену по тайм-ауту и передачу переменных с учётом длительности и контракта каждого дочернего проекта. Изменение набора этапов выполняй в головном графе, не смешивая детали всех ETL-операций в одном большом графе.

Расписание общей сборки назначай головному проекту. Дочерние проекты оставляй доступными для ручной диагностики и повторного запуска; отдельные расписания им задавай только при самостоятельной потребности, чтобы не запускать одну и ту же выгрузку дважды. Управляй расписанием через инструменты MCP установленной версии:

| Инструмент | Назначение |
| --- | --- |
| `list_project_schedules` | Прочитать доступные расписания, включая отключённые, с пагинацией. |
| `get_project_schedule` | Прочитать настройки, следующий запуск, последние запуски и цепочку повторов; `schedule: null` означает отсутствие расписания. |
| `set_project_schedule` | Создать или заменить настройки расписания и сразу включить его. |
| `update_project_schedule` | Изменить только переданные поля `patch`, сохранив остальные настройки и состояние включения. |
| `set_project_schedule_enabled` | Включить или выключить существующее расписание через `enabled`, сохранив настройки. |

Все операции требуют ADMIN/SUPERADMIN и доступа пользователя и токена к проекту. Cron содержит пять полей и работает в UTC. Если пользователь задал местное время, а часовой пояс неизвестен, уточни его. Настройки включают режим выполнения, принудительный запуск и параметры повторов; сверяй ограничения со схемой инструмента. В patch пропускай неизменяемые поля, не передавай null. Состояние переключай отдельным инструментом.

Перед активацией проверяется доступ к подключениям графа. Выключение доступно и при проблемах с подключениями: оно предотвращает будущие попытки планировщика и отменяет цепочку повторов, но не заменяет STOP выполняющейся задачи. Расписание сохраняется независимо от срока действия MCP-токена.

После изменения перечитай `get_project_schedule`, проверь настройки и `next_run_time`. Настройка расписания сама по себе не требует немедленного запуска проекта. При отсутствии инструментов на старой установке используй разрешённый интерфейс конкретной версии; не подставляй адреса и токены из других инсталляций.

В рассмотренном примере головной проект вызывает через `ExecuteProject` отдельные проекты лидов, сделок, задач, смарт-процессов и истории. Дочерние проекты сгруппированы в папке; головной проект может находиться в другой папке. Граф сочетает цепочки, развилки и независимые стартовые этапы, поэтому для строго последовательного процесса выстраивай одну цепочку. Используй project ID, папки и зависимости конкретной установки.

## Применение и завершение

Вызови `validate_graph_changes`, затем примени тот же патч с актуальными revision/etag. При конфликте перечитай граф и пересобери патч. Проверь MCP `isError` и наличие структурированного результата до чтения ID или токенов версии. Меняй только нужные поля. Координаты агент не передаёт: сервер автоматически перераскладывает затронутые связанные части при структурных изменениях, сохраняя позиции независимых частей.

Запуск, диагностика, критерий завершения и проверочный список — в [выполнение и проверка](execution.md). MCP patch, генератор патча и UI-экспорт — разные артефакты.


## Временные ссылки и серверные идентификаторы

В `add_nodes` укажи уникальный внутри патча `ref` вместо `id`. Это непустое обозначение
до 255 символов, например `reader`, а не постоянный ID. Концы новой связи имеют вид
`{"ref": "reader"}` для новой ноды или `{"id": "node_..."}` для существующей.
Не передавай `id` создаваемых связей и `position` ни для новых, ни для существующих нод.
Постоянные ID `node_<uuid>` и `edge_<uuid>` генерирует сервер; существующие ID сохраняются.

Валидация возвращает `preview` с составом изменений и перемещаемыми сущностями, без сохранения.
Примени тот же патч с теми же revision/etag. Ответ применения содержит `node_ids_by_ref`:
используй полученные ID для последующих изменений и запусков. В следующем патче тот же `ref`
можно использовать для другой новой ноды. Не подставляй ref внутрь параметров, SQL или выражений.
При ошибках новые ноды обозначаются через `node_ref`, существующие — через `node_id`.
После тайм-аута применения перечитай граф и определи оставшуюся работу; не повторяй создание
вслепую с обновлёнными токенами версии.

Компоновка охватывает связанные части графа до и после структурного изменения. Она может двигать
существующие подграфы вместе со всеми участниками. Изменения только параметров или комментариев
не запускают перерасстановку. Ошибка компоновки отменяет весь патч.

Для просьбы упорядочить уже существующий проект используй `auto_layout_project`:
сначала `dry_run=true` (значение по умолчанию), затем `dry_run=false` с теми же revision/etag.
Предпросмотр показывает перемещаемые ноды, подграфы и границы. Если задача уже согласована,
предпросмотр сам по себе не требует повторного разрешения пользователя.

Отдельная компоновка меняет только координаты, не запускает пайплайн и не требует запуска после
применения. Она работает с недонастроенными нодами и недоступными расширениями; нужны доступ
к проекту и целостные ссылки графа. Пустой граф допустим. Результат проверь чтением графа.
Это исключение из обычного validate/apply/run относится только к `auto_layout_project`.
Расчётные размеры карточек фиксированы; визуальное совпадение с ELK в UI не гарантируется.
Создавать, удалять и редактировать свойства подграфов через MCP по-прежнему нельзя.
