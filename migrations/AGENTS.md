# Миграции без длительного простоя клиента

DVT работает на машине клиента, к которой у разработчиков может не быть доступа.
Миграции предшествуют запуску Gateway. Приоритет — быстро вернуть клиенту работающий DVT
после обновления, сбоя или отката, сохранив данные. Ручной SQL и срочный патч не являются штатным восстановлением.

## Обновление

- Не добавляйте `raise` для ожидаемых особенностей старых данных: пустых полей, старых форматов,
  дублей и конфликтов имён. Такие случаи должны иметь безопасный сценарий перехода.
- Предпочитайте добавление совместимых полей и сохранение старого представления данных.
  Переименование, удаление и ужесточение ограничений выполняйте только после подготовки данных
  и совместимости приложения. Не совмещайте разрушительное преобразование с первым запуском новой версии.
- Однозначные исправления выполняйте автоматически. Неоднозначные данные сохраняйте без потерь
  и произвольного выбора владельца. Оставить запись как есть допустимо, только если приложение
  сможет с ней запуститься и работать; иначе до выпуска нужен совместимый путь обработки.
  Нельзя просто перенести исключение из миграции в стартовую синхронизацию.
- Сохраняйте ID, связи, настройки, пути и физические хранилища. Не выдумывайте identity из
  отображаемого имени и не удаляйте данные ради успешной миграции. Выводите предупреждения с ID,
  без секретов; не скрывайте ошибки общим `except: pass`.
- Обязательная часть миграции должна быть короткой: избегайте длительных блокировок, сетевых
  запросов и зависимости от доступности внешних сервисов. Большие преобразования выполняйте
  возобновляемыми порциями вне критического пути запуска при поддержке промежуточного состояния.
- Используйте транзакции для атомарных изменений. После прерывания повторный запуск должен
  безопасно завершать переход, а не падать на уже созданной колонке или обработанной записи.

## Откат и проверка

- Проектируйте `upgrade()` и `downgrade()` вместе. Не ставьте в `downgrade()` исключение
  «откат не поддерживается»: откат должен возвращать возможность запустить предыдущую версию.
- Не обязательно физически отменять каждое изменение. Новые поля и сохранённые данные можно
  оставить, если предыдущая версия с ними работает, а повторный `upgrade()` корректно их учитывает.
  Пустой `downgrade()` допустим только при проверенной совместимости, включая ревизию Alembic.
- Проверяйте обновление со старых данных, конфликты, прерывание и повторный запуск, а также цикл
  `upgrade → downgrade → upgrade`. Проверяйте запуск и синхронизацию приложения после переходов;
  успешный Alembic или старт контейнера сами по себе недостаточны. Особенности PostgreSQL проверяйте на PostgreSQL.
- Если переход нельзя сделать совместимым, разбейте его на этапы/релизы. Выявляйте препятствия
  до остановки рабочей версии; не выпускайте переход, восстановление которого требует доступа разработчика.
- Предусмотрите доступный клиенту путь возврата рабочей версии при сбое; возврат образов сам по себе
  не откатывает БД. Резервное восстановление — аварийная мера, а не обычный ответ на конфликт метаданных.
- Исправление в N+1 не помогает клиенту, застрявшему на N. Исправляйте сам заблокированный переход;
  не используйте `stamp` для сокрытия невыполненных изменений.
