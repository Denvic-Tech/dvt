# Применение проверенного комплекта

Отдельный исполнитель применяет сохранённую операцию, принятую через мастер или API.
Для установки сначала нужен `VerifiedStaging.prepare` с известным образом bootstrap-мастера.
Для обновления нужны зафиксированный исходный комплект, поддерживаемая пара ревизий,
закрытый gate и проверенная копия. Выбор версии из подписанного каталога и подготовка
предшествуют подтверждению обслуживания. `--public-url` задаёт адрес приложения, который
исполнитель проверяет после запуска. Мастер использует отдельный сохранённый адрес.
[Действия оператора](operator_browser.md) · [Окно обслуживания и копия](maintenance_backup.md)

- `MIGRATING`: исполнитель сверяет подпись, отпечаток манифеста и эффективный Compose с
  приватным планом. Если `.bootstrap/release-trust.json` присутствует, это актуальная политика
  (`roots`: ID → hex, `revoked_signers`: список fingerprints); иначе действуют доверенные корни и
  отзывы на момент staging. До пуска записывается операция и неизменяемая связка экземпляра,
  digest комплекта, digest Gateway, исходной и целевой ревизий, PostgreSQL system identifier
  и OID базы. При обновлении исходная копия и реально замороженный gate проверяются повторно.
- `migrate` выполняет PostgreSQL readiness и `pg_try_advisory_lock` на одном физическом соединении.
  Core Alembic и запись `core` фиксируются одной транзакцией. Затем готовятся расширения; ошибки
  отдельных расширений записываются как прежде. Подписанное необязательное поле
  `schema.required_extensions` перечисляет расширения, ошибки, отключение или отсутствие которых
  блокируют запуск. После проверки записывается `done`. Повтор с точной записью `done` или
  `resumed` проверяет текущие схему и обязательные расширения без повторной подготовки. Старый
  код выхода 0 без совпадающей записи в текущей БД не подтверждает миграцию.
- `APPLYING` / `VERIFYING`: после подтверждения одноразового контейнера запускается полный Compose
  без списка прикладных служб. Мастер независим. Новый образ предварительно читает журнал, затем
  проверяется по сохранённому HTTP- или HTTPS-адресу с тем же ID. Если новый мастер не отвечает,
  возвращается известный предыдущий мастер. Исполнитель проверяет привязки к образам, Gateway через Proxy, UI, живой
  Scheduler, Orchestrator и доступные слоты или heartbeat работающих воркеров текущих контейнеров.
  Для включённого MCP проверяются его приватное соединение с Gateway и публичный маршрут; для
  выключенного публичный маршрут должен возвращать 404. Незавершившийся Compose можно повторить по ID.
- После двух последовательных наблюдений готовности сохраняются рабочие `.env` и
  `docker-compose.yaml` как защищённые файлы, затем атомарно публикуется
  `.bootstrap/current-release.json`. Предыдущие файлы остаются в прежнем staging и в проверенной
  копии. `RESUMING` открывает gate только по своему ID и в одной транзакции PostgreSQL записывает
  `resumed`. Повтор подтверждает эту же запись и состояние gate; только после этого операция
  переходит в `SUCCEEDED`.

Манифест должен быть действующим при первом допуске. После истечения срока можно довести до
готовности тот же заранее разрешённый комплект, если реальная БД и ревизия подтверждают `done`
или `resumed`. Отзыв ключа, удаление корня и отсутствие подтверждённого результата блокируют
продолжение: сохраните журнал и копию, не открывайте gate вручную; для смены комплекта или
аварийного возврата используйте [процедуру восстановления](recovery.md). Старая подпись без
`schema.required_extensions` проверяется без добавления нового поля в подписанные байты.

Режим стандартного Compose и dev сохраняет отдельный `migrate` без контекста операции; это не
является подтверждённым обновлением. Для локального запуска Gateway напрямую сначала выполните
`<venv>/bin/python -m services.gateway.migrate` с тем же окружением БД. Release Bake продолжает
собирать отдельный образ Gateway один раз; мигратор использует тот же образ. Профиль проверенного
обновления не переносит PostgreSQL, не меняет её инфраструктурный образ и не управляет
восстановлением физических клонов базы.
