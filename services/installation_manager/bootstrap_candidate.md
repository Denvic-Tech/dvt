# Кандидатный bootstrap мастера DVT

Для публичной установки используйте
[руководство оператора](customer_installation.md).

## Частная проверка публичного входа

Разместите ту же версию `install.sh` на изолированном HTTPS-origin.
Запустите приватный каталог Distributor с точным подписанным RC.
В манифесте укажите bytes `host_bootstrap.py` с поддержкой контейнерного
режима и digest утверждённого образа. Новый SHA bootstrap требует нового
подписанного манифеста. Выдавайте artifact на подписанном HTTPS URL.
Проверяйте с хоста без Python. Bootstrap исполняется в одном временном
контейнере этого же образа, а хостовый systemd вызывает сохранённый POSIX
launcher для продолжения.

~~~bash
bash <(curl -fsS --cacert "$TEST_CA" "$TEST_RAW/dvt/install.sh") \
  --dir /var/lib/dvt-private --project dvt-private --port 8889 \
  --catalog-origin "$TEST_CATALOG" --catalog-ca "$TEST_CA" --test-rc \
  --public-url https://dvt.example.org
~~~

`TEST_CA` подтверждает сертификаты raw, каталога и HTTPS assets. Настройте
доверие тестового Docker Registry отдельно в Engine. Выполняйте команду
в административном терминале. Проверьте выбор точного RC и его закреплённого
digest. Мастер показывает RC в общем списке и передаёт `confirm_rc` при выборе
предварительного релиза. [Частный Distributor](https://github.com/Denvic-Tech/denvic-distributor)

## Закрепление вручную и замена мастера

Для установки кандидата нужны локальный Docker Engine с Linux amd64 и Compose,
systemd для регистрации службы, административный терминал и доверенные digest трёх ролей. Роли исходного мастера и исполнителя могут использовать один образ с поддержкой соответствующих режимов. Целевой образ отличается от исходного. Используйте выделенный экземпляр и проверяйте происхождение digest до запуска.

Из корня доверенного комплекта запустите одну команду.

~~~bash
sudo /usr/bin/python3 ./services/installation_manager/host_bootstrap.py bootstrap --non-interactive \
  --dir /var/lib/dvt-beta --project dvt-beta --port 8888 \
  --public-url https://dvt.example.org \
  --manager "registry.example.org/dvt/manager@sha256:<source_digest>" \
  --candidate "registry.example.org/dvt/manager@sha256:<target_digest>" \
  --executor "registry.example.org/dvt/manager@sha256:<executor_digest>" \
  --cert /secure/manager-cert.pem --key /secure/manager-key.pem \
  --ca /secure/manager-ca.pem --containerd-root /var/lib/containerd
~~~

Подставьте полные digest вместо угловых скобок. Для файлов TLS используйте PEM, сертификат с SAN `DNS:localhost` и CA, которой доверяет рабочее место. Не добавляйте приватный ключ в комплект. В интерактивном режиме опустите `--non-interactive` для заполнения недостающих значений. На хосте без Docker команда выведет необходимость административных прав и подготовит APT-пакеты из подписанного репозитория Docker только по `--install-docker` или после согласия в терминале. Источник закреплён за опубликованным основным fingerprint.

Если Engine использует containerd image store, передайте его фактический каталог, определённый по конфигурации этой ВМ. Например, типовое системное значение `/var/lib/containerd` отличается от каталога встроенного containerd. Для Engine без containerd image store опустите `--containerd-root`. Дополнительные `--temporary` и `--backup` задают реальные каталоги хоста. По умолчанию это `tmp` и `backup` под каталогом DVT. Bootstrap фиксирует путь хранилища Docker по ответу локального Unix socket и передаёт backing paths и хостовый `/etc/os-release` в контейнер за пределами приложения. Исполнитель использует хостовое сетевое пространство. Эти параметры берутся из root-owned конфигурации.

Команда возвращает `https://localhost:8888`, ID экземпляра, канонический каталог и проект. Повтор с теми же параметрами сохраняет их. В удалённом сценарии запустите из рабочего места `ssh -N -L 127.0.0.1:8888:127.0.0.1:8888 administrator@host`, проверьте SSH host key и откройте тот же HTTPS-адрес в браузере. Используйте доверенный для браузера CA и проверку имени localhost. Мастер публикует порт только на IPv4 loopback хоста. Если локальный порт занят, освободите его для туннеля с тем же номером, который сохранён в identity.

При первом запуске из административного терминала команда печатает одноразовый код на 10 минут. Введите его в поле мастера. После запуска без терминала или по истечении срока получите новый код командой `sudo /usr/bin/python3 /var/lib/dvt-beta/.bootstrap/host_bootstrap.py bootstrap --dir /var/lib/dvt-beta --new-pairing-token` из защищённого терминала. Сессия действует восемь часов и сохраняется при пересоздании мастера. Для автоматизации используется отдельный Bearer, хранящийся в защищённом файле `.bootstrap/machine-token`. Передаваемые браузером изменения требуют точного Origin и заголовка CSRF, машинный вход используется вне браузера. Передача секретов в URL не поддерживается.

## Операция кандидата

- `GET /api/operations/candidate` возвращает закреплённое намерение обслуживания управляющего интерфейса.
- `POST /api/operations` принимает `{"kind":"manager_recovery","release":{"release_id":"…","manifest_digest":"sha256:…"}}` и заголовок `Idempotency-Key`. Ответ `202` подтверждает сохранённый ID. `409` содержит активный ID и `Location`.
- `GET /api/operations/active`, `GET /api/operations` и `GET /api/operations/{id}` читают текущее состояние и историю. `GET /api/operations/{id}/events?after=0&limit=100` читает журнал страницами. `POST /api/operations/{id}/resume` запускает продолжение того же ID.
- Хостовый unit `dvt-bootstrap-<project>.service` после старта Docker запускает временного исполнителя для незавершённого ID. Исполнитель повторно сверяет контейнеры, подхватывает host lock, проверяет формат журнала и подтверждает HTTP-доступ к тому же ID на том же адресе.
- Старые HTTP-входы в этом экземпляре требуют авторизации и возвращают `410` с указанием нового API. Для прежнего мастера предусмотрен отдельный raw URL `dvt/services/installation_manager/install.sh`.

Дескриптор `manager-handoff-v1` закрепляет образы исходного и целевого мастеров и исполнителя, платформу и формат журнала. Он согласуется хостовым администратором для данного стендового экземпляра. Формат подписанного release-манифеста и проверка продукта описаны отдельно. Bootstrap Compose находится в `.bootstrap/bootstrap.compose.yaml`, а Compose кандидатной операции и подтверждение передачи лежат в её staging-каталоге. Контролируемый Compose содержит только мастер. При проверенном возврате предыдущего digest состояние операции `cancelled`, а журнал сохраняет причину недоступности цели. Установка приложения выполняется через операторский API с подготовкой и проверенной миграцией. Обновление также включает проверенную резервную копию. [Проверенная подготовка релиза](verified_staging.md) · [Применение приложения](migration_apply.md)


## Локальная проверка образа мастера

В одноразовом Debian с работающим Docker и Compose запустите корневой
`install.sh` из копии репозитория. Образ мастера заранее загрузите в Docker
этого Debian с проверяемым RepoDigest. В примере используется
локальный образ `dvt/installation_manager:latest`.

```sh
sh ./install.sh --local-image dvt/installation_manager:latest --channel rc \
  --public-url http://localhost --containerd-root /var/lib/docker/containerd/daemon
```

Режим `--local-image` использует локальный digest и чистый каталог данных.
Укажите фактический корень containerd, если Docker использует его для хранения
образов. Команда выше указывает путь для тестового Debian. Мастер и отдельный
исполнитель используют локальный образ, а каталог релизов предоставляет политику
доверия и проверяемые данные релиза DVT. Если Debian запущен во вложенном
Docker, пробросьте порт мастера на loopback рабочего компьютера и откройте
полную ссылку с одноразовым кодом, напечатанную в терминале.


Чтобы проверить локальную сборку интерфейса DVT, добавьте к команде `install.sh`
флаг `--local-ui-image dvt/ui:local-setup`. Образ можно собрать командой
`docker build -t dvt/ui:local-setup .` из каталога `dvt-ui`, затем загрузить
в Docker тестового хоста с проверяемым RepoDigest.

Флаг доступен вместе с `--local-image` при новой онлайн-установке. Bootstrap
фиксирует digest локального образа. Исполнитель проверяет подписанный Compose
и манифест, после чего использует локальный digest для сервиса `ui`.
Остальные сервисы используют образы из подписанного релиза.
