# Продолжение и восстановление DVT

## Действия по ID

Защищённый мастер показывает доступные действия в сохранённой операции. Сохраните
исходный ID, скачайте диагностику и продолжайте по этому ID. Для экземпляра,
созданного публичной командой, используйте сохранённый launcher.

```sh
sudo /bin/sh /var/lib/dvt/.bootstrap/host-launch.sh resume /var/lib/dvt
sudo /bin/sh /var/lib/dvt/.bootstrap/host-launch.sh recover-manager /var/lib/dvt \
  --operation-id "$OPERATION_ID"
```

Подставьте фактический каталог экземпляра. Для ранее созданных экземпляров и
офлайн-поставок CLI из `.bootstrap/host_bootstrap.py` принимает те же ID и использует
тот же исполнитель и блокировку.
На подготовке можно отменить операцию без остановки действующего комплекта. Повтор подготовки
использует `VerifiedStaging.prepare` с тем же закреплённым манифестом. Если до подготовки
первой онлайн-установки пропал bootstrap-мастер и проект пуст, повтор bootstrap или хостовый
`resume` поднимает последний подтверждённый образ. Подготовка продолжится с прежним ID
после проверки исходного digest. В незамороженном окне можно продлить ожидание или
отложить обслуживание.

После проверенной копии и до появления контекста миграции `return-to-source --operation-id ID`
возвращает прежние процессы. Исполнитель проверяет рабочий Compose, реальные ID контейнеров,
образы, ревизию, идентификатор PostgreSQL и копию. Gate остаётся замороженным, пока прежние
приложение и его публичный URL не подтвердят готовность. Открытие gate и запись о возврате
совершаются одной транзакцией. Операция заканчивается отменой, прошлые записи остаются в журнале.

После обрыва миграции исполнитель проверяет фактическую ревизию, активный контейнер и
advisory lock PostgreSQL. Он различает начало, незавершённый результат, завершённую core
транзакцию и подтверждённую целевую схему. При наличии `done` продолжает запуск закреплённого
целевого комплекта. При необъяснимой ревизии нужен подтверждённый сценарий восстановления.
Более ранний релиз отклоняется на обычной подготовке обновления.

Действие `recover-manager --operation-id ID` на хосте может вернуть прежний совместимый образ
мастера отдельно от состояния приложения и PostgreSQL. Оно подтверждает тот же адрес,
порт, экземпляр, журнал и ID операции по сохранённому HTTP- или HTTPS-адресу.

Защищённый `GET /api/operations/{id}/diagnostics` возвращает сведения об операции, ранее
сохранённый отказ, последнюю наблюдённую версию Compose, состояния ролей, digest, ревизии
из журнала, свободное место и inode по назначению файловых систем и ограниченную страницу
структурированных событий. Содержимое Compose, `.env`, произвольный Docker stdout и данные
аутентификации не включаются. Наблюдение содержит время съёма.

## Переход из прежнего менеджера

Для DVT `1.22.0`, `1.23.0` и `1.24.0-rc1`–`rc12` со старым менеджером
обновление запускается в профиле через точную стабильную версию или `latest`.
Менеджер проверяет версию и фактическую ревизию PostgreSQL, принимает экземпляр
на базовый комплект `1.24.0`, затем продолжает закреплённый маршрут к выбранной цели.
Оператор получает результат по исходному ID. Поддерживаются следующие пары.

| Исходная версия | Ревизия БД |
| --- | --- |
| `1.22.0` | `0061` |
| `1.23.0` | `0063` |
| `1.24.0-rc1` | `0065` |
| `1.24.0-rc2` | `0068` |
| `1.24.0-rc3` | `0069` |
| `1.24.0-rc4` | `0070` |
| `1.24.0-rc5` | `0063` |
| `1.24.0-rc6`–`rc12` | `0070` |

Проверки также учитывают реальные контейнеры, исходный Compose, конфигурацию,
локальный PostgreSQL и сохранённую копию. Для несовпадающей схемы или изменённой
инфраструктуры требуется отдельный план перехода.
[Действия в старом UI](customer_installation.md)

## Ручное обследование и принятие старого bootstrap

Сначала запустите только наблюдение на Linux с локальным Docker. Доверенный список predecessor
описывает полный набор **активных** ролей с registry digest и ожидаемую Alembic-ревизию для
каждой утверждённой версии.

```sh
sudo env PYTHONPATH="$DVT_CHECKOUT" "$DVT_VENV/bin/python" \
  -m services.installation_manager.application.legacy_transition \
  --dir "$DVT_DATA" --project "$DVT_PROJECT" --predecessors "$APPROVED_PREDECESSORS"
```

Формат JSON — `{"format_version":1,"predecessors":[{"version":"…","revision":"…","images":{…}}]}`.
Проверка читает Docker labels, действительные image IDs и `RepoDigests`, рабочие Compose и
`.env`, а также ревизию из PostgreSQL. `DVT_VERSION` из `.env` только сравнивается с
наблюдаемой версией. Отчёт показывает привязки TCP, имена сетей, относительные bind-каталоги,
реплики и расхождения. Для выбора маршрута дополнительно передайте
`--target-manifest`, `--target-digest`, `--target-release` и `--trust`.

`application.legacy_adopt` — отдельный opt-in для старого bootstrap, который уже запускает
образа с admission v1 из известного совместимого комплекта. Команда проверяет подписи и pin
исходного и целевого комплектов, сверяет подписанный исходный Compose, фактический gate и
версию. Подготовленная host-конфигурация указывает тот же UUID из `installation/instance_id`,
каталог, проект, localhost bind, публичный origin, Docker backing directories и закреплённые
образы `manager`, `candidate`, `executor`. TLS-каталог содержит `ca.pem`, `cert.pem`,
`key.pem` для localhost. Сторонние сети/профили вне подписанного комплекта не переносятся.

```sh
sudo env PYTHONPATH="$DVT_CHECKOUT" "$DVT_VENV/bin/python" \
  -m services.installation_manager.application.legacy_adopt \
  --dir "$DVT_DATA" --bootstrap-config "$HOST_CONFIG" --tls-dir "$TLS_DIR" \
  --predecessors "$APPROVED_PREDECESSORS" --trust "$TRUST" \
  --source-manifest "$SOURCE_MANIFEST" --source-digest "$SOURCE_DIGEST" \
  --source-release "$SOURCE_RELEASE" \
  --target-manifest "$TARGET_MANIFEST" --target-digest "$TARGET_DIGEST" \
  --target-release "$TARGET_RELEASE"
```

Операция заменяет только веб-мастер, проверяет его ответ с тем же ID и сохраняет подтверждённый
исходный комплект. При недоступности нового веб-мастера возвращается старый контроллер,
а продолжение идёт через `legacy_adopt --dir "$DVT_DATA" --resume "$OPERATION_ID"`.
Данные, исходный PostgreSQL, работающие роли приложения и сохранённые значения `.env`
остаются на месте. Допуск этого ручного сценария требует подтверждённых подписи,
схемы, Compose и admission v1. Для прежнего менеджера в перечисленных выше
исторических версиях используйте контролируемый импорт через базовый `1.24.0`.

## Полная копия на чистом хосте

Поддерживается логическая копия формата 1 из окна обслуживания admission v1. На получателе
нужны тот же абсолютный путь экземпляра, свободный Compose project, совместимые Linux и Docker
Compose и локально проверенные прежние образы по digest, включая исходный PostgreSQL.
Папка экземпляра ещё отсутствует. Телеметрия и подтверждение идут через защищённый журнал
с тем же ID. Старый работающий источник доступен отдельно до переключения входящего трафика.

```sh
sudo env PYTHONPATH="$DVT_CHECKOUT" "$DVT_VENV/bin/python" \
  -m services.installation_manager.application.portable_restore plan --copy "$COPY"
```

План показывает digest манифеста и UTC-время копии. Записи после этой точки и внешние
эффекты ETL копия не восстанавливает. Для подтверждения передайте **оба** значения плана.

```sh
sudo env PYTHONPATH="$DVT_CHECKOUT" "$DVT_VENV/bin/python" \
  -m services.installation_manager.application.portable_restore restore-data \
  --dir "$DVT_DATA" --copy "$COPY" \
  --confirm-manifest "$BACKUP_MANIFEST_DIGEST" --confirm-loss-after "$COPIED_AT"
```

Для сохранения ошибки после точки копии можно дополнить вызов
`--source-diagnostics <закрытый JSON>`. Это авторизованный ответ исходного мастера
`/api/operations/{id}/diagnostics`, полученный после отказа. При недоступности мастера
администратор хоста может получить минимальный экспорт через
`python -m services.installation_manager.application.recovery --dir "$DVT_DATA" --operation-id "$OPERATION_ID"`
и перенаправить его в закрытый файл. В новом экземпляре сохраняется
только первый структурированный исходный отказ для того же экземпляра и операции.
При утрате исходного диска без такого экспорта доступна история до точки копии.
Если содержимое менялось или проверка не прошла, подготовка прекращается до публикации
каталога. Подготовка восстанавливает роли и БД, identity, конфигурацию, файлы и расширения
в изолированном PostgreSQL. Gate сохраняется замороженным.

```sh
sudo env PYTHONPATH="$DVT_CHECKOUT" "$DVT_VENV/bin/python" \
  -m services.installation_manager.application.restore_runtime start \
  --dir "$DVT_DATA" --operation-id "$OPERATION_ID"
```

Если настроен совместимый исполнитель с кодом восстановления, вместо вызова `start` можно
установить и использовать хостовый `host_bootstrap.py restore-start --dir ... --operation-id ...`.
Размещайте копию в каталоге, доступном этому исполнителю. Шаг связывает вновь созданный
PostgreSQL с закреплённым предыдущим комплектом. Новая запись подтверждает ту же ревизию
и frozen gate перед запуском Compose. После успешной готовности прежних образов, воркеров,
профилей, URL и защищённого мастера операция остаётся в `verifying`.

Войдите прежним администратором DVT и подготовьте свежее значение access cookie. Команда
запрашивает его без эха и проверяет аутентификацию, существующий проект, установленные расширения
через локальный Gateway, а также отсутствие незавершённых задач в замороженной БД.

```sh
sudo env PYTHONPATH="$DVT_CHECKOUT" "$DVT_VENV/bin/python" \
  -m services.installation_manager.application.restore_runtime finalize \
  --dir "$DVT_DATA" --operation-id "$OPERATION_ID" --project-id "$PROJECT_ID"
```

UUID проекта можно опустить только для экземпляра без сохранённых проектов.
Только после этих проверок исполнитель подтверждает открытие gate и завершает операцию.
Контрольный ETL для проверки профиля запускается штатным авторизованным клиентом после resume.
Если готовность или аутентификация не подтверждаются, повторяйте по тому же ID.

## Удаление

`uninstall.sh --plan --dir <каталог>` показывает подтверждённые Compose ресурсы и
место хранения данных и копий. По умолчанию удаление экземпляра оставляет конфигурацию,
данные, тома и копии. Чтобы запланировать удаление данных, добавьте `--delete-data`.
Оно требует отдельного подтверждения полного канонического пути `--confirm-data <каталог>`.
Подтверждение охватывает показанные тома и вложенные копии. Внешние копии и образы сохраняются.
