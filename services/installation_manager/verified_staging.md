# Проверенный релиз и подготовка

Контракт v1 используется издателем релиза, Distribution и Linux-исполнителем. В Python схему определяет `SignedRelease` из [release_manifest.py](domain/release_manifest.py). Её можно экспортировать командой `SignedRelease.model_json_schema(by_alias=True)`. [Подписанный beta-комплект](../../tests/data/installation_manager/verified_staging/) содержит манифест, Compose, bootstrap и корень доверия. Синтетические digest образов из этого комплекта используют только тесты контракта. Файл `fixtures.py` воспроизводит комплект командой `python -m tests.data.installation_manager.verified_staging.fixtures`. Закрытые ключи fixture публичны и предназначены исключительно для тестов.

## Закрепление и доверие

- `ReleasePin` содержит `release_id` и SHA-256 полных байтов полученного JSON-конверта, включая форматирование и завершающий перевод строки. По одному ID операции используется тот же pin. Поля `key_signature` и `manifest_signature` содержат подписи Ed25519 в hex нижнего регистра. JSON со вложенными дублирующимися ключами отвергается.
- Подпись сертификата ключа вычисляется над ASCII-префиксом `DVT release signing key v1`, байтом `0x00` и каноническим JSON поля `signing_key`. Подпись конверта использует префикс `DVT release manifest v1`, байт `0x00` и канонический JSON поля `payload`. Канонический JSON v1 эквивалентен Python `json.dumps(value, sort_keys=True, separators=(",", ":"), ensure_ascii=True)` в ASCII. Поля v1 типизированы, числа целые.
- Bootstrap отдельно получает доверенные корни Ed25519 по ID и список отозванных подписывающих SHA-256 fingerprints (от 32 сырых байтов открытого ключа). Конверт доставляет подписанный корнем сертификат публичного release-ключа. Даты в UTC имеют формат `YYYY-MM-DDThh:mm:ssZ`. Время выпуска входит в интервал сертификата. Конец действия манифеста должен укладываться в срок действия сертификата. При каждой проверке текущее доверенное время лежит между выпуском включительно и истечением исключительно. Отзыв или удаление корня действует на все манифесты соответствующего ключа, включая уже сохранённые.
- Ротация онлайн-ключа требует нового сертификата. Для проверяемости поддерживаемых архивов сохраняют прежний корень и старый публичный сертификат в конверте до конца заявленного срока поддержки. При смене корня в bootstrap устанавливают новый и прежний корни на период перекрытия. Истёкший или отозванный пакет требует отдельно удостоверенного релиза и нового pin. V1 не использует доверенные метки времени подписи и ретроспективное исключение для скомпрометированных ключей.
- Манифест и каждый указанный в нём файл скачивают из явно разрешённых HTTPS origins. Redirect, параметры запроса, URL credentials и наследуемые настройки proxy отключены. Корпоративная TLS-инфраструктура для файлов задаётся явным CA bundle. Сетевой путь Registry принадлежит Docker daemon и проверяется фактической командой `docker image pull --platform ... registry/repository@sha256:...`. Credentials Registry получает из явно выбранной защищённой конфигурации CLI. Названия образов, теги и `latest` не считаются доказательством содержимого.
- Для каждой платформы издатель записывает digest leaf-манифеста, а также размер передаваемых слоёв, пиковую оценку размера после распаковки и inode. Ссылки имеют вид `registry.example/repo@sha256:…` с явным Registry (для Docker Hub `docker.io/library/…`). Gateway и мигратор ссылаются на одинаковый образ. Подготовка проверяет наличие всех образов в подписанной конфигурации Compose, включая неактивные профили, и загружает только активные. При кешировании используется локальная связь `RepoDigests`, архитектура и тип descriptor, если Docker его сообщает. Будущий офлайн-импорт должен отдельно устанавливать проверяемую связь экспортированных слоёв с manifest digest. Наличие одноимённого локального тега после `docker load` ничего не удостоверяет.

## Вызов из исполнителя

1. Ожидаемая identity установлена в `OperationStore`. Доверенный слой записывает неизменяемые выбранные значения через `save_config(store, values)`, связывает UUID с `OperationRequest.config_id` и принимает запрос с `ReleasePin`. Используются значения сохранённой или уже согласованной оператором конфигурации. Кандидат RC требует `DVT_ALLOW_PRERELEASE=true` в выбранном пакете. `DVT_TASK_WORKERS_COUNT` должен совпасть с эффективным числом реплик. Дополнительные сохранённые публичные адреса остаются в списке `DVT_PUBLIC_URL`. Первый origin должен совпадать с identity. Секреты передаются только по закрытому каналу и через защищённый каталог. `StagedRelease.environment` содержит исходные значения для доверенного исполнителя. Для статуса используется структурированный журнал или очищенный план.
2. `VerifiedStaging.prepare(operation_id, manifest_url, observed=..., applied=..., bootstrap_image=...)` захватывает блокировку и готовит артефакты без запуска или остановки контейнеров. Адрес может измениться при повторе, но digest и ID релиза остаются прежними. Кеш Manifest, Compose и bootstrap проходят повторную проверку. Detached executor вызывает метод после сохранения запроса.
3. `UPDATE` принимает отдельно последний подтверждённый `applied: ReleasePin | None` и доверенный `ObservedRelease(version, revision, pin, images)`. Версию и ревизию получает исполнитель из фактических проверок приложения и БД, а ожидаемый полный набор digest работающих сервисов берёт из проверенного прежде применённого релиза. Staging независимо сверяет, что эти digest соответствуют образам ID контейнеров целевого проекта. `observed.pin` совпадает с `applied`. Для legacy, где нового указателя ещё нет, этап 06 должен независимым методом сопоставить digest каждого реально запущенного образа со старым манифестом/проверенным реестром, получить фактическую ревизию и проверить поддерживаемый маршрут. Только этот контролируемый канал передаёт оба pin как `None`. Значение версии из `.env` или пользовательского запроса не подходит. Тип `ObservedRelease` описывает снимок, а не авторизацию.
4. `INSTALL` допускает пустой рабочий проект или единственный ожидаемый bootstrap `installation_manager` в том же Compose-проекте. В последнем случае доверенный исполнитель передаёт точный `bootstrap_image`. Образ, привязка, хранилище и сеть существующего мастера должны совпасть с согласованной конфигурацией. Каталоги PostgreSQL и Valkey должны быть свежими. В v1 смена образа PostgreSQL или Valkey, привязки портов работающего сервиса, типов/источников томов, текущих подключений и учётных данных считается неподдерживаемым переходом. Допускаются уже наблюдавшаяся инфраструктура и предусмотренные добавления профиля.
5. Путь комплекта — `OperationStore.artifact_path(ArtifactKind.STAGING, operation_id)`. Файлы `manifest.json`, `compose.yaml`, `bootstrap.sh`, `plan.json` пишутся атомарно и изолированы от рабочего Compose. План без секретов содержит кандидата, известный применённый pin, наблюдаемые версии/образы и список изменений. Прежний применённый указатель остаётся независимым. В чекапойнте `source_digest` хранится digest применённого манифеста, в `target_digest` digest кандидатного манифеста, в `observed_digest` digest реально работающего Gateway. `PREPARED` подтверждает проверку комплекта, конфигурации, ресурсов и наличия активных образов. Перезапуск до применения повторяет проверку под блокировкой по тому же ID.
6. Однофайловый Compose v1 не читает другие файлы Compose, env, метки, секреты или конфиги. Он не собирает образы и не запускает хостовые hooks. Сохраняйте одни и те же параметры проекта, env, Compose и профили между проверкой и применением. В executor параметры нового пути включаются отдельно от действующих маршрутов.

## Хостовые наблюдения

- Исполнитель использует локальный Unix socket Docker и настоящую хостовую сетевую namespace, включая проверку доступности новых портов. Контейнер исполнителя для кандидата монтирует `/etc/os-release` хоста только для чтения и передаёт его путь в `HostPaths.os_release`. Он видит каталоги Docker, containerd, работы, данных и копий по реальным абсолютным хостовым путям. Информация об ОС Python-образа и его внутренний overlay непригодны для такой проверки. UID и права файлов операции должны совпадать с контрактом этапа 01.
- Корень Docker читается из локального daemon. При использовании containerd image store доверенный host bootstrap передаёт фактический корень containerd, определённый конфигурацией daemon. Он различается для system containerd и embedded containerd. Другой недоступный backing path останавливает проверку. В Linux процессам задаётся выбранный `TMPDIR`, а резерв коррелирует с его фактической ФС.
- Для быстрых повторов уже присутствующие образы проверяются по digest. Занятые ими и предыдущими релизами блоки учитываются через `statvfs`. Для отсутствующих дополнительно резервируется консервативная сумма полных сжатых и распакованных слоёв и inode плюс крупнейшие параллельные буферы. Shared layers предыдущих образов отдельно как свободные не учитываются. На одной ФС резервы складываются. Для копии используется размер текущих постоянных каталогов, к нему добавляется запас профиля. Исходное приложение может продолжать запись, поэтому непосредственно перед копией исполнитель следующего этапа повторно проверяет доступность места. Типы ФС с квотами и отдельными snapshotter требуют подтверждённого профиля.
- Compose и загрузчики работают с общим монотонным дедлайном и ограничением одной попытки. Прерывание охватывает группу процессов, включая молчащий Compose plugin. Работа стороннего демона по сокету не входит в группу процессов. При сетевой ошибке вывод дочерних команд анализируется внутри адаптера для кода и безопасного действия. На внешнюю границу выходят типизированные причины, без stdout Compose и credentials. DNS, TLS и доступ проверяются по реальным путям, настройки MTU и firewall остаются задачей оператора. Проверка доступности публичного DVT по его адресу после старта и readiness выполняются последующими этапами.
